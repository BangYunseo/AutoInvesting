# 전체 아키텍처 트레이싱 (Phase 1)

## 개요
> 코드베이스 분석·리팩토링 워크플로우의 Phase 1 산출물로, "데이터 유입 → 매매 판단 → 주문/기록"의 실제 흐름을 코드 기준으로 추적한다.

## 배경 / 목적
코드베이스 분석·리팩토링 워크플로우의 **Phase 1** 산출물이다. 자동매매의 일반적 파이프라인
(데이터 → 신호 → 주문)이 이 시스템에서 실제로 어떻게 구현되어 있는지를, 추측 없이 실제 소스 읽기를
근거로 트레이싱한다. (작성일: 2026-07-04)

## 본문

### 핵심 결론 — 판단이 없다
이 시스템에는 **신호/전략 생성 단계가 존재하지 않습니다.** Phase 6에서 타이밍 판단 레이어를
전부 제거했기 때문입니다. 따라서 일반적인 자동매매의 `데이터 → 신호 → 주문` 중 **가운데(신호)가
비어 있고**, 대신 사람이 설정한 **고정 수량**을 그대로 주문합니다.

```text
[크론/수동 트리거] → [설정 로드(고정수량)] → [현재가·환율 조회] → [고정수량 주문] → [DB 기록 + 이메일]
                       ↑ 여기엔 "언제 살까" 판단이 없음 (의도된 설계)
```

#### ✅ 확정된 사실 (Phase 0의 불명확 항목 해소)
`DcaAccumulationEngine.PlanPurchases`는 **목표비중을 계산하지 않습니다.** 입력 `quantities`(종목별
정수)를 받아 현재가가 있는 종목만 **그 수량 그대로** 계획에 넣고, `수량×현재가×환율`로 총액만
산출합니다. → **현재 코드의 실제 모델 = "템플릿 고정수량 매수"** (CLAUDE.md 규칙과 일치).
기존 `Documents/reference/CODE_READING_GUIDE.md`·`ONBOARDING_GUIDE.md`의 "목표비중대로 정수 매수"는 **낡은 서술**.

### 트리거 / 스케줄링

| 경로 | 방식 | 관련 코드 |
|---|---|---|
| 자동 | GitHub Actions 크론이 매일 KST 23:40 `POST /api/order/dca-run` 호출 | `.github/workflows/daily-run.yml` |
| 수동(사이클) | 같은 엔드포인트를 사람이 호출 | `OrderController.RunDcaCycle` |
| 수동(단건 주문) | `POST /api/order/manual` (BUY/SELL 즉시) | `OrderController.PlaceManualOrder` |

- **비동기 처리**: `dca-run`은 `Task.Run(...)`으로 백그라운드 실행 후 **즉시 202** 반환. 결과는 로그/이메일로 확인.
- **월 1회 멱등 가드**: 크론은 매일 호출하지만, 엔진이 `TB_APP_CONFIG.DCA_LAST_RUN_MONTH`("yyyy-MM")를
  확인해 **그 달에 이미 체결됐으면 스킵**. 체결 0건인 날은 마커를 남기지 않아 다음 날 재시도.
  (Scoped 서비스라 `IServiceScopeFactory.CreateScope()`로 스코프 생성)

### 설정 로드 단계
매매 판단을 대신하는 유일한 "입력" 단계입니다.

**설정 우선순위** (`AppConfigManager.Get`):
```text
① 환경변수  →  ② DB(TB_APP_CONFIG)  →  ③ appsettings.json  →  ④ 코드 기본값
```
- **민감정보(KIS 키·시크릿·계좌·API 접근키·Resend 키)**: 환경변수 전용(최우선). DB 저장 시 `MASTER_KEY`로 암호화.
- **DCA 설정 로드** (`DcaSettings.Load`):
  1. `DCA_TEMPLATES`(JSON) + `DCA_MONTH_MAP`(JSON, 월→템플릿Id) → 현재(KST) 월의 템플릿 선택 (`SelectTemplate`, 순수함수)
  2. 없으면 레거시 단일 설정 `DCA_QTYS`/`DCA_BUDGET_KRW`를 "기본" 템플릿 하나로 자동 이관
  3. 그것도 없으면 `appsettings.json > Dca` 폴백, 최후엔 코드 기본값(예산 100만원)
  - 월배정이 비어 있으면 첫 템플릿을 매월 사용, 배정된 달에 템플릿이 없으면 **매수 스킵**
- 편집 경로: `DcaController` (`GET/PUT /api/dca/config`) → `DcaSettings.SaveConfig` → DB 저장.

관련 코드: `Data/AppConfigManager.cs`, `Core/DcaSettings.cs`, `Data/DTO/DcaTemplate.cs`, `Controllers/DcaController.cs`

### 주문 실행 단계

#### 적립 사이클 (DailyExecutionService.RunDcaCycleAsync)
```text
멱등 가드 확인
  → SessionManager.GetClient() (KIS 키 유무·IS_PAPER_TRADING로 Sim/KIS 분기)
  → 로그인 (실패 시 스킵, finally에서 보고서 발송)
  → DcaSettings.Load() (현재 월 고정수량+예산)
  → DcaAccumulationEngine.AccumulateAsync(quantities, budget)
       → GetExchangeRateAsync() (0 이하면 중단)
       → 종목별 GetCurrentPriceAsync() (실패 종목 제외)
       → PlanPurchases() (순수함수: 고정수량 계획 + 총액)
       → 예산 초과 시 경고 이메일만(수량 유지)
       → 종목별 PlaceBuyOrderAsync() → TradeHistoryDAO.Insert()
  → 체결 1건↑이면 DCA_LAST_RUN_MONTH 저장
  → finally: SendDcaReportAsync() (항상 발송)
```

#### 수동 단건 주문 (OrderController.PlaceManualOrder) — 동기 응답
- 입력 검증(ticker/qty/orderType) → 로그인 → **매도 안전가드**(보유 수량 범위 내에서만 SELL 허용)
  → 가격 미지정 시 현재가 사용 → `PlaceBuy/SellOrderAsync` → `TradeHistoryDAO.Insert`.

- **브로커 추상화**: 모든 주문/시세는 `IBrokerClient` 경유. 구현체 `SimBrokerClient`(모의) / `KisBrokerClient`(실거래, Polly).
  KIS 실제 HTTP·토큰 세부는 고위험 모듈로 분류해 **Phase 3에서 별도 정밀 추적**(현재는 인터페이스 경계까지만).

관련 코드: `Core/DailyExecutionService.cs`, `Core/DcaAccumulationEngine.cs`, `Core/IBrokerClient.cs`, `Core/SessionManager.cs`, `Core/KisBrokerClient.cs`, `Core/SimBrokerClient.cs`, `Core/KisTokenManager.cs`

   테이블 스키마·`appsettings.json`의 판단 설정)는 발견 시 **삭제**한다(사유: 불필요한 코드가 실제 작업을
   오염시킴). 단 경계: **죽은 코드는 삭제(git 복구 가능)**하되, **운영 DB 테이블의 물리 DROP은 영구 손실**
   이므로 코드 참조 제거와 분리해 별도 확인받는다. `TB_MARKET_SNAPSHOT`은 규칙상 보존.

   - 확인된 생존 코드(유지): `GetCashBalanceAsync`(PortfolioController 사용).

## 정리 / 결론
- 이 시스템은 `데이터 → 신호 → 주문` 파이프라인에서 **신호(판단) 단계가 의도적으로 비어 있다.** 사람이 설정한 현재 월 템플릿의 **고정 수량**을 그대로 매수한다.
- 트리거는 GitHub Actions 크론(매일 KST 23:40)의 `dca-run`이며, 엔진의 **월 1회 멱등 가드**(`DCA_LAST_RUN_MONTH`)로 실제 체결은 월 1회로 수렴한다.
- 설정은 `환경변수 → DB → appsettings → 코드 기본값` 순으로 로드되며, 민감정보는 환경변수 전용이다.
- 주문/시세는 모두 `IBrokerClient`를 경유(Sim/KIS 분기)하고, 체결은 `TB_TRADE_HISTORY`에 기록·이메일로 리포팅된다.
- `PlanPurchases`가 목표비중이 아닌 **고정수량 매수**임이 코드로 확정되어, 낡은 가이드 문서(목표비중 서술)는 정정 대상이다.
