# 모듈별 우선순위 매트릭스

## 개요
> 코드베이스 분석·리팩토링 워크플로우의 Phase 2 산출물로, 어떤 모듈부터 손댈지 착수 순서를 정한다.

## 배경 / 목적
이 문서는 코드베이스 분석·리팩토링 워크플로우의 Phase 2 결과물이다(작성일 2026-07-04). 모듈마다 복잡도·위험도·이해필요도를 점수화해 매트릭스로 정리하고, 이를 근거로 리팩토링 착수 순서를 확정한다.

우선순위 원칙(플랜)은 다음과 같다. 위험도 낮고 이해필요도 높은 것 먼저, 주문·시크릿 등 고위험은 맨 마지막으로 두고 매 단계 사용자 확인을 거친다.

## 본문
### 평가 기준
각 항목을 1~3점으로 평가한다.

| 기준 | 1 (낮음) | 3 (높음) |
|---|---|---|
| **복잡도** | 단순/짧음 | 얽힘, 책임 혼재, 외부 프로토콜 |
| **위험도** | 잘못돼도 조회/표시만 영향 | 실제 자금·주문·인증·시크릿에 직결 |
| **이해필요도** | 이미 자명 | 사용자가 가장 이해하고 싶은 핵심 흐름 |

### 죽은 코드 제거 (별도 항목)
Phase 1에서 참조 0으로 확인된 죽은 코드. **위험도 낮음(미사용 + git 복구 가능), 정리 가치 높음.**

- DTO: `AdaptiveThresholdStatusDto`, `DailyTokenUsageDto`, `StrategySummaryDto`, `AssetMasterDto`, `PriceRangeDto`
- 브로커 메서드 체인: `IBrokerClient.GetPriceRangeAsync` / `GetOhlcvAsync` + 양 구현체 + `OhlcvDto`
- 스키마 테이블(코드 참조 0): `TB_SELL_PLAN`, `TB_TOKEN_USAGE`, `TB_AI_PERFORMANCE`, `TB_INVEST_STRATEGY`, `TB_ASSET_MASTER` → **create_tables.sql의 생성문만 제거**(운영 DB 물리 DROP은 별도 확인)
- `appsettings.json`·`AppConfigManager`의 판단 레이어 설정 매핑(`Rebalance`/`Consensus`/`FxAdvisor`/`StrategyType`/`ActiveStrategy`)

### 제안하는 진행 순서
**초반(안전·고이해도) → 후반(고위험, 확인 필수)** 원칙. 각 단계는 Phase 3 루프(이해문서→스모크테스트→제안→확인→적용→검증→문서→커밋)를 1모듈씩 적용한다.

| 순서 | 대상 | 근거 |
|:---:|---|---|
| **1** | **죽은 코드 제거** (위 별도 항목, 테이블 물리삭제 제외) | 이후 모든 이해를 방해하는 노이즈 먼저 제거. 저위험 |
| **2** | `AppConfigManager` + `DcaSettings` | 설정 흐름 = "무엇을 살지"의 근원. 죽은 키 정리 병행. 저~중위험 |
| **3** | `SimBrokerClient` | 안전한 시뮬레이션으로 브로커 인터페이스 감 잡기 |
| **4** | `DcaAccumulationEngine` (+ `PlanPurchases` 스모크테스트) | 적립 심장부. 이해필요도 최고. Sim 모드로 검증하며 신중 |
| **5** | `DailyExecutionService` | 사이클/멱등가드 흐름 |
| **6** | 조회 컨트롤러 (`Price`→`History`→`Portfolio`→`Config`→`Dca`→`Auth`) | 저위험, 표면 API 이해 |
| **7** | Utils (`Logger`→`ExchangeRate`→`Notification`→`ApiKeyAuth`) | 주변 인프라 |
| **8** | `SessionManager` → `OrderController`/`TestController` | 주문 경로 진입 — 확인 강화 |
| **9** | **`CryptoUtil` → `KisTokenManager` → `KisBrokerClient`** | 최고위험(시크릿·인증·실거래 주문). **맨 마지막, 매 변경 사용자 확인** |

4번(엔진)은 이해필요도가 최고라 앞당겼지만 실주문 위험이 있어, 반드시 `IS_PAPER_TRADING`(SimBroker) 모드 + `PlanPurchases` 단위테스트로만 검증하고 로직 의미는 바꾸지 않는다(동작 보존).

## 정리 / 결론
- 착수 순서는 위험도 낮고 이해필요도 높은 모듈을 먼저, 주문·시크릿 등 고위험 모듈을 맨 마지막에 두는 원칙을 따른다.
- 실제 진행은 죽은 코드 제거(1) → 설정 흐름(2) → 시뮬레이션 브로커(3) → 적립 엔진(4) → 사이클 서비스(5) → 조회 컨트롤러(6) → Utils(7) → 주문 경로(8) → 시크릿·인증·실거래(9) 순서다.
- 적립 엔진과 실거래·인증 경로는 동작 보존을 전제로, SimBroker 모드와 단위테스트로만 검증하며 매 변경 시 사용자 확인을 거친다.
