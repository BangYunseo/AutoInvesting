# 로컬 검증환경 구축과 체결대사 전환

## 개요
> 로컬에서 실제 KIS API를 호출할 수 있는 환경을 만들고, 그 환경에서 `inquire-ccnl` 응답을 확인한 뒤 체결 대사를 보유 수량 차이 추론에서 주문별 체결 수량 조회로 전환했다. 주문 직전 잔고 스냅샷(`Before`)을 제거해 거짓 체결 판정 경로도 함께 없앴다.

## 배경 / 목적

`[2026-09-11] 01_체결대사_주문체결내역조회_전환.md`에서 조회 메서드를 붙였지만 실제로 호출해보지 못했다. 로컬에 설정 파일이 없어 `dotnet run`이 기동 단계에서 멈췄기 때문이다.

응답 형태를 확인하지 않고 대사를 전환하면, 잘못된 체결 수량으로 판정하게 되고 그 결과는 중복 매수 또는 적립 누락이다. 잔고 조회에서 `OVRS_EXCG_CD=NASD`의 의미가 실전과 모의에서 달라 종목이 누락된 전례가 있어, 문서만 보고 짜는 것을 신뢰할 수 없었다.

그래서 개발보다 로컬 환경 구축을 먼저 했다.

## 본문

### 로컬 환경 구성

운영 시크릿을 로컬로 가져오지 않는 것을 원칙으로 잡았다. 키 이름은 같되 값은 전부 개발 전용이다.

| 키 | 운영 | 로컬 |
|---|---|---|
| `MASTER_KEY` | Render 환경변수 | 로컬에서 새로 생성 |
| `KIS_APP_KEY` / `SECRET` / `ACCOUNT_NO` | 실전 발급분 | 모의투자 발급분 |
| `IS_PAPER_TRADING` | `0` | `true` |
| `API_ACCESS_KEY` | Render 환경변수 | 로컬 전용 문자열 |
| `DATABASE_URL` | Neon | **설정하지 않음** |

`MASTER_KEY`를 운영과 분리할 수 있는 근거는 용도가 둘인데 하나가 로컬에서 불필요하기 때문이다. DB에 저장된 시크릿을 복호화하는 용도와 로그인 토큰 서명 용도인데, 시크릿을 DB에 저장하는 경로가 2026-08-06에 제거돼 복호화할 대상이 없다. 로컬에서는 토큰 서명에만 쓰이므로 base64 32바이트면 무엇이든 된다.

`DATABASE_URL`은 설정하지 않는 편이 낫다. `DBManager`가 환경변수를 직접 읽고, 없으면 로컬 PostgreSQL을 기본값으로 쓴다.

```csharp
private string GetConnectionString()
{
    var envUrl = Environment.GetEnvironmentVariable("DATABASE_URL");
    if (string.IsNullOrEmpty(envUrl))
    {
        // 로컬 개발용 기본 접속 정보
        return "Host=localhost;Username=postgres;Password=postgres;Database=autoinvest";
    }

    // Render.com 등에서 제공하는 URI 형식 (postgres://user:pass@host:port/db) 파싱
    if (envUrl.StartsWith("postgres://") || envUrl.StartsWith("postgresql://"))
    {
        var uri = new Uri(envUrl);
        var userInfo = uri.UserInfo.Split(':');
        return $"Host={uri.Host};Port={(uri.Port > 0 ? uri.Port : 5432)};Username={userInfo[0]};Password={(userInfo.Length > 1 ? userInfo[1] : "")};Database={uri.LocalPath.TrimStart('/')};SslMode=Require;Trust Server Certificate=true;";
    }

    return envUrl;
}
```

이 방식이면 로컬에 접속 문자열이 하나 줄고, 운영 DB에 실수로 붙을 경로가 없어진다. 스키마는 기동할 때 `create_tables.sql`이 자동 실행되므로 빈 DB만 만들면 된다.

### 설정 우선순위 확인

`appsettings.local.json`은 환경변수보다 뒤에 읽힌다.

```
환경변수 → DB(TB_APP_CONFIG) → appsettings.local.json → appsettings.json → 코드 기본값
```

로컬에는 환경변수가 하나도 설정돼 있지 않아 파일이 실질적 출처가 된다. 운영은 환경변수가 전부 차 있고 `appsettings.local.json`이 `.gitignore` 대상이라 배포에 존재하지 않는다. 코드를 바꾸지 않아도 두 환경이 자연스럽게 갈린다.

`MASTER_KEY`만 우선순위가 반대다. `CryptoUtil`은 파일을 먼저 본다.

```csharp
private static string? GetConfigValue(string key)
    => _config?[key] ?? Environment.GetEnvironmentVariable(key);
```

`AppConfigManager.Get`과 방향이 달라 일관성이 깨져 있다. 지금은 로컬에 환경변수가 없어 결과가 같지만 알아둘 지점이다.

키 경로도 종류마다 다르다. `MASTER_KEY`는 최상위 문자열이고 나머지는 섹션이다.

```json
{
  "MASTER_KEY": "base64 32바이트",
  "Trading": { "IsPaperTrading": true },
  "Kis": { "AppKey": "", "AppSecret": "", "AccountNo": "", "AccountProd": "" },
  "Security": { "ApiAccessKey": "" }
}
```

`API_ACCESS_KEY`가 `Security:ApiAccessKey`로 매핑되는 것은 `AppConfigManager.ResolveFromConfiguration`이 한다.

### 구축 중 막힌 지점

#### 출력 폴더의 설정 파일 복사본

프로젝트 루트의 `appsettings.local.json`을 고쳤는데 서버가 계속 옛 값을 읽었다. 인증이 401로 막혔다.

원인은 빌드 시 출력 폴더로 복사되는 사본이었다.

```
appsettings.local.json                      ← 편집한 파일
bin\Debug\net8.0\appsettings.local.json     ← 서버가 읽는 파일
```

`dotnet run`의 ContentRoot가 출력 폴더이므로 그쪽을 읽는다. 루트만 고치고 빌드를 다시 하지 않으면 반영되지 않는다.

시크릿 사본이 `bin` 아래에도 생긴다는 뜻이므로, 나중에 로컬 시크릿을 정리할 때 출력 폴더도 함께 지워야 한다.

#### PowerShell의 curl 별칭

PowerShell에서 `curl`은 `Invoke-WebRequest`의 별칭이라 `-H` 옵션을 받지 못한다. 헤더 없는 요청은 통과하지만 헤더를 붙이는 순간 깨진다.

```powershell
curl.exe -H "x-api-key: 값" http://localhost:5000/api/order/dca-schedule
Invoke-RestMethod -Uri "http://localhost:5000/api/order/dca-schedule" -Headers @{ "x-api-key" = "값" }
```

둘 중 하나를 써야 한다.

### inquire-ccnl 실호출 검증

`TestController`에 임시 엔드포인트를 붙여 호출했다.

```csharp
        [HttpGet("order-fills")]
        public async Task<IActionResult> TEST()
        {
            var client = _session.GetClient();
            var fills = await client.GetOrderFillsAsync("20260101", "20260911");
            return Ok(fills);
        }
```

모의계좌에서 14건이 조회됐다.

```
[Session] 거래 모드: 모의투자
[Session] KIS API 클라이언트 생성 (모의 모드)
[KisToken] 토큰 발급 성공
[KisBroker] 주문 체결 내역 조회: 20260101~20260911 14건
```

필드별 확인 결과다.

| 필드 | 결과 |
|---|---|
| `orderNo` | 채워져 옴. 대사 매칭 키로 쓸 수 있다 |
| `orderQty` | 정상 |
| `filledQty` | 정상. 파싱도 문제없다 |
| `unfilledQty` | 정상 |
| `statusName` | **비어 있음** |
| `rejectReason` | 확인하지 않음 |

`orderQty`와 `filledQty`가 일치하고 `unfilledQty`가 0이라 정합성이 맞았다. 잔여를 `orderQty - filledQty`로 계산하는 설계가 성립한다.

`statusName`이 비는 이유는 확인하지 않았다. 모의계좌가 `prcs_stat_name`을 채우지 않는 것으로 추측된다. 잔고 조회에서도 실전과 모의의 동작이 달랐던 전례가 있다. 대사 판정은 수량으로 하므로 이 필드가 없어도 지장은 없다.

조회된 14건이 모두 전량 체결이라 부분 체결과 미체결 케이스를 실데이터로 검증하지 못했다.

### 체결 대사 전환

#### 주문 직전 잔고 조회 제거

`RunDcaCycleAsync`에서 이 블록을 삭제했다.

```csharp
                    Dictionary<string, int> beforeQty;
                    try
                    {
                        beforeQty = (await client.GetHoldingsAsync())
                            .GroupBy(h => h.Ticker, StringComparer.OrdinalIgnoreCase)
                            .ToDictionary(g => g.Key.ToUpper(), g => g.Sum(h => h.Qty), StringComparer.OrdinalIgnoreCase);
                    }
                    catch (Exception ex)
                    {
                        beforeQty = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase);
                        Logger.Warn($"[DCA] 주문 전 보유 수량 조회 실패 : 체결 대사 불가: {ex.Message}");
                    }
```

이 경로가 확정 결함이었다. 조회가 실패하면 빈 딕셔너리로 진행하는데, `SavePendingSnapshot`의 유일한 가드가 접수 건수가 0인지뿐이라 빈 스냅샷이 그대로 저장됐다. 대사 시점에 `before`가 0이 되고 `delta`가 기존 보유 전량이 되어 클램프를 거치면 전 종목이 FILLED로 판정됐다. `delta`가 음수가 아니므로 매도 감지 안전망도 발동하지 않았다.

주문 직전 보유 수량이 더 이상 필요 없으므로 원인이 사라졌다. KIS 호출도 한 번 줄었다.

#### 스냅샷 구조 축소

```csharp
        private sealed class PendingSnapshot
        {
            public string Month { get; set; } = string.Empty;
            public List<PendingOrder> Ordered { get; set; } = new List<PendingOrder>();
        }
```

`Before` 필드를 제거했다. `SavePendingSnapshot`의 `beforeQty` 인자도 함께 뺐다.

`System.Text.Json`은 클래스에 없는 필드를 무시하므로, 기존 JSON에 `Before`가 남아 있어도 역직렬화가 깨지지 않는다.

`Month`와 `Ordered`는 남겼다. `Ordered`가 대사 대상을 알려주는 유일한 정보이기 때문이다. 이것을 `TB_TRADE_HISTORY`에서 읽도록 바꾸는 것은 다음 단계다.

#### 판정부 교체

잔고 차이 추론을 주문별 체결 수량 조회로 바꿨다.

```csharp
                // 주문 단위 체결 수량 기록(정확한 값)
                var kstNow = DateTime.UtcNow.AddHours(9);
                string from = kstNow.AddDays(-3).ToString("yyyyMMdd"); 
                string to = kstNow.ToString("yyyyMMdd");

                var filledByOrderNo = (await client.GetOrderFillsAsync(from, to))
                    .Where(f => !string.IsNullOrEmpty(f.OrderNo))
                    .GroupBy(f => f.OrderNo)
                    .ToDictionary(g => g.Key, g => g.Sum(x => x.FilledQty));

                int totalOrdered = 0, totalFilled = 0;
                var lines = new List<string>();

                foreach (var o in snap.Ordered)
                {
                    if (string.IsNullOrEmpty(o.OrderNo)) Logger.Warn($"[Reconcile] {o.Ticker} 주문번호 미수신으로 체결 판정이 불가능합니다.");

                    filledByOrderNo.TryGetValue(o.OrderNo ?? "", out int filled);
                    filled = Math.Min(filled, o.Qty);

                    totalOrdered += o.Qty;
                    totalFilled += filled;

                    string status;
                    if (filled == 0)
                    {
                        status = "FAILED";
                    }
                    else if (filled < o.Qty)
                    {
                        status = "PARTIAL";
                    }
                    else
                    {
                        status = "FILLED";
                    }
                    TradeHistoryDAO.UpdateStatusByOrderNo(o.OrderNo, status);

                    lines.Add($"{o.Ticker} {o.Qty}주 — {status}");
                    Logger.Info($"[Reconcile] {o.Ticker} 주문 {o.Qty}주 — {status}");
                }
```

조회 범위를 3일로 잡은 이유는 날짜가 미국 현지 기준이기 때문이다. 대사 크론이 KST 06:30에 도는데 그 시점에 미국은 전날이다. 주말과 휴장까지 감안해 넉넉히 잡았다.

`anySold` 판정과 그 분기를 삭제했다. 주문별 체결을 직접 받으므로 대사 전에 사람이 매도해도 판정이 흔들리지 않는다. 삭제 후 `else if (totalFilled == 0)`을 `if`로 바꿨다.

마커 정책은 바꾸지 않았다. 전량 미체결이면 해제하고, 부분 체결이면 유지한다.

### 남은 위험

`OrderNo`가 비어 있는 주문은 매칭되지 않아 미체결로 계상된다. 실제로는 체결됐을 수 있다.

그 주문이 그 사이클의 유일한 주문이면 `totalFilled == 0`이 되어 마커가 해제되고 다음 크론이 재매수한다. 경고 로그는 남지만 자동으로 막지는 않는다.

이 위험은 갱신 키를 `TB_TRADE_HISTORY.TRADE_ID`로 바꾸는 단계에서 해소된다. 지금 방어를 넣으면 그 단계에서 다시 걷어내야 하므로 두었다.

### 브랜치 운영

`dev`에서 작업하고 검증이 끝난 것만 `main`에 fast-forward 머지한다. GitHub Actions의 `schedule` 트리거는 기본 브랜치에서만 발화하므로 `dev` 커밋은 크론을 돌리지 않는다.

`dev`에만 두고 `main`에 넘기지 말아야 할 것이 둘 있다.

`Program.cs`의 `reloadOnChange`를 `true`로 바꿨다. 로컬에서 설정 파일을 고칠 때마다 재시작하지 않기 위해서다. 운영에서는 `false`여야 한다. Render 무료 인스턴스는 리눅스 inotify instance 한도(128)를 이웃 컨테이너와 공유하는데, 감시 대상마다 하나씩 쓰므로 자리를 못 얻으면 `CreateBuilder` 단계에서 기동이 실패한다. 2026-09-02 21:09에 실제로 겪은 장애다.

`TestController`의 `order-fills` 엔드포인트는 검증용 임시 코드다. 인증은 걸려 있고 조회만 하지만 운영에 필요하지 않다.

**`main` 머지 전에 이 둘을 되돌려야 한다.**

## 정리 / 결론

체결 판정이 추론에서 조회로 바뀌었다. 증권사가 주문별로 체결 수량을 알려주므로 잔고 차이를 계산할 필요가 없어졌고, 그 계산을 지탱하던 스냅샷의 `Before`와 매도 감지 판정이 함께 사라졌다.

거짓 FILLED 판정을 만들던 경로는 원인째 없어졌다. 고친 것이 아니라 그 값을 더 이상 쓰지 않게 됐다.

실호출로 확인한 것은 필드가 오는지까지다. 부분 체결과 미체결은 실데이터로 보지 못했다. 판정 자체는 `filledQty`와 `orderQty`를 비교하는 순수 계산이라 `SimBrokerClient`로 확인할 수 있다.

다음 단계는 `SimBrokerClient`로 `dca-run` → `reconcile` 전체 흐름을 돌려보는 것이다. Sim은 장 시간을 보지 않고 접수한 주문을 전량 체결로 돌려주므로 `TB_TRADE_HISTORY`의 `STATUS`가 `PENDING`에서 `FILLED`로 바뀌는지 확인할 수 있다.

그 뒤로는 주문을 내지 못한 종목에 `SKIPPED` 상태를 남기고, 마커를 월 단위 값에서 종목별 상태 판단으로 옮기는 순서다.
