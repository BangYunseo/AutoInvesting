# 260703 대시보드 로딩 지연 — 보유종목 중복 조회 제거

- 상태: 진행중 (사용자 테스트 대기)
- 작성/갱신: 260703

## 목적 / 요청
대시보드 화면 로딩이 지연되는 원인을 분석하고, 화면 전환 시마다 발생하는
스피너/지연을 줄인다. 우선순위가 가장 높은 개선(왕복 1회 + 400ms 절감)을 먼저 적용.

## 분석 결과 (지연 원인, 영향 큰 순)
1. **`GetHoldingsAsync()` 중복 호출** — `Dashboard.jsx`가 `/api/portfolio/summary`와
   `/api/portfolio/holdings`를 동시 호출. summary 응답에 이미 보유종목이 들어있는데
   테이블이 holdings API로 또 조회 → KIS 잔고조회 왕복 2회 + 각 400ms 강제 대기.
2. `summary` 엔드포인트의 순차 KIS 호출(holdings→cash→rate) 누적 (각 400ms 하드코딩 딜레이).
3. (모의투자 한정) `GetCashBalanceAsync`가 `Task.Delay(400)` 후 `return 0` → 400ms 낭비.
   **현재는 실전투자라 해당 없음**(실전은 실제 예수금 조회가 필요한 정당한 호출).
4. Render 콜드 스타트 — 사용자가 이번 개선 범위에서 제외(첫 로딩은 감수).
5. 첫 진입 시 토큰 발급 왕복.
6. 화면 전체가 느린 summary 완료까지 스피너로 블로킹되는 UX 게이트.

## 진행 / 결정
- 우선순위 1번만 적용: `Dashboard.jsx`에서 `/api/portfolio/holdings` 호출을 제거하고
  테이블이 `summary.holdings`(summaryHoldings)를 재사용하도록 변경.
- 하단 보유종목 상태/조회 함수(holdings/holdingsLoading/holdingsError/holdingsUpdated/fetchHoldings) 삭제.
- 테이블의 "새로고침" 버튼·타임스탬프를 summary 기준으로 통일.
- 효과: 대시보드 1회 로드 시 KIS 잔고조회 왕복 2→1회, Rate limit 대기 400ms 절감.
- 백엔드 `PortfolioController.GetHoldings`(/holdings) 엔드포인트는 그대로 둠(다른 사용처 대비).
- `npx vite build` 성공(오류 0).
