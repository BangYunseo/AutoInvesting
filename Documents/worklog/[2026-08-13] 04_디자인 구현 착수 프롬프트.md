# 디자인 구현 착수 프롬프트

## 개요
> `03_UI 디자인 정의 항목.md`를 채운 뒤, 새 세션에 그대로 붙여넣어 UI 재설계 구현을 시작할 수 있는 프롬프트다. 빈칸을 대신 채우지 못하게 막고 단계마다 확인을 받도록 설계했다.

## 배경 / 목적

설계는 사람이 하고 구현은 에이전트가 한다. 그 경계를 프롬프트에 못 박아 두지 않으면 두 가지가 반드시 일어난다.

첫째, 채워지지 않은 항목을 에이전트가 그럴듯한 기본값으로 메운다. 그 순간 설계 문서는 장식이 되고 화면은 도구의 취향이 된다. 원 결정목록이 경계한 지점이 정확히 이것이다.

둘째, 실주문 경로를 스타일 작업 중에 건드린다. `Order.jsx`는 1169줄이고 그 안에 주문 파라미터와 금액 계산과 스타일이 같은 JSX에 얽혀 있다. 스타일만 고치겠다는 의도로도 로직 줄이 diff에 들어간다.

그래서 이 프롬프트는 두 가지를 강제한다. **빈칸은 질문으로 되돌리고, 금지 구간은 diff 등장 자체를 오류로 취급한다.**

프롬프트를 문서로 남기는 이유는 재사용이다. 재설계는 한 번에 끝나지 않고 단계마다 세션이 끊긴다. 매번 같은 전제를 다시 설명하지 않으려면 붙여넣을 것이 하나 있어야 한다.

## 본문

### 착수 전 준비 확인

프롬프트를 쓰기 전에 아래가 준비돼 있어야 한다. 하나라도 비면 에이전트가 질문으로 멈추므로, 미리 확인하는 편이 왕복이 줄어든다.

| # | 준비물 | 어디에 |
|---|---|---|
| 1 | 설계 정의값 | `03_UI 디자인 정의 항목.md` 의 `답` 열. 최소 A·B·E·N·O |
| 2 | Tailwind 도입 결정 D1~D8 | `02_Tailwind 전환 수정범위 분해.md` §0-4. 최소 D2·D3·D4 |
| 3 | 작업 대상·제외 화면 | 03의 B-1 |
| 4 | 워킹트리 정리 | 미커밋 변경 없는 상태 |
| 5 | 빌드 통과 | `cd Frontend && npm run build` |

D1~D8은 03이 아니라 02에 있다. 03은 무엇을 만들지, 02는 어떻게 만들지를 담는다. 둘 다 필요하다.

### 착수 프롬프트

새 세션에 아래 블록을 그대로 붙여넣는다.

```text
AutoInvesting 프론트엔드 UI를 재설계된 디자인으로 교체한다.
설계는 이미 확정되어 문서에 있다. 너는 구현만 한다.

# 1. 먼저 읽을 것 (순서대로, 전문. 요약해서 읽지 말 것)

1) CLAUDE.md 와 .agents/rules/ 하위 전체
2) Documents/worklog/[2026-08-13] 03_UI 디자인 정의 항목.md
   → 설계 확정값. 디자인에 관한 유일한 진실 원천
3) Documents/worklog/[2026-08-13] 02_Tailwind 전환 수정범위 분해.md
   → 작업분해(S0~S6), 위험도 분류, 금지 구간, 검증 명령, 커밋 단위
4) Documents/worklog/[2026-08-13] 01_AutoInvesting UI 리디자인 결정목록.md
   → 용어 정의 불일치표, 커스터마이징 계층 L1~L6, 조사 결과

읽은 뒤 착수 전에 아래를 보고한다.
- 03에서 비어 있는 항목 목록
- 02의 D1~D8 중 결정되지 않은 것 목록
- 그 미결이 어느 단계를 막는지

# 2. 절대 규칙

- 03의 `답` 열이 빈 항목을 대신 채우지 않는다. 추측한 기본값을 넣지 않는다.
  그 항목에 의존하는 작업만 멈추고 질문하고, 의존하지 않는 작업은 계속 진행한다.
- 03에 `현행 유지`라고 적힌 것은 결정이다. 빈칸과 다르게 취급한다.
- 03의 값과 현재 코드가 다르면 03을 따른다.
- 02 §4의 무접촉 줄 범위는 건드리지 않는다. diff에 등장하면 그 자체가 오류다.
  최소한 아래는 절대 수정 금지다.
    Frontend/src/App.jsx        19-21 (인증 가드), 56-65 (라우트)
    Frontend/src/main.jsx       전체 (fetch 인터셉터·토큰 주입)
    Frontend/src/pages/Order.jsx      1-6, 232-703, 1144-1164
    Frontend/src/pages/DcaConfig.jsx  1-354
- 판단 레이어를 재도입하지 않는다 (.agents/rules/recommended_rules.md).
  세금 추정과 집행 판정은 표시 전용이며, 매수 의사결정에 어떤 값도 흘려보내지 않는다.
- 시크릿·개인정보·DB 접속정보를 코드·로그·커밋·문서에 넣지 않는다.
- 저장소는 public이다. 실보유 종목·금액·계좌 정보를 코드나 문서에 남기지 않는다.
- Tailwind 유틸리티 이름을 문자열 보간으로 조립하지 않는다.
  `bg-${tone}` 같은 코드는 개발 서버에서는 보이고 프로덕션 빌드에서만 색이 사라진다.

# 3. 작업 순서

02 §2의 S0~S6 을 그대로 따른다. 순서를 바꾸지 않는다.
각 단계마다 아래 6개를 빠짐없이 수행한다.

1. 이 단계가 의존하는 03·02 항목이 채워졌는지 확인. 비어 있으면 질문하고 멈춘다.
2. 구현.
3. 02 §6 의 해당 검증 명령을 실행하고 출력을 그대로 붙여 보고한다.
   최소: cd Frontend && npm run build && npm run lint
4. 02 §6-2 의 육안 체크리스트 중 해당 항목을 나열하고, 내가 확인할 수 있게 무엇을
   봐야 하는지 알려준다.
5. 커밋. .agents/rules/git-conventions.md 준수 (한국어, `type: 제목`, 스코프 없음).
6. 다음 단계로 넘어가기 전에 멈추고 내 확인을 받는다.

# 4. 브랜치와 배포

.agents/rules/git-conventions.md 의 새 브랜치 라이프사이클을 따른다.

- feature/ui-redesign 에서 작업한다. main 에 직접 커밋하지 않는다.
- main 은 Render 배포 대상이다. 머지는 내가 직접 테스트해 OK 한 뒤에만 한다.
- push 는 매번 명시적으로 확인받고 실행한다.
- push 전에 git fetch 로 원격이 앞서갔는지 확인한다.

# 5. S6 (실주문·적립 실행 화면) 특칙

이 단계는 실자금 경로다. 아래를 추가로 지킨다.

- IS_PAPER_TRADING=1 (SimBroker) 모드로 먼저 검증한다.
- 02 §2 S6 의 육안 체크리스트 9항목을 전부 수행한다.
- 하위 단계(6-1 ~ 6-10)마다 개별 커밋한다.
- 02 §6-1 ③ 의 금지구간 접촉 감지 명령을 매 하위 단계 후 실행한다.
  출력이 있으면 즉시 중단하고 보고한다.

# 6. 보고 형식

단계마다 아래 4개만 보고한다. 장문 설명은 하지 않는다.

- 바꾼 것: 파일과 줄 범위
- 검증: 명령 출력 그대로
- 미결: 질문할 것
- 다음: 다음 단계 이름

# 7. worklog

착수 시 Documents/worklog/ 에 작업 보고서를 먼저 만든다.
.agents/rules/worklog.md 규칙과 create-md 스킬 형식을 따른다.
단계마다 갱신하고, 커밋 해시는 적지 않는다.

# 8. 지금 할 일

1번의 문서 4개를 읽고, 착수 전 보고(미결 항목 목록)만 하고 멈춘다.
내 확인 없이 코드를 수정하지 않는다.
```

### 부분 착수용 변형

설계를 전부 채우지 않고 일부만 확정한 상태에서 시작하려면, 위 프롬프트의 `# 8. 지금 할 일`을 아래로 바꾼다.

```text
# 8. 지금 할 일

1번의 문서 4개를 읽고 착수 전 보고를 한 뒤, 03에서 채워진 항목만으로 진행
가능한 단계를 골라 제안한다. 빈 항목에 의존하는 단계는 목록에서 제외하고
무엇이 막고 있는지 적는다. 내 승인 후 그 단계부터 시작한다.
```

빈칸이 많은 상태에서도 S0(설정)·S1(죽은 코드 정리)·S3의 일부는 설계값과 무관하게 진행할 수 있다. 다만 S2(토큰 이관)는 D·E·F가 채워지지 않으면 두 번 작업하게 되므로 미루는 편이 낫다.

### 이 프롬프트가 막는 것

| 막는 것 | 어떻게 |
|---|---|
| 빈칸을 도구가 채움 | §2 첫 줄 + §3 1번 + §8의 "보고만 하고 멈춘다" |
| 실주문 로직 훼손 | §2의 줄 범위 명시 + §5의 접촉 감지 명령 |
| 프로덕션에서만 깨지는 클래스 | §2 마지막 줄 (문자열 보간 금지) |
| 한 번에 다 고치고 검증 못 함 | §3 6번 (단계마다 멈춤) |
| main 직행 배포 | §4 |
| 판단 레이어 재도입 | §2 |
| 공개 저장소에 실보유 정보 노출 | §2 |

### 프롬프트를 고칠 때

문서 번호나 경로가 바뀌면 `# 1. 먼저 읽을 것`의 경로 4개를 함께 고친다. 경로가 틀리면 에이전트가 문서를 못 찾고 자기 판단으로 진행한다. 그것이 이 프롬프트가 막으려는 상태다.

금지 줄 범위(`# 2`)는 파일이 편집되면 밀린다. S4 이후 단계에 들어갈 때 02 §4를 다시 읽어 줄 번호를 갱신하고, 프롬프트에도 반영한다.

## 정리 / 결론

프롬프트의 핵심은 세 줄이다.

빈칸은 채우지 말고 질문한다. 금지 구간은 diff 등장이 곧 오류다. 단계마다 멈춘다.

나머지는 이 세 줄을 어디에 어떻게 적용하는지에 대한 서술이다. 프롬프트를 줄일 일이 생기면 이 세 줄과 읽을 문서 목록만 남기면 된다.

착수 전 준비물 5개 중 D1~D8이 가장 놓치기 쉽다. 설계 문서(03)를 다 채우고도 구현 결정(02 §0-4)이 비어 있으면 S0에서 바로 막힌다.
