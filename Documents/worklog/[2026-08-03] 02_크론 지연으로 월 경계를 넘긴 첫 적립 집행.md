# 크론 지연으로 월 경계를 넘긴 첫 적립 집행

## 개요
> 실계좌 첫 적립이 체결됐으나 의도한 7월 템플릿이 아니라 8월 템플릿이 집행됐다. GitHub Actions 스케줄 지연 1시간 41분이 KST 자정을 넘겨 엔진의 월 판정을 다음 달로 뒤집은 것이 원인이다. 원인 확정 과정과 크론 시각 재설계, 그리고 월 판정 기준을 KST로 통일한 결정 근거를 남긴다.

## 배경 / 목적

실계좌 전환 후 외화 예수금을 넣고 첫 적립을 기다렸다. 다음 날 체결이 확인됐으나 매수된 종목이 7월 배정 템플릿(BND 5주 + VTI 8주)이 아니라 8월 배정 템플릿(QQQ 1주 + VOO 4주)이었다.

첫 실집행이므로 원인을 확정하지 않으면 매달 어느 템플릿이 쓰일지 예측할 수 없다. 기계적 적립을 목적으로 만든 시스템에서 집행 결과가 비결정적인 것은 설계 목표를 정면으로 깨뜨린다.

## 본문

### 실측 데이터

`TB_TRADE_HISTORY` 조회 결과다. `TRADE_DATE`는 `DateTime.Now`이고 컨테이너 타임존이 `Asia/Seoul`이므로 KST 실행 시각이 그대로 찍힌다.

```text
TRADE_ID  TRADE_DATE            TICKER  ORDER_TYPE  QTY  PRICE     STATUS  ORDER_NO
16        2026-08-01 01:21:10   QQQ    BUY         1    282.3000  FILLED  0031541054
15        2026-08-01 01:21:09   VOO    BUY         4    87.5350   FILLED
```

집행 금액은 `4 × 87.535 + 1 × 282.30 = $632.44`다.

### 지연 폭 계산

| 항목 | 시각 |
|---|---|
| 크론 발화 (설정값 `40 14 1-31 * *`) | UTC 2026-07-31 14:40:00 |
| 발화 시각의 KST | 2026-07-31 23:40 |
| 실제 엔진 집행 | KST 2026-08-01 01:21:09 (= UTC 16:21:09) |
| **지연** | **1시간 41분 9초** |

지연 요인은 둘이다. `daily-run.yml`의 Render 웨이크업 폴링이 `seq 1 30` × `sleep 10`으로 최대 5분을 소비하고, 나머지 약 1시간 36분이 GitHub Actions 스케줄 지연이다. 무료 스케줄러가 고부하 시 밀리는 것은 문서화된 동작이다.

운영자 관찰로도 실행이 매일 KST 01시 전후에 몰린다고 확인됐다. 즉 지연이 우발적이 아니라 체계적으로 반복된다.

### 원인 — 마진이 20분뿐이었다

엔진은 집행 시점의 KST 월을 읽는다.

```csharp
/// <summary>현재(KST=UTC+9) 월을 "yyyy-MM"으로 반환합니다.</summary>
private static string CurrentKstMonth() => DateTime.UtcNow.AddHours(9).ToString("yyyy-MM");
```

템플릿 선택도 같은 기준이다.

```csharp
public static (Dictionary<string, int> Quantities, decimal BudgetKrw) Load()
{
    var templates = LoadTemplates();
    var monthMap = LoadMonthMap();
    int month = KstNow().Month;

    DcaTemplate? chosen = SelectTemplate(templates, monthMap, month);

    if (chosen == null)
    {
        Logger.Warn($"[DcaSettings] {month}월에 배정된 템플릿이 없어 이번 사이클 매수를 스킵합니다.");
        return (new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase), 0m);
    }

    var qtys = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase);
    foreach (var kv in chosen.Quantities)
        if (kv.Value > 0) qtys[kv.Key] = kv.Value;

    decimal budget = chosen.BudgetKrw > 0 ? chosen.BudgetKrw : DefaultBudgetKrw;
    Logger.Info($"[DcaSettings] {month}월 적용 템플릿='{chosen.Name}' (종목 {qtys.Count}개, 예산 {budget:N0}원)");
    return (qtys, budget);
}
```

크론이 KST 23:40에 발화하므로 KST 자정(UTC 15:00)까지 **마진이 20분**이었다. 지연 1시간 41분이 이 마진을 5배 초과해 집행 시점의 KST 날짜가 8월 1일이 되었고, 그 결과 8월 템플릿이 선택되고 마커도 `2026-08`로 기록됐다.

그 시각 미국 동부는 7월 31일 금요일 12시 21분으로 정규장 한복판이었다. 그래서 주문은 정상 체결됐다.

### 영향

| 항목 | 결과 |
|---|---|
| 7월 적립 | **누락.** KST 8월이 된 뒤에는 7월 배정을 조회하지 않는다 |
| 8월 적립 | 조기 집행 완료 |
| 8월 남은 기간 | 마커가 `2026-08`이라 전부 스킵. 추가 매수 없음 |
| 다음 집행 | KST 9월 |
| 순손실 | 연 12회 중 1회 누락 |

체결 자체는 정상이고 중복 매수도 없었다. 손실은 7월 1회 누락뿐이다.

### 부수 확인 — 양호한 신호 둘

`ORDER_NO`에 `0031541054`가 들어왔다. KIS 응답의 `ODNO`가 정상 수신되어 `Guid` 폴백을 타지 않았다는 뜻이다. 향후 체결 대사를 배선할 때 이 값이 매칭 키로 쓰이므로, 폴백이 발동하지 않는 것이 전제 조건이었다.

`VOO`은 8월 템플릿의 정규 종목으로 확인됐다. 직전 작업에서 DB 레거시 키 `DCA_QTYS`가 `{"GLD":1,"VTI":1,"VOO":1}`인 것을 보고 미확인 티커로 취급했으나, 실제로 운영자가 사용하는 종목이었다.

### 크론을 당기는 것은 불가능하다

지연을 흡수하려면 크론을 앞으로 당겨 자정 전에 집행이 끝나게 해야 한다. 그러나 UTC 기준 제약을 늘어놓으면 창이 나오지 않는다.

| 이벤트 | UTC |
|---|---|
| 미장 개장 (EDT, 여름) | 13:30 |
| 미장 개장 (EST, 겨울) | 14:30 |
| KST 자정 | 15:00 |
| 미장 마감 (EDT) | 20:00 |
| 미장 마감 (EST) | 21:00 |

"KST 같은 날 + 여름·겨울 모두 장중"인 창은 `UTC 14:30 ~ 15:00` = **30분뿐**이다. 겨울 개장이 KST 자정의 30분 전이기 때문이다. 지연 1시간 41분은 이 창을 무조건 넘긴다. 더 당기면 겨울에 개장 전 주문이 되어 거부된다.

반면 "KST 다음 날 + 양 계절 장중"인 창은 `UTC 15:00 ~ 20:00` = **5시간**이다. 지연을 흡수할 여유가 있고, 창 앞쪽에 붙일수록 양쪽 마진이 커진다.

### 수정 — 크론을 자정 직후로

```yaml
    - cron: '10 15 1-31 * *'   # 매월 1~31일(=매일) KST 00:10 (UTC 15:10). 월 1회 실행은 엔진 가드가 보장.
```

| 크론 | KST | 월 경계 마진 | 미장 마감 마진(EDT) |
|---|---|---|---|
| `40 14` (이전) | 23:40 | **20분** | 5시간 20분 |
| `10 15` (변경) | **00:10** | **23시간 50분** | **4시간 50분** |

GitHub Actions 지연은 늦게만 밀리므로 자정 10분 뒤에 두어도 안전하다. 실측 지연 1시간 41분을 더하면 집행이 KST 01:51, 미국 동부로는 정규장 한복판이다.

`daily-run.yml` 상단 주석에 "이 시각을 당기지 말 것"과 30분 창 계산, 실측 지연치를 함께 남겼다. 다음 사람이 같은 계산을 다시 하지 않도록 하는 것이 목적이다.

### 월 판정 기준을 KST로 통일한다

크론 위치와 별개로, 월 판정 자체를 미국 동부 기준으로 바꾸는 안을 검토했다. 거래가 미국 시장에서 일어나므로 의미상 정확해 보인다. **채택하지 않았다.** 근거는 넷이다.

**첫째, 시스템에 두 번째 시간 기준이 생긴다.** 현재 시간 기준을 쓰는 곳은 전부 KST다 — 멱등 마커, 템플릿 선택, `DcaController`의 `currentMonth`, `TradeHistoryDto.TradeDate`, `HistoryController`. ET를 쓰는 곳은 0곳이다. ET를 도입하면 화면은 KST인데 판정은 ET가 되어, "8월 1일 거래인데 왜 7월 템플릿?"이라는 새 혼란이 생긴다. 지금 문제는 "월이 밀렸다" 하나인데, 그것을 "기준이 두 개다"라는 더 나쁜 문제로 바꾸는 셈이다.

**둘째, 사람이 보는 모든 표면이 KST다.** 메일, 로그, `TB_SYSTEM_LOG`, 거래내역, 대시보드가 전부 KST로 표시된다. 판정도 KST여야 화면과 판단이 일치한다.

**셋째, 템플릿의 의미가 하루 차이에 비어 있다.** 월별 배정을 다르게 두는 이유는 자금 사정이나 조합 순환이고, 어느 이유도 하루 차이에 영향받지 않는다. ET가 "정확하다"는 주장이 실제로 지키는 것이 없다.

**넷째, 새 실패 모드를 만든다.** `TimeZoneInfo.FindSystemTimeZoneById`는 플랫폼별 ID가 다르고 ICU가 없으면 예외를 던진다. 실계좌를 만지는 사이클에 시간대 변환 실패 경로를 추가하는 대가가 하루 라벨보다 크다.

ET가 맞다는 가장 강한 반론은 "월 1회 적립의 실질은 시장 노출 1회이고 시장은 ET로 도니, KST로 세면 ET 기준으로 두 번 사거나 안 살 수 있다"였다. 검산해보면 성립하지 않는다.

| 집행 (KST) | 미국 동부 날짜 | 적용 템플릿 | ET 기준 월 |
|---|---|---|---|
| 7/1 00:10 | 6/30 | 7월 | ET 6월 |
| 8/1 00:10 | 7/31 | 8월 | ET 7월 |
| 9/1 00:10 | 8/31 | 9월 | ET 8월 |

ET 기준으로도 정확히 월 1회다. 라벨만 한 달 밀린다. 국내 해외주식 양도소득세는 보유기간과 무관하므로 취득일 하루 차이도 무영향이다.

결론은 **KST 단일 기준 유지 + 크론 위치 변경**이며, 코드 변경은 0줄이다.

### 남는 한계

`10 15`는 조기폐장일(13:00 ET 마감, 연 2~3회)에 지연이 겹치면 장 마감 후가 될 수 있다. 이 경우 체결 0건이므로 마커가 남지 않아 다음 날 자동 재시도된다. 치명적이지 않아 이 한계를 안고 간다.

더 이르게 당기면 KST 자정 이전이 되어 월 경계 위험이 돌아온다. 두 위험이 균형을 이루는 지점이 자정 직후다.

### 부수 발견 — 문서 날짜 오류

이 사건을 분석하면서 직전 작업에서 만든 문서 두 건의 날짜가 실제 작성일과 어긋난 것을 발견했다. 작성일을 `2026-07-31`로 적었으나 실제로는 `2026-08-03`이었다. `create-md` 규칙이 "`date`는 문서를 생성하는 실제 오늘 날짜를 넣고 임의 날짜를 지어내지 않는다"고 명시하는데 이를 위반했다.

파일명과 프론트매터를 정정하고, 조사·삭제 작업일을 언급한 본문도 함께 고쳤다. 실거래 전환 시점은 정확한 설정일이 확인되지 않아 확정 사실인 **첫 실집행일(2026-08-01)** 로 표기했다.

## 정리 / 결론

반영 완료.

| 항목 | 내용 |
|---|---|
| 크론 | `40 14 1-31 * *` → `10 15 1-31 * *` (KST 23:40 → 00:10) |
| 주석 | 30분 창 계산 · 실측 지연 1시간 41분 · "당기지 말 것" 명시 |
| 월 판정 기준 | KST 단일 유지 (코드 변경 없음) |
| 문서 날짜 | 두 건 파일명·프론트매터·본문 정정 |

다음 단계.

1. **9월 첫 집행 확인.** 마커가 `2026-08`이므로 다음 집행은 KST 9월이다. `10 15` 적용 후 집행 시각이 KST 9/1 01~02시대에 들어오는지, 9월 템플릿이 선택되는지 확인한다.
2. **9월 배정 템플릿 확인.** 배정이 없으면 스킵되어 9월 적립이 빠진다.
3. **7월분 보정 여부 결정.** `POST /api/order/manual`로 7월 템플릿 수량을 수동 매수할 수 있다. 판단이 아니라 누락 보정이므로 원칙에 걸리지 않는다. 안 해도 무해하다.
4. **체결 대사 배선.** `ORDER_NO`가 정상 수신되는 것이 확인됐으므로 `PENDING` + `inquire-ccnl` 배선의 전제 조건이 충족됐다. `Guid` 폴백 제거가 선행 작업이다.
5. **토스 이체 실측 갱신.** KIS 타발 수수료·소요 시간·가능 시간대를 확인해 환전 경로 분석 문서를 확정한다.

교훈은 하나다. **스케줄러의 발화 시각이 아니라 집행 시각이 판정 기준이 된다.** 외부 스케줄러에 지연이 있는 한, 날짜·월 경계에서 판단하는 로직은 발화 시각을 기준으로 마진을 잡으면 안 된다. 지연의 실측 상한을 먼저 재고 그만큼 경계에서 떨어뜨려야 한다.
