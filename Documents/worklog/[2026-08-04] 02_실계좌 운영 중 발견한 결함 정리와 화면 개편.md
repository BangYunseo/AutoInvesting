# 실계좌 운영 중 발견한 결함 정리와 화면 개편

## 개요
> 실계좌(LIVE) 운영 첫 주에 화면을 쓰면서 드러난 결함을 순서대로 잡고, 적립 실행·예약 흐름과 대시보드·설정 화면을 개편한 기록이다. 인증 경계 정리는 같은 날의 [2026-08-04] 01 보고서에 따로 있다.

## 배경 / 목적

같은 달에 한 번 더 적립하고 싶다는 요구에서 시작해, 확인하는 과정에서 결함이 연쇄적으로 드러났다. 대부분 "값이 조용히 0이거나 비어 있어도 화면이 그럴듯하게 보이던" 종류였고, 실계좌라 값이 실제로 채워지자 한꺼번에 노출됐다.

발견 순서가 곧 작업 순서다.

1. 당월 멱등 가드가 화면에서 누른 추가 적립까지 막았다
2. 즉시 실행은 한국 낮에 누르면 미국장이 닫혀 거부된다
3. 월별 실행 표시가 주문 건수를 집행 횟수로 오독하게 했다
4. 예수금이 늘 0이었다 — 잘못된 엔드포인트를 보고 있었다
5. 총 자산이 주식 평가금액과 같은 값이었다 — 예수금이 0이라 가려져 있었다
6. 토큰 발급 실패가 스스로를 재생산해 403 폭주가 됐다

## 본문

### 적립 사이클 강제 실행

`DailyExecutionService.RunDcaCycleAsync`의 당월 1회 멱등 가드가 크론과 화면을 구분하지 않아, 이미 적립한 달에는 화면의 실행 버튼이 아무 일도 하지 않았다. 더 나쁜 점은 스킵이 `try` 진입 전에 `return`되어 **보고서 메일도 나가지 않고**, 컨트롤러는 항상 202를 반환해 화면에는 성공 메시지가 떴다는 것이다. 매수 0건인데 화면은 성공처럼 보였다.

가드의 목적은 크론이 매일 30번 호출하는 것을 막는 것이지 사람 손가락을 막는 것이 아니다. `force` 파라미터를 넣고 프론트 버튼은 항상 `force=true`를 보낸다. 크론(`daily-run.yml`)은 이 파라미터를 붙이지 않으므로 월 1회 동작이 그대로다.

### 개장 시간 예약 집행

즉시 실행은 한국 낮에 누르면 미국장이 닫혀 있어 주문이 거부된다. 그렇다고 크론에 강제 실행을 상시로 걸면 매일 중복 매수가 된다.

새 스케줄러는 만들지 않았다. 크론이 이미 개장 직후(매일 14:40 UTC = 서머타임 10:40 ET, 겨울 09:40 ET)에 돌고 있으므로, 그 실행이 당월 가드를 **한 번만** 넘도록 예약 마커를 둔다.

마커 값을 `"1"`이 아니라 **월**로 잡은 것이 핵심이다. 예약이 소진되지 않은 채 달을 넘기면 다음 달 정기 적립에 얹혀 2회 매수가 된다. 월이 바뀌면 저절로 무효가 되게 했다.

```csharp
// ── 월 1회 멱등 가드: 이번 달(KST) 이미 적립했으면 스킵 ──
// 예약(ForceRunMonthKey)이 이번 달로 걸려 있으면 크론 호출도 가드를 한 번 넘는다.
string thisMonth = CurrentKstMonth();
string lastRunMonth = AppConfigManager.Get(LastRunMonthKey, "");
bool reserved = AppConfigManager.Get(ForceRunMonthKey, "") == thisMonth;

if (lastRunMonth == thisMonth && !force && !reserved)
{
    statusNote = $"이번 달({thisMonth}) 적립이 이미 완료되어 매수를 건너뜁니다.";
    Logger.Info($"[DcaCycle] 이번 달({thisMonth}) 적립 완료 상태 — 매수 스킵");
    return statusNote;
}
if (lastRunMonth == thisMonth)
    Logger.Warn($"[DcaCycle] {(reserved ? "예약된" : "강제")} 실행 — 이번 달({thisMonth}) 적립 완료 상태에서 추가 매수를 진행합니다.");
```

예약은 주문 접수가 있을 때만 소진한다. 접수 0건(휴장·예수금 부족)이면 예약을 남겨 다음 크론이 다시 시도한다 — 월 마커와 같은 재시도 정책이다.

```csharp
if (result.Accepted.Count > 0)
{
    // 예약분은 접수가 있을 때만 소진한다. 접수 0건(휴장·예수금 부족)이면 예약을 남겨
    // 다음 크론이 다시 시도한다 — 월 마커와 같은 재시도 정책이다.
    if (reserved && !AppConfigManager.Set(ForceRunMonthKey, ""))
    {
        statusNote = "⚠️ 추가 적립 예약을 해제하지 못했습니다. 다음 크론 실행이 또 매수할 수 있으니 "
            + $"TB_APP_CONFIG의 {ForceRunMonthKey}를 비우세요.";
        Logger.Error($"[DcaCycle] {ForceRunMonthKey} 해제 실패 — 중복 매수 위험");
    }

    // 마커 저장이 조용히 실패하면 다음 날 크론이 같은 달에 또 매수한다(실자금 중복 집행).
    // 저장 실패는 반드시 보고서에 실어 사람이 알아채게 한다.
    if (AppConfigManager.Set(LastRunMonthKey, thisMonth))
    {
        Logger.Info($"[DcaCycle] 이번 달({thisMonth}) 적립 완료 표시 저장");
    }
    else
    {
        // 예약 해제 실패 안내가 이미 있을 수 있으므로 덮어쓰지 않고 잇는다.
        statusNote += $"{(statusNote.Length > 0 ? " " : "")}⚠️ 이번 달({thisMonth}) 적립 완료 표시를 저장하지 못했습니다. "
            + "이 상태로 두면 다음 크론 실행이 같은 달에 다시 매수합니다 — "
            + $"TB_APP_CONFIG의 {LastRunMonthKey}를 '{thisMonth}'로 직접 넣거나 크론을 멈추세요.";
        Logger.Error($"[DcaCycle] {LastRunMonthKey} 저장 실패 — 중복 매수 위험");
    }
}
```

### 확인창을 상태에 맞게

실행 버튼의 확인 문구가 이번 달 실행 여부와 무관하게 늘 같은 중복 경고를 띄웠다. 늘 뜨는 경고는 정작 중요한 순간에 눈에 띄지 않는다.

`GET /api/order/dca-schedule`이 이번 달 실행 여부·예약 여부·**적용될 템플릿**을 함께 준다. 템플릿 선택은 엔진이 쓰는 `DcaSettings.SelectTemplate`을 그대로 호출한다 — 여기서 따로 판단하면 화면이 안내한 템플릿과 실제로 사는 템플릿이 어긋날 수 있다.

```csharp
[HttpGet("dca-schedule")]
public IActionResult GetDcaSchedule()
{
    string month = DailyExecutionService.CurrentKstMonth();

    // 실행하면 무엇을 사는지 화면이 확인 문구에 그대로 띄울 수 있어야 한다.
    // 엔진이 쓰는 것과 같은 선택 로직(SelectTemplate)을 그대로 쓴다 — 여기서 따로 판단하면
    // 화면이 안내한 템플릿과 실제로 사는 템플릿이 어긋날 수 있다.
    var templates = DcaSettings.LoadTemplates();
    var monthMap = DcaSettings.LoadMonthMap();
    var chosen = DcaSettings.SelectTemplate(templates, monthMap, int.Parse(month.Substring(5, 2)));

    return Ok(new
    {
        month,
        alreadyRan = AppConfigManager.Get(DailyExecutionService.LastRunMonthKey, "") == month,
        reserved = AppConfigManager.Get(DailyExecutionService.ForceRunMonthKey, "") == month,
        activeTemplateName = chosen?.Name ?? "",
        activeQuantities = chosen?.Quantities
            .Where(kv => kv.Value > 0)
            .ToDictionary(kv => kv.Key, kv => kv.Value)
            ?? new Dictionary<string, int>()
    });
}
```

브라우저 기본 `confirm()`도 걷어냈다. 앱 테마와 따로 놀고, 브라우저가 반복 표시를 억제하면 경고 없이 실행될 수 있어 실자금 버튼의 확인창으로는 부적절하다. 기존 매도 확인 모달의 `.modal-overlay` 스타일을 그대로 쓰는 `ConfirmDialog`를 추가했다.

실수하면 돈이 나가는 사실만 붉은 굵은 글씨로 띄운다. 전부 강조하면 아무것도 강조되지 않는다.

```css
/* 확인 모달에서 "실수하면 돈이 나가는" 사실만 눈에 박히게. 남발하면 강조가 죽는다. */
.confirm-em {
  color: var(--loss-red);
  font-weight: 700;
}
```

예약 버튼은 문구로 상태를 말하지 않고 **눌린 모양**으로 보여주는 토글이 됐다. 켤 때든 끌 때든 현재 상태와 무엇을 사게 되는지를 같은 형식으로 보여주고 확인받는다.

### 집행 회차 세기

월별 실행 표시가 `●2`로 나와 "2번 매수"로 읽혔는데, 실제로는 1회 집행이 2종목을 산 것이었다. 거래이력 1행은 주문 1건이라 그 수를 그대로 센 것이 원인이다.

한 사이클의 주문들은 Rate limit 간격을 두고 연달아 접수되므로, 앞 주문과의 간격이 벌어지는 지점에서 회차를 끊는다. 적립 설정의 월별 로그와 주문·적립의 예약 확인창이 같은 숫자를 보여야 해서 공용 유틸로 뺐다.

```javascript
/** 같은 집행으로 볼 최대 주문 간격 (밀리초) */
export const RUN_GAP_MS = 10 * 60 * 1000;

/**
 * 거래이력에서 매수 주문만 골라 파싱된 시각(at)을 붙여 반환합니다.
 * @param {Array} trades /api/history/trades 응답의 trades 배열
 */
export function toBuyRows(trades) {
  const rows = [];
  for (const t of trades ?? []) {
    if ((t.orderType || '').toUpperCase() !== 'BUY') continue;
    const at = new Date(t.tradeDate);
    if (Number.isNaN(at.getTime())) continue;
    rows.push({ ...t, at });
  }
  return rows;
}

/**
 * 주문들을 집행 회차별 배열로 묶습니다 (최신 회차가 앞).
 * @param {Array} rows toBuyRows가 만든 행들
 */
export function groupRuns(rows) {
  if (!rows || rows.length === 0) return [];

  const asc = [...rows].sort((a, b) => a.at - b.at);
  const runs = [[asc[0]]];
  for (let i = 1; i < asc.length; i++) {
    if (asc[i].at - asc[i - 1].at > RUN_GAP_MS) runs.push([asc[i]]);
    else runs[runs.length - 1].push(asc[i]);
  }
  return runs.reverse();
}

/**
 * 특정 연-월의 집행 회차 수를 셉니다.
 * @param {Array} trades /api/history/trades 응답의 trades 배열
 * @param {string} yearMonth 'yyyy-MM'
 */
export function countRunsInMonth(trades, yearMonth) {
  const [y, m] = (yearMonth || '').split('-').map(Number);
  if (!y || !m) return 0;

  const rows = toBuyRows(trades).filter(
    r => r.at.getFullYear() === y && r.at.getMonth() + 1 === m,
  );
  return groupRuns(rows).length;
}
```

시간 간격 휴리스틱이라 같은 회차가 10분 넘게 걸리거나 서로 다른 회차가 10분 안에 겹치면 어긋난다. 정확히 세야 할 일이 생기면 `TB_TRADE_HISTORY`에 실행 ID 컬럼을 두는 쪽이 맞다. 화면 안내 문구에도 추정 방식임을 적었다.

### 예수금이 늘 0이던 이유

실계좌에 외화가 있는데도 대시보드 예수금이 0원이었고, 로그에 매 조회마다 `예수금 조회 실패. 기본값 0 반환.`이 남아 있었다.

외화 예수금 `frcr_dncl_amt_2`는 **체결기준현재잔고**(`inquire-present-balance`, `CTRP6504R`)의 `output2`에만 있는 필드다. 잔고조회(`inquire-balance`, `TTTS3012R`)의 `output2`는 평가 요약(매입금액·손익·수익률)이라 이 필드가 없다. 필드명은 맞는데 없는 곳을 뒤지고 있었다.

`output2`가 통화별 배열이라는 점도 중요하다. 예전 코드는 배열이면 무조건 첫 번째 요소를 집었는데, 원화 행이 섞여 오면 엉뚱한 값을 읽는다.

```csharp
// 외화 예수금(frcr_dncl_amt_2)은 '체결기준현재잔고'(CTRP6504R)의 output2에만 있다.
// 잔고조회(TTTS3012R)의 output2는 평가 요약(매입금액·손익·수익률)이라 이 필드가 없어
// 2026-08-04까지 매번 "예수금 조회 실패"로 떨어지며 $0을 반환하고 있었다.
//
// output2는 통화별 배열이므로 crcy_cd로 USD 행을 골라야 한다(원화 행이 섞여 온다).
// WCRC_FRCR_DVSN_CD=02(외화), NATN_CD=000(전체), TR_MKET_CD=00(전체), INQR_DVSN_CD=00(전체).
string trId = "CTRP6504R";
string path = $"/uapi/overseas-stock/v1/trading/inquire-present-balance"
    + $"?CANO={_accountNoPrefix}&ACNT_PRDT_CD={_accountNoSuffix}"
    + "&WCRC_FRCR_DVSN_CD=02&NATN_CD=000&TR_MKET_CD=00&INQR_DVSN_CD=00";

var response = await SendWithRetryAsync(() => CreateRequest(HttpMethod.Get, path, trId));
response.EnsureSuccessStatusCode();

var responseString = await response.Content.ReadAsStringAsync();
var json = JsonSerializer.Deserialize<JsonElement>(responseString);

if (json.TryGetProperty("output2", out var output2) && output2.ValueKind == JsonValueKind.Array)
{
    foreach (var row in output2.EnumerateArray())
    {
        string currency = row.TryGetProperty("crcy_cd", out var cc) ? (cc.GetString() ?? "") : "";
        if (!string.Equals(currency, "USD", StringComparison.OrdinalIgnoreCase)) continue;

        if (row.TryGetProperty("frcr_dncl_amt_2", out var cashProp)
            && decimal.TryParse(cashProp.GetString(), NumberStyles.Any, CultureInfo.InvariantCulture, out decimal cash))
        {
            Logger.Info($"[KisBroker] 예수금 조회: ${cash:N2}");
            return cash;
        }
    }

    Logger.Warn("[KisBroker] 예수금 조회: output2에 USD 행이 없음. 0 반환.");
    return 0m;
}

// 실패 사유를 남긴다 — 필드 부재와 API 거부(rt_cd≠0)는 원인이 달라 구분이 필요하다.
string msg = json.TryGetProperty("msg1", out var m1) ? (m1.GetString() ?? "").Trim() : "";
string rtCd = json.TryGetProperty("rt_cd", out var rc) ? (rc.GetString() ?? "") : "";
Logger.Warn($"[KisBroker] 예수금 조회 실패 (rt_cd={rtCd}, msg1={msg}). 기본값 0 반환.");
return 0m;
```

배포 후 로그에 `[KisBroker] 예수금 조회: $725.77`이 찍혀 정상 동작을 확인했다.

보유 종목 조회는 영향이 없었다. 같은 잔고조회를 쓰지만 `output1`을 읽고, 실전에서 `NASD`는 '미국전체'라 NYSE·AMEX까지 잡힌다. 로그에서 `GLDM`·`SCHD` 둘 다 `EXCD=AMS`인데 정상 조회되는 것으로 실측 확인됐다.

### 총 자산 계산

예수금이 잡히자 총 자산 카드와 주식 평가금액 카드가 같은 숫자를 보여준다는 게 드러났다. 총 자산이 주식 평가액만 담고 있었고, 예수금이 늘 0이던 동안은 우연히 맞아떨어져 보이지 않았다.

```javascript
// 총 자산 = 주식 평가액 + 예수금.
// 예전에는 예수금을 뺀 주식 평가액만 담아 '총 자산'과 '주식 평가금액' 두 카드가 같은 값을
// 보여줬다. 예수금 조회가 늘 0을 반환하던 동안은 우연히 맞아떨어져 드러나지 않았다.
const totalAssetsUsd = stockEvalUsd + cashBalance;
```

카드 보조 줄에 `주식 $X + 예수금 $Y`를 적어 어디서 온 값인지 보이게 했다.

### 토큰 발급 실패 폭주

배포로 구·신 인스턴스가 잠깐 겹치면서 같은 앱키로 토큰을 동시에 요청했고, KIS의 분당 1회 제한에 걸려 한쪽이 403을 받았다. 여기서 그치지 않고 초당 수 회씩 `/oauth2/tokenP`를 두드리는 상태로 굳었다.

원인은 실패 후 재시도를 막는 장치가 없다는 것이다. 발급이 실패하면 토큰이 빈 채로 남아 `IsExpiringSoon()`이 계속 true가 되고, 그러면 API 호출 하나하나가 새 발급을 부른다. 그 재시도가 다시 제한에 걸리므로 실패가 실패를 낳는다.

```csharp
/// <summary>
/// 토큰이 유효한지 확인하고 필요 시 재발급합니다.
/// </summary>
public async Task EnsureValidTokenAsync()
{
    if (!IsExpiringSoon()) return;

    // 동시 요청이 각자 토큰을 발급하면 KIS의 "분당 1회" 제한에 걸려 실패한다.
    // 락으로 직렬화하고, 락 획득 후 재확인해 한 번만 발급하고 나머지는 공유한다.
    await _refreshLock.WaitAsync();
    try
    {
        if (!IsExpiringSoon()) return;

        // 직전 발급이 실패했다면 보류 시간이 지날 때까지 아예 시도하지 않는다.
        // 실패를 그대로 재시도하면 호출 수만큼 발급 요청이 늘어 제한이 계속 갱신된다.
        if (DateTime.Now < _refreshBlockedUntil)
        {
            int waitSec = (int)Math.Ceiling((_refreshBlockedUntil - DateTime.Now).TotalSeconds);
            throw new InvalidOperationException(
                $"직전 토큰 발급이 실패해 {waitSec}초간 재시도를 보류 중입니다 (KIS 분당 1회 제한).");
        }

        await RefreshTokenAsync();
    }
    finally
    {
        _refreshLock.Release();
    }
}
```

발급 실패 로그에 응답 본문(`error_code`/`error_description`)을 남기도록 했다. 상태코드만으로는 분당 제한과 앱키 오류를 구분할 수 없어 원인 찾는 데 시간이 걸렸다. 본문에 시크릿은 없고 300자로 자른다.

### 화면 개편

**월별 템플릿 배정과 실행 로그.** 월별 배정을 그리드로만 보여줘 그 달에 실제로 매수가 돌았는지 확인할 방법이 없었다. 좌측에 12개월 세로 리스트, 우측에 선택한 달의 매수 기록을 회차별로 묶어 보여준다. 데이터는 기존 `/api/history/trades`를 연-월로 묶어 쓰므로 백엔드 변경이 없다. 해가 바뀌어도 지난해 기록이 사라지지 않도록 연도 이동을 붙였다.

**자산 비중 도넛.** 표 안의 막대는 행 폭에 눌려 짧고 전체 100% 중 어느 정도인지 한눈에 안 들어왔다. 비중 열을 없애고 대시보드 하단에 도넛 카드를 뒀다. 외부 차트 라이브러리는 쓰지 않는다 — 종목 몇 개짜리 도넛 하나에 chart.js 계열을 더할 이유가 없어 SVG 원 하나에 `stroke-dasharray`로 그린다. 3D로 그리지 않은 이유는 원근이 들어가면 앞쪽 조각이 실제 비중보다 커 보여, 비중을 읽으라고 만든 그림이 비중을 왜곡하기 때문이다. 색상 순서는 앱의 다크 표면 기준으로 명도대·채도·색각 분리·대비 검증을 통과한 조합을 쓰고, 링 양끝이 맞닿는 쌍까지 확인했다.

**네이티브 컨트롤 교체.** `select`는 닫힌 상태만 테마가 먹고 펼쳐지는 목록은 OS가 그린다. 선택지가 적은 곳은 팝업을 예쁘게 만들 게 아니라 없애는 쪽이 짧다. 라디오 `input`을 시각적으로만 감추고 라벨을 칩으로 그리면 팝업이 사라지면서도 같은 `name`의 라디오 그룹이라 화살표 이동·스크린리더 낭독이 그대로 남는다. 커스텀 드롭다운을 만들었을 때 직접 떠안아야 하는 키보드 탐색·외부 클릭·ARIA·모바일 터치가 전부 필요 없다.

**시스템 로그 달력.** 날짜 입력의 달력 팝업도 브라우저가 그려 테마가 안 먹고, 로그는 서비스가 실제로 돈 날에만 남으므로 365칸 중 대부분이 빈 날이다. 서버가 이미 갖고 있던 `SystemLogDAO.GetAvailableDates()`를 항상 내려주고, 카드 안에 달력을 직접 그려 **로그가 있는 날만** 활성화했다. 팝업이 아니라 인라인이라 바깥 클릭·포커스 트랩 처리도 필요 없다.

**모바일.** 티커 입력 줄이 한 줄에 6개 컨트롤을 밀어 넣으면서 `wrap`도 `minWidth`도 없어 좁은 화면에서 입력창이 찌그러졌다. 줄바꿈과 최소 폭을 넣고, 640px 이하에서 카드 안쪽 여백을 줄였다.

**월 예산 표기와 빈 템플릿.** 예산 입력이 `type="number"`라 천 단위 구분을 넣을 수 없었다. 숫자만 저장하고 화면에는 콤마를 넣어 보여주도록 `text` + `inputMode="numeric"`으로 바꿨다. 그리고 `handleSave`가 모든 템플릿을 검증하는 바람에 `+ 새 템플릿`을 눌러두기만 해도 다른 템플릿의 수정분까지 저장되지 않았다 — 만들다 만 껍데기가 나머지를 인질로 잡는 구조였다. 종목이 하나도 없는 템플릿은 저장에서 빼고, 무엇이 왜 빠졌는지 안내 문구에 남긴다.

## 정리 / 결론

오늘 확인한 것 중 **고치지 않고 남긴 것**이 셋 있다.

**지정가가 안 붙으면 그 달 적립이 조용히 누락된다.** 주문은 시장가가 아니라 지정가(`ORD_DVSN="00"`)이고, 지정가로 넣는 값이 조회 시점의 마지막 체결가다. 매수는 매도호가를 쳐야 붙는데 체결가에 걸면 스프레드만큼 뒤에 줄을 서고, 시세 조회와 주문 사이에 Rate limit 지연이 수 초 끼어 그 사이 가격이 오르면 밀린다. 그런데 마커는 **접수** 기준으로 찍히므로, 미체결로 장이 끝나도 그 달은 완료로 남는다. 매수 지정가에 소폭 버퍼를 넣거나 호가를 쓰는 쪽을 검토해야 한다. 마커 기준을 체결로 바꾸려면 주문번호로 체결을 대사하는 경로가 먼저 필요하다.

**테스트를 도는 CI가 없다.** 인증 회귀 방지 테스트를 만들었지만 자동으로 실행되지 않는다. 라이브 검증으로 대신하기로 해 이번에는 넣지 않았다.

**`dotnet test`가 실제 DB에 붙는다.** 뮤테이션 검증 중 로그인 배선 테스트가 503이 아니라 401을 반환했는데, 이는 `TryReadDb`가 성공했다는 뜻이다. `DATABASE_URL`이 가리키는 DB에 관리자 행이 실재한다. 읽기 전용이라 위험은 없으나 분리하는 편이 낫다.

검증 상태는 백엔드 빌드 오류 0·경고 0, 테스트 51건 전부 통과, 프론트 빌드 통과, 린트 신규 문제 0이다. 남은 린트 7건은 손대지 않은 화면의 기존 `set-state-in-effect`다.

운영자가 알아야 할 것 하나. `API_ACCESS_KEY`는 크론용에서 **부트스트랩 필수**로 성격이 바뀌었다(같은 날 01 보고서 참고). Render 환경변수에서 지우면 새 환경에서 관리자를 만들 수 없다.
