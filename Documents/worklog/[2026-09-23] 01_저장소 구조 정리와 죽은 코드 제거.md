# 저장소 구조 정리와 죽은 코드 제거

## 개요
> 저장소 전체를 과잉설계 관점에서 전수 스캔해, 호출자가 0인 코드·읽는 코드가 없는 설정·이관이 끝난 레거시 폴백·쓰기 경로가 사라진 시크릿 암호화 레이어를 제거했다. 순 267줄 삭제 / 70줄 추가(추가분은 대부분 사라진 안전 근거를 코드 옆으로 옮긴 주석)이며, `dev` 브랜치에 5커밋으로 나눠 push했다. `main` 머지는 사용자 실기동 확인 후로 미뤘다.

## 배경 / 목적
주니어에게 프로젝트 구조를 설명할 자료를 준비하던 중, 설명 대상 자체를 먼저 줄이기로 했다. 설명해야 할 코드가 적을수록 설명이 정확해지고, "이건 왜 있어요?"에 답할 수 없는 코드가 남아 있으면 온보딩 문서가 거짓말을 하게 된다.

이 저장소는 2026-08-01부터 실계좌로 집행 중이다. 따라서 삭제 판단 기준은 "안 쓰는 것 같다"가 아니라 **"호출자를 전수 확인했고 0건"** 이었고, 운영 데이터에 의존하는 항목은 사용자 확인을 거친 뒤에만 지웠다.

## 본문

### 검토 방법
파일 단위로 훑지 않고, 의심 심볼마다 `grep`으로 호출자를 전수 확인했다. 대상은 `public` 멤버, `appsettings.json`의 각 섹션, 프론트 컴포넌트, API 라우트 전부다.

검토 결과 **깨끗했던 것**도 기록해 둔다. 다음 번에 같은 곳을 다시 파지 않기 위함이다.

- 프론트 페이지 5개·컴포넌트 3개·유틸 1개 전부 배선돼 있다.
- API 라우트 전부 소비자가 있다(프론트 또는 크론).
- `.gitignore`가 `.vs/`·`.opencode/`·`node_modules`·분석 캐시를 이미 차단하고 있고, 빌드 산출물이 추적된 것은 0건이다.

### 제거 1: 호출자 없는 죽은 코드
`Controllers/TestController.cs`를 파일째 삭제했다. 체결내역 확인용으로 며칠 전 추가한 임시 엔드포인트(`GET /api/test/order-fills`)이며, 프론트와 크론 어디에서도 호출하지 않는다. 같은 파일이 과거 `/api/test/buy`(실주문 우회 경로)를 품었다가 삭제된 전력이 있어, "임시"라는 이름의 표면을 남겨두지 않기로 했다.

`Core/SessionManager.cs`의 `Reset()`을 제거했다. 유일한 호출자였던 `ConfigController`가 2026-08-06에 제거되면서 호출자가 0이 됐다.

`Utils/NotificationService.cs`의 `SendEmailOrThrowAsync`는 `public`에서 `private`으로 좁혔다. "테스트·헬스체크 엔드포인트에서 실패 원인을 응답으로 확인하기 위해" 열어둔 메서드인데, 그 엔드포인트가 이미 사라져 유일한 호출자가 같은 클래스의 `SendEmailAsync` 하나였다.

### 제거 2: 읽는 코드 없는 설정 섹션과 DCA 레거시 폴백
`appsettings.json`에서 `Smtp`·`Dca` 두 섹션을 제거했다.

`Smtp`는 Render가 SMTP 포트(25/465/587)를 막아 Resend HTTP API로 옮긴 뒤 남은 폴백 2키(`SenderName`·`AdminEmail`)였다. 수신자는 환경변수 `ADMIN_EMAIL`이, 발신자명은 `Resend` 섹션이 이미 담당하고 있어 두 값 모두 빈 문자열이었다. `NotificationService.Initialize`의 `smtpSection` 읽기도 함께 걷어냈다.

`Dca`는 `MonthlyBudgetKrw`(값이 `DcaSettings.DefaultBudgetKrw`와 동일해 중복)와 의도적으로 비워둔 `Quantities`만 남아 있었고, 이 둘을 읽던 `DcaSettings.LoadLegacyQuantities`·`LoadLegacyBudget`과 레거시 DB 키 상수 `QuantitiesKey`(`DCA_QTYS`)·`BudgetKey`(`DCA_BUDGET_KRW`)를 함께 제거했다. 매수 템플릿 이관은 2026-06-29에 끝났다.

제거 후 `LoadTemplates()`의 폴백은 다음과 같다. DB 조회·파싱이 실패하면 **종목이 빈 기본 템플릿**이 되고, 그 사이클은 매수를 건너뛴 뒤 마커를 남기지 않아 다음 날 재시도한다.

```csharp
public static List<DcaTemplate> LoadTemplates()
{
    string json = AppConfigManager.Get(TemplatesKey, "");
    if (!string.IsNullOrWhiteSpace(json))
    {
        try
        {
            var parsed = JsonSerializer.Deserialize<List<DcaTemplate>>(json);
            if (parsed != null)
            {
                var clean = new List<DcaTemplate>(); 
                foreach (var t in parsed)
                {
                    if (t != null && !string.IsNullOrWhiteSpace(t.Id)) clean.Add(t);
                }
                if (clean.Count > 0) return clean;
            }
        }
        catch (Exception ex)
        {
            Logger.Error($"[DCA] DCA_TEMPLATES 파싱 실패 : 종목 없는 기본 템플릿으로 폴백(매수 스킵): {ex.Message}");
        }
    }

    // 기본 템플릿 — 종목을 일부러 비워 둔다. 여기에 수량이 채워지면 DB 조회 실패만으로
    // 의도하지 않은 바스켓이 실계좌에 매수된다. 종목은 적립설정 화면에서만 들어온다.
    return new List<DcaTemplate>
    {
        new DcaTemplate
        {
            Id = "default",
            Name = "기본",
            BudgetKrw = DefaultBudgetKrw,
            Quantities = new Dictionary<string, int>()
        }
    };
}
```

이 변경으로 동작이 한 칸 **더 보수적**이 된다. 기존에는 `DCA_TEMPLATES`가 없거나 깨졌을 때 `DCA_QTYS`에 남아 있던 낡은 바스켓을 되살려 실계좌에 매수할 수 있었다. 이제는 그런 경로가 없고 스킵한다. `appsettings.json` 주석으로만 존재하던 "Quantities를 채우지 말 것"이라는 안전 근거는 위 코드 주석으로 옮겨, 규칙이 지켜야 할 코드 바로 옆에 있게 했다.

### 제거 3: 시크릿 DB 암호화 레이어
`Utils/CryptoUtil.cs`의 AES-256-GCM 암복호화 3종(`EncryptSecret`·`DecryptSecret`·`IsEncrypted`, `enc:v1:` 접두사 형식)과 `Data/AppConfigManager.cs`의 `SensitiveKeys` 집합·암복호화 분기를 제거했다. 이 항목 하나가 삭제분의 절반 이상이다.

판단 근거는 호출자 전수 확인이다. `AppConfigManager.Set`의 호출부는 8곳이며 전부 다음 키만 쓴다.

- `DCA_LAST_RUN_MONTH`, `DCA_LAST_RUN_DATE`, `DCA_FORCE_RUN_MONTH`, `DCA_PENDING_SNAPSHOT` (적립 마커)
- `DCA_TEMPLATES`, `DCA_MONTH_MAP`, `DCA_RUN_DAY` (적립 설정)
- `ADMIN_USERNAME`, `ADMIN_PASSWORD_HASH` (관리자 계정)

즉 `SensitiveKeys`에 등록된 5개 키(`KIS_APP_KEY`·`KIS_APP_SECRET`·`KIS_ACCOUNT_NO`·`RESEND_API_KEY`·`API_ACCESS_KEY`)는 **어디에서도 DB에 쓰이지 않는다.** 이 키들을 DB에 넣던 유일한 경로인 설정 화면과 `ConfigController`가 2026-08-06에 제거됐고, `security.md`도 시크릿은 환경변수 전용이라고 못 박은 상태다.

남은 위험은 하나였다. 과거에 쓰인 `enc:v1:` 행이 DB에 남아 있으면 복호화기를 지웠을 때 암호문이 그대로 값으로 읽힌다. 그래서 삭제 전에 확인용 조회를 먼저 요청했다. 값은 조회하지 않고 키 이름과 건수만 본다.

```sql
SELECT CONFIG_KEY
  FROM TB_APP_CONFIG
 WHERE CONFIG_VALUE LIKE 'enc:v1:%';
```

결과 0건을 확인한 뒤 삭제했다. 제거 후 `TryReadDb`와 `Set`은 다음과 같이 단순해졌다.

```csharp
public static bool TryReadDb(string key, out string? value)
{
    value = null;
    try
    {
        using (var conn = DBManager.Instance.GetConnection())
        using (var cmd = new NpgsqlCommand(
            "SELECT CONFIG_VALUE FROM TB_APP_CONFIG WHERE CONFIG_KEY=@k", conn))
        {
            cmd.Parameters.AddWithValue("@k", key);
            value = cmd.ExecuteScalar()?.ToString();
            return true;
        }
    }
    catch (Exception ex)
    {
        Logger.Warn($"[AppConfig] DB 조회 실패 -> 기본 설정 폴백 [{key}]: {ex.Message}");
        return false;
    }
}

public static bool Set(string key, string value)
{
    try
    {
        using (var conn = DBManager.Instance.GetConnection())
        using (var cmd = new NpgsqlCommand(
            "UPDATE TB_APP_CONFIG SET CONFIG_VALUE=@v WHERE CONFIG_KEY=@k", conn))
        {
            cmd.Parameters.AddWithValue("@v", value);
            cmd.Parameters.AddWithValue("@k", key);
            int affected = cmd.ExecuteNonQuery();

            if (affected == 0)
            {
                // 키가 없을 경우 INSERT
                using var insertCmd = new NpgsqlCommand(
                    "INSERT INTO TB_APP_CONFIG (CONFIG_KEY, CONFIG_VALUE) VALUES (@k, @v)", conn);
                insertCmd.Parameters.AddWithValue("@k", key);
                insertCmd.Parameters.AddWithValue("@v", value);
                insertCmd.ExecuteNonQuery();
            }
        }

        // 값은 로그에 남기지 않는다. TB_SYSTEM_LOG는 영구 저장소이므로 여기에 값을 찍으면
        // 계정(ADMIN_USERNAME)·자격증명 해시가 평문으로 영구 적재된다(조직 보안정책 위반).
        // 저장 여부 진단에는 키 이름과 값 길이로 충분하다.
        Logger.Info($"[AppConfig] 저장: {key} (길이 {value?.Length ?? 0})");
        return true;
    }
    catch (Exception ex)
    {
        Logger.Error($"[AppConfig] 저장 실패 [{key}]: {ex.Message}");
        return false;
    }
}
```

`MASTER_KEY`는 세션 토큰 서명 키 파생에 계속 쓰이므로 `MasterKey`·`IsConfigured`와 `Program.cs`의 기동 가드는 유지했다. 다만 그 가드의 주석이 "복호화 실패 시 값이 비어 `SessionManager`가 조용히 `SimBrokerClient`로 폴백한다"를 근거로 들고 있었는데, 복호화 경로가 사라져 그 시나리오가 더는 성립하지 않는다. 실제 근거(토큰 서명 키가 없으면 로그인이 전부 500)로 고쳐 적었다.

### 강화: PublicEndpoint 어트리뷰트 대상 축소
`Utils/PublicEndpointAttribute.cs`의 `AttributeTargets`에서 `Class`를 뺐다. 삭제가 아니라 조임이다.

`architecture.md`가 "`[PublicEndpoint]`를 컨트롤러 클래스에 붙이지 말 것"을 금지 규칙으로 두고 `Tests/PublicEndpointExposureTests.cs`가 면제 목록을 리플렉션으로 고정하고 있었지만, 정작 어트리뷰트 자체는 클래스 부착을 허용하고 있었다. 규칙이 금지하는 것을 타입이 허용하면 언젠가 다시 붙는다. 과거 `AuthController`가 클래스 단위로 열려 있어 `setup`까지 미인증 공개였고, 관리자 자리가 비어 보이는 순간 누구나 관리자를 선점해 실주문을 낼 수 있었다(2026-08-04 수정).

```csharp
using System;

namespace AutoInvest.Utils
{
    /// <summary>
    /// 전역 인증 필터(<see cref="ApiKeyAuthAttribute"/>)를 면제하는 마커 어트리뷰트입니다.
    /// 로그인·상태조회처럼 인증 없이 접근해야 하는 엔드포인트에 부착합니다(닭-달걀 방지).
    ///
    /// 액션 메서드에만 붙일 수 있습니다. 컨트롤러 클래스에 붙이면 그 안의 모든 액션이 한꺼번에
    /// 열리며, 과거 <c>AuthController</c>가 그 상태여서 <c>setup</c>까지 미인증 공개였습니다
    /// (2026-08-04 수정). 같은 실수가 컴파일 단계에서 막히도록 대상을 메서드로 좁혀 둡니다.
    /// </summary>
    [AttributeUsage(AttributeTargets.Method, AllowMultiple = false)]
    public sealed class PublicEndpointAttribute : Attribute
    {
    }
}
```

테스트의 클래스 단위 검사는 그대로 뒀다. `AttributeTargets`를 누가 다시 넓히는 변경에 대한 2차 방어선이다.

### 건드리지 않은 것
다음은 검토 대상에 올랐으나 남겨둔 항목이다. 다음 세션이 같은 고민을 반복하지 않도록 이유와 함께 적는다.

`Program.cs`의 `MASTER_KEY` 기동 가드는 이제 실제 필요보다 한 칸 엄격하다. `AUTH_TOKEN_SECRET`만 있어도 토큰 서명은 가능하기 때문이다(`CryptoUtil.GetTokenKey`). 배포 환경에 두 키가 모두 있어 지금은 무해하며, 기동 가드를 느슨하게 푸는 변경은 성격이 달라 별도 판단 대상으로 남겼다. 해당 내용은 코드 주석에도 적어 뒀다.

`TB_MARKET_SNAPSHOT` 테이블은 Phase 6 이후 기록되지 않는 레거시지만 과거 분석·회귀 검증용이라 스키마에 그대로 뒀다(`recommended_rules.md`의 누적 데이터 보호 규칙).

`Controllers/PortfolioController.cs`(XML 주석 문구 변경)와 `Documents/worklog/_TEMPLATE.md`(한 줄 삭제), 미추적 `Properties/`는 이번 작업 이전부터 작업트리에 있던 변경이라 커밋에서 제외했다. 특히 `Properties/launchSettings.json`은 `ASPNETCORE_ENVIRONMENT=Development`를 걸어 로컬에서 Swagger를 켜는 프로필인데, 커밋할지 `.gitignore`에 넣을지 아직 정하지 않았다.

### 로컬 검증 중 발견: 실행 포트 불일치
로컬 기동 직후 프론트가 `/api/portfolio/summary`에 대해 `ECONNREFUSED`만 반복했다. 백엔드가 죽은 것으로 보이지만 실제로는 정상 기동한 상태였고, 듣는 포트가 달랐다.

```text
AutoInvest (PID 19976)  ->  62527 / 62528   실제 바인딩
Vite (PID 12264)        ->  5173, /api 프록시 대상 = 5000
```

원인은 Visual Studio가 만든 `Properties/launchSettings.json`의 `applicationUrl`이 62527/62528을 가리키고 있었던 것이다. `Frontend/vite.config.js`의 프록시 대상은 `http://localhost:5000` 고정이라 서로 만나지 못했다. `CLAUDE.md`에는 "`launchSettings.json` 없음 — Kestrel 기본값"이라 적혀 있어 전제 자체가 깨진 상태였다.

`applicationUrl`을 `http://localhost:5000` 하나로 좁혀 프록시 대상과 맞추고 파일을 추적 대상에 넣었다. 지우지 않은 이유는 Visual Studio가 언제든 다시 만들기 때문이다 — 커밋해 두면 다음에도 같은 포트로 고정된다. `ASPNETCORE_ENVIRONMENT=Development`는 그대로 뒀다(로컬에서만 Swagger가 열리고, 아래 관리자 시딩의 게이트로도 쓰인다). `CLAUDE.md`의 설명도 현재 상태와 어긋남 증상까지 함께 고쳐 적었다.

진단 교훈을 하나 남긴다. "안 된다"의 첫 질문은 "프로세스가 죽었나"가 아니라 **"누가 어느 포트를 듣고 있나"** 다. `Get-NetTCPConnection -State Listen` 한 줄이 "백엔드가 안 뜬다"와 "백엔드가 딴 데 떠 있다"를 갈랐고, 이 둘은 고치는 법이 완전히 다르다.

### 로컬 관리자 계정 자동 생성
포트를 맞춘 뒤에는 로그인 화면이 최초 설정을 요구했다. 로컬 DB에 관리자가 없기 때문이며, `POST /api/auth/setup`은 전역 인증 필터를 타므로 `x-api-key`를 붙여 직접 호출해야 한다(2026-08-04 조치). 운영에서는 옳지만 로컬 DB를 새로 만들 때마다 반복하기엔 번거로워, 그 한 번을 대신하는 경로를 `Program.SeedLocalAdmin`으로 추가했다.

검토 과정에서 기각한 대안이 둘이다.

첫째, **`IsDevelopment()`면 인증 필터를 통과시키는 방식**은 쓰지 않는다. 게이트가 `ASPNETCORE_ENVIRONMENT` 하나뿐이라, 그 값이 배포 환경에 잘못 들어가는 순간 `POST /api/order/manual`을 포함한 API 전체가 무인증으로 열린다. 실계좌 주문 경로를 환경변수 오타 하나에 걸어둘 수 없다.

둘째, **소스에 계정을 하드코딩하는 방식**도 쓰지 않는다. 이 저장소는 공개이므로 자격증명을 깃허브에 게시하는 것과 같고, `gitleaks` 워크플로에도 걸린다.

채택한 방식은 값을 `appsettings.local.json`에서만 읽는 것이다. 이 파일은 `.gitignore`와 `.dockerignore` 양쪽에서 제외되므로 저장소에도, 배포 이미지에도 들어가지 않는다.

```csharp
/// <summary>
/// 로컬 개발 환경에서 관리자 계정이 아직 없을 때, <c>appsettings.local.json</c>의
/// <c>Admin:Username</c>·<c>Admin:Password</c>로 계정을 한 번 생성합니다.
///
/// 최초 설정(<c>POST /api/auth/setup</c>)은 전역 인증 필터를 타므로 <c>x-api-key</c>를 붙여
/// 직접 호출해야 하는데, 로컬 DB를 새로 만들 때마다 반복하기엔 번거롭습니다. 그 한 번을
/// 대신합니다. 운영의 최초 설정 경로는 그대로 두며, 이 메서드는 아래 셋을 모두 만족할 때만
/// 동작합니다 — 하나라도 어긋나면 아무 일도 하지 않습니다.
///
/// <list type="number">
/// <item><description><c>Development</c> 환경일 것 (호출부에서 검사).</description></item>
/// <item><description>설정에 아이디·비밀번호가 둘 다 있을 것. 값은 <c>appsettings.local.json</c>에만
/// 두며, 이 파일은 <c>.gitignore</c>·<c>.dockerignore</c> 대상이라 저장소(공개)와 배포 이미지
/// 어느 쪽에도 들어가지 않는다 — 그래서 소스에 자격증명을 박지 않는다.</description></item>
/// <item><description>DB에 관리자 해시가 아직 없을 것. 조회에 실패하면 "없음"으로 오판하지 않고
/// 건너뛴다(fail-closed) — 기존 계정을 덮어쓰지 않기 위함이다.</description></item>
/// </list>
/// </summary>
/// <param name="config">아이디·비밀번호를 읽을 설정 소스</param>
private static void SeedLocalAdmin(IConfiguration config)
{
    string username = (config["Admin:Username"] ?? string.Empty).Trim();
    string password = config["Admin:Password"] ?? string.Empty;

    if (string.IsNullOrWhiteSpace(username) || string.IsNullOrWhiteSpace(password))
    {
        return;
    }

    if (!AppConfigManager.TryReadDb("ADMIN_PASSWORD_HASH", out string? existingHash))
    {
        Logger.Warn("[Seed] 관리자 설정 여부를 확인할 수 없어 로컬 계정 생성을 건너뜁니다 (DB 조회 실패).");
        return;
    }

    if (!string.IsNullOrWhiteSpace(existingHash))
    {
        return; // 이미 있는 계정은 덮어쓰지 않는다
    }

    // 사용자명 → 해시 순서를 지킨다(AuthController.Setup과 동일). 뒤집으면 도중 실패 시
    // 해시만 남아 setup은 409, 로그인은 사용자명 공백으로 거부되는 잠김이 된다.
    bool userSaved = AppConfigManager.Set("ADMIN_USERNAME", username);
    bool hashSaved = AppConfigManager.Set("ADMIN_PASSWORD_HASH", CryptoUtil.HashPassword(password));

    if (!userSaved || !hashSaved)
    {
        Logger.Error("[Seed] 로컬 관리자 계정 저장 실패 — 설정이 반영되지 않았습니다.");
        return;
    }

    // 아이디·비밀번호는 로그에 남기지 않는다. TB_SYSTEM_LOG는 영구 저장소다.
    Logger.Warn("[Seed] 로컬 개발용 관리자 계정을 생성했습니다. 이 경로는 Development에서만 동작합니다.");
}
```

호출부는 `Program.Main`에서 DB가 준비된 직후다.

```csharp
// ── 로컬 개발용 관리자 계정 자동 생성 (Development 전용) ──
if (builder.Environment.IsDevelopment())
{
    SeedLocalAdmin(builder.Configuration);
}
```

배포에서 이 경로가 동작하지 않는 근거는 셋이며, 서로 독립적이다.

| 조건 | 배포에서 왜 성립하지 않나 |
|---|---|
| `ASPNETCORE_ENVIRONMENT=Development` | `Dockerfile`이 설정하지 않아 ASP.NET 기본값 `Production`이다 |
| 설정에 아이디·비밀번호가 둘 다 있을 것 | `.dockerignore`가 `*.local.json`을 빼므로 배포 이미지에 파일 자체가 없다 |
| DB에 관리자 해시가 없을 것 | 운영 DB에는 이미 있다. 조회 실패 시에도 건너뛴다 |

세 번째가 가장 강한 게이트다. 앞의 둘이 모두 뚫려도 **기존 계정을 덮어쓰지 않는다.**

## 정리 / 결론
구조 정리로 삭제 267줄 / 추가 70줄, 파일 2개 소멸(`TestController.cs`, 루트의 빈 `Visual Studio 18/` 디렉터리). 이후 로컬 검증 과정에서 실행 포트 고정과 로컬 관리자 시딩이 더해졌다.

이번 작업의 성격은 기능 변경이 아니라 **표면 축소**다. 실행 경로 중 바뀐 것은 DCA 설정 폴백 하나뿐이며, 그것도 "낡은 바스켓 매수" 대신 "스킵" 쪽으로 좁아진 것이라 기존보다 안전한 방향이다. 로컬 관리자 시딩은 새로 늘어난 유일한 경로인데, 배포에서 성립하지 않는 게이트가 셋이고 그중 하나는 기존 계정을 덮어쓰지 않는다는 조건이라 운영 인증 표면은 그대로다.

로컬 실기동 검증까지 통과했다. 남은 일은 둘이다.

첫째, `main` 머지다. `dev`가 `main`을 포함하고 있어 fast-forward가 가능하다. `main` push는 Render 재배포이자 실계좌 경로이므로 실행 직전에 다시 확인을 받는다. 배포 후에는 첫 크론에서 적립 보고서 메일이 정상 발송되는지 확인해야 한다 — 로컬에서 검증할 수 없었던 유일한 항목이다.

둘째, 이번 정리를 계기로 준비하던 주니어 온보딩 설명이다. 새 문서를 만들지 않고 기존 `ONBOARDING_GUIDE.md`·`CODE_READING_GUIDE.md`·`CODE_MAP.md` 3종을 쓰기로 했다.
