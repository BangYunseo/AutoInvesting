# 실전 전환 첫날 준비와 설정 표면 정리

## 개요
> 계좌를 실전(LIVE)으로 전환한 첫날, 적립 사이클이 실제 자금으로 집행되기 전에 필요한 준비를 정리하고 코드 3건을 반영했다. 함께 KIS 체결조회 API 실현 가능성, 설정·환경변수 전 표면, 판단 레이어 폐기 근거를 조사해 다음 작업의 판단 근거를 확보했다.

## 배경 / 목적

대시보드 배지가 `LIVE`로 바뀌어 `POST /api/order/dca-run`이 실제 자금으로 주문하는 상태가 되었다. 그동안 적립 매수는 매일 실패했고 원인은 외화 예수금 미입금이었다(정상 동작). 입금이 방아쇠이므로, 입금 전에 다음을 확정해야 했다.

1. USD 예수금만 준비하면 사이클이 실제로 매수하는가
2. 원화를 자동 환전하는 로직을 넣을 수 있는가
3. 주문이 접수만 되고 미체결로 끝나는 위험을 어떻게 감지하는가
4. 설정·환경변수가 4층에 흩어져 있어 무엇이 어디 있는지 파악이 안 되는 문제

## 본문

### 반영한 코드 변경

커밋 3건을 `main`에 반영하고 `origin/main`에 push했다. 주문 로직(`PlanPurchases`, `PlaceBuyOrderAsync`)은 한 줄도 건드리지 않았다.

#### KIS 숫자 파싱·주문단가에 InvariantCulture 명시

KIS는 응답의 숫자를 `"293.42"` 형식 문자열로 준다. 파싱이 `CurrentCulture`를 따르고 있어, 소수점이 쉼표인 로케일에서 실행되면 `29342`로 읽혀 **잘못된 값으로 주문이 성공**할 수 있었다. 출력 오류는 주문 거부로 안전하게 실패하지만 입력 오류는 조용히 통과한다.

`Core/KisBrokerClient.cs`의 파싱 6곳과 주문단가 포맷 1곳에 `CultureInfo.InvariantCulture`를 명시했다.

```csharp

// CurrentCulture로 파싱하면 29342로 읽히므로 InvariantCulture를 반드시 명시한다.
if (json.TryGetProperty("output", out var output) &&
```

컨테이너 조사 결과 현재는 깨지지 않는다. `Dockerfile`에 `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT`·`LANG`이 없고 베이스가 Debian 계열 `mcr.microsoft.com/dotnet/aspnet:8.0`이라 ICU는 있으나 `LANG` 부재로 `CurrentCulture`가 Invariant로 떨어진다. 즉 이 변경은 예방이다.

#### 설정 저장 로그에서 값 출력 제거

`Logger`는 `Program.cs`의 `DbSink`를 통해 `TB_SYSTEM_LOG`에 영구 적재된다. `AppConfigManager.Set`이 비민감 분류 키의 값을 평문으로 찍고 있었고, `ADMIN_USERNAME`이 `SensitiveKeys`에 없어 **관리자 계정명이 DB에 평문으로 영구 저장**되고 있었다. 조직 보안정책은 계정을 개인정보로 명시한다.

```csharp
// 값은 로그에 남기지 않는다. TB_SYSTEM_LOG는 영구 저장소이므로 여기에 값을 찍으면

// 저장 여부 진단에는 키 이름과 값 길이로 충분하고, 값 확인은 GET /api/config로 한다.
Logger.Info($"[AppConfig] 저장: {key} (길이 {value?.Length ?? 0})");
```

민감 키 분기가 사라져 4줄이 줄었다. 과거에 적재된 로그는 그대로 남아 있어 별도 마스킹이 필요하다.

### 확인한 사실: USD 예수금만으로 매수가 되는가

된다. 단 예수금은 4개 관문 중 마지막이다.

| 관문 | 근거 | 상태 |
|---|---|---|
| 실전 모드 `IS_PAPER_TRADING="0"` | `Core/SessionManager.cs` | 환경변수로 설정됨 (배지 LIVE 확인) |
| 당월 마커 미기록 | `Core/DailyExecutionService.cs` | 체결 0건이라 마커 미기록 |
| 해당 월 배정 템플릿 존재 | `Core/DcaSettings.cs` | 7월 = BND 5주 + VTI 8주 |
| USD 외화 예수금 | 검증 코드 없음 | 사용자 입금 대기 |

**예수금 사전 검증 코드는 어디에도 없다.** `GetCashBalanceAsync` 호출부는 `Controllers/PortfolioController.cs`(화면 표시)와 테스트뿐이고, 적립 경로는 잔고를 보지 않고 주문을 던진 뒤 KIS 거부에 맡긴다.

```csharp
string rtCd = json.GetProperty("rt_cd").GetString() ?? "";
string msg = json.GetProperty("msg1").GetString() ?? "";

if (rtCd != "0")
{
    throw new Exception($"주문 에러: {msg}");
}
```

이 `msg1`이 실패 메일 카드의 `사유`로 올라온다. 현재 관측된 문구는 `주문가능금액을 초과 했습니다`다.

부분 충족이 가장 위험하다. 앞쪽 종목만 체결되고 예수금이 마르면 뒤쪽은 실패하지만, 마커 조건이 `result.Filled.Count > 0`이라 **그 달 남은 종목은 재시도되지 않는다.** 어중간한 금액을 넣으면 안 된다.

### 확인한 사실: 원화 자동 환전은 API로 불가

KIS Developers 공개 REST API에 환전 엔드포인트가 없다. 공식 저장소 `koreainvestment/open-trading-api`의 `examples_llm/overseas_stock` 전수 조사 결과 환전 계열 0건이며, `foreign_margin`(TTTC2101R)은 증거금 조회 전용이다. 환전 채널은 HTS·MTS·영업점뿐이다.

코드베이스에도 환전 실행 로직이 없다. `Utils/ExchangeRateService.cs`는 Frankfurter·ExchangeRate-API를 GET 조회하고 1시간 캐시하는 읽기 전용이며, `IBrokerClient`에 환전 메서드가 없고 주문 바디에 통화 필드도 없다.

따라서 "낮에 환전 잡, 밤에 매수 잡"으로 스케줄러를 분리하는 안은 낮 단계가 구현 불가라 성립하지 않는다.

대체 경로는 **해외주식 통합증거금** 신청이다. KIS 공식 안내는 이를 "원화 및 국내주식 매도결제 예정금액을 매수증거금으로 사용해 환전 없이 해외주식을 거래하고, 회사가 정한 자동환전일에 필요한 결제외화만큼 자동 환전하는 서비스"로 정의한다. 신청 채널은 HTS eFriend Plus `[7473] 해외증권 거래신청`, MTS 고객지원 거래서비스 신청, 영업점이며 해외주식 거래신청과 별도 추가 신청이 필요하다. **OPEN API 주문에도 적용되는지는 명문 근거를 찾지 못했다** — 정황 근거로 `/uapi/domestic-stock/v1/trading/intgr-margin`(TTTC0869R)이 통합증거금 신청계좌의 해외 주문가능금액을 반환한다는 독스트링이 있다. 소액 실주문 실측이 필요하다.

USD 실시간 환전 가능 시간은 위탁계좌 주요통화 기준 평일 `00:10~06:00`, `09:00~23:30`이며 `06:00~09:00`과 토·공휴일은 불가하다. 크론이 KST 23:40이므로 환전 마감이 사이클 10분 전이다.

### 확인한 사실: 미국 매수는 시장가가 없다

`/uapi/overseas-stock/v1/trading/order`의 ORD_DVSN 허용값은 tr_id로 갈린다. 공식 저장소 독스트링 원문이 명확하다.

```text
ord_dvsn (str): [Header tr_id TTTT1002U(미국 매수 주문)] 00 : 지정가 32 : LOO(장개시지정가) 34 : LOC(장마감지정가)
* 모의투자 VTTT1002U(미국 매수 주문)로는 00:지정가만 가능
[Header tr_id TTTT1006U(미국 매도 주문)] 00 : 지정가 31 : MOO(장개시시장가) 32 : LOO(장개시지정가) 33 : MOC(장마감시장가) 34 : LOC(장마감지정가)
```

MOO(31)·MOC(33)는 매도 전용이고 단순 시장가 코드는 존재하지 않는다. KIS 외화증권 서비스 안내의 미국 주문유형 목록에도 장중 시장가가 없다. 따라서 현재 코드의 `ORD_DVSN = "00"`은 매수·매도·실전·모의 4조합에서 유효한 유일한 값이며 선택의 여지가 없다.

호가단위는 주문가격 $1 이상 소수점 2자리, $1 미만 4자리다. 현재 `price.ToString("0.00", ...)`는 ETF 기준 규격에 맞다.

지정가는 상한이다. SEC 원문이 `A buy limit order can only be executed at the limit price or lower`로 규정하므로, 지정가를 올려도 실제 체결은 최우선 매도호가에서 일어난다. 즉 지정가는 슬리피지 상한 역할만 한다.

### 검토 후 보류한 것: 지정가 슬리피지 버퍼

현재가 그대로 지정가를 걸면 가격이 위로 달아날 때 미체결이 되고, 접수 시점에 `Status = "FILLED"`를 하드코딩하므로 **미체결인데 "매수 완료" 메일이 오고 그 달 적립이 종료**된다. 이를 막기 위해 주문가에 0.5% 버퍼를 넣는 안을 검토했으나 **보류했다.**

보류 근거는 세 가지다.

첫째, 저장소에 지정가 미체결이 실제로 발생했다는 증거가 없다. 미체결을 탐지하는 코드 경로 자체가 없어 관측된 적이 없고, 계측되지 않은 증상에 대한 수정이 된다.

둘째, 기록가에 버퍼를 넣으면 `TB_TRADE_HISTORY.PRICE`가 실제 체결가보다 항상 크거나 같아져 증권사 계좌와의 대사가 구조적으로 불가능해진다. 프론트 컬럼 라벨이 `체결가 (USD)`이고 DTO 주석도 `체결 가격 (USD)`이다. 그리고 **이미 적재된 행은 코드 롤백으로 되돌아오지 않는다.**

셋째, `SimBrokerClient`에는 체결 판정이 없어 버퍼가 있으나 없으나 100% 체결된다. 즉 SimBroker 검증 절차로는 버퍼의 목적을 확인할 수 없고 부작용(평단 약 −0.5% 평가손 표시)만 드러난다.

세금 경로 영향은 없음을 확인했다. `Core/TaxEstimator.cs`는 `TB_TRADE_HISTORY`를 읽지 않고 취득단가를 브로커 잔고(`HoldingDto.AvgPrice` ← KIS `pchs_avg_pric`)에서 받는다. 왜곡은 SimBroker 모드에서만 발생한다. 다만 사람이 History 화면의 `체결가` 라벨을 취득가 근거로 세무 신고에 쓰면 취득가 과대 → 차익 과소 방향이 되므로 라벨 정직화가 우선이다.

### 확인한 사실: 체결 조회는 가능하나 주문번호로는 못 한다

`PENDING`을 `FILLED`로 해소할 경로가 존재한다.

`/uapi/overseas-stock/v1/trading/inquire-ccnl` · tr_id `TTTS3035R`(실전) / `VTTS3035R`(모의). **모의투자를 지원하므로 `IS_PAPER_TRADING=1`에서 배선·검증이 가능하다.** `inquire-nccs`(미체결내역, `TTTS3018R`)는 모의 TR ID가 저장소에 없어 지금 검증조차 못 하므로 배선하지 않는다.

`nccs_qty`가 두 엔드포인트 응답에 모두 있어 `inquire-ccnl` 하나로 체결·미체결·부분체결을 전부 판정할 수 있다.

```text
odno (str): "" (Null 값 설정) ※ 주문번호로 검색 불가능합니다. 반드시 ""(Null 값 설정) 바랍니다.
```

`ODNO`·`ORD_DT`·`ORD_GNO_BRNO`가 Null 고정이므로 **기간 조회 후 클라이언트에서 `odno` 문자열 매칭**이 유일한 경로다. 즉 `ORDER_NO`는 DB 갱신 키가 아니라 KIS 응답에서 우리 주문을 골라내는 매칭 키다.

판정식은 수량 비교다.

| 상황 | 판정 |
|---|---|
| 미체결 | `ft_ccld_qty == 0 && nccs_qty > 0` |
| 부분체결 | `ft_ccld_qty > 0 && nccs_qty > 0` |
| 전량체결 | `nccs_qty == 0 && ft_ccld_qty == ft_ord_qty` |
| 거부 | `rjct_rson` 존재 |

체결단가는 `ft_ccld_unpr3`가 가중평균인지 마지막 체결가인지 저장소에 명시가 없으므로 `ft_ccld_amt3 / ft_ccld_qty`로 역산하는 편이 안전하다.

함정 두 개가 다음 사람이 반드시 밟을 지점이다.

```text
ord_strt_dt (str): YYYYMMDD 형식 (현지시각 기준)
ord_end_dt (str): YYYYMMDD 형식 (현지시각 기준)
```

**조회 날짜가 현지시각 기준**이라 KST 23:40 크론에서 KST 날짜를 그대로 넣으면 조회창이 어긋난다. 현지시각 기준 ±2일로 넉넉히 잡는다.

그리고 **모의 계정은 파라미터가 제한된다.** `PDNO=""`, `SLL_BUY_DVSN="00"`, `CCLD_NCCS_DVSN="00"`, `OVRS_EXCG_CD=""`만 허용되고 `SORT_SQN`은 사용 불가다. 즉 모의에서는 전체 조회 후 클라이언트 필터가 유일하며 `_isPaperTrading` 분기가 필요하다.

WebSocket 실시간체결통보(`H0GSCNI0`/`H0GSCNI9`)는 `ODER_NO`·`CNTG_QTY`·`CNTG_UNPR`을 주는 유일한 주문번호 매칭 경로지만 상시 연결이 전제다. Headless 구조에 상시 연결 컴포넌트를 더하고 Render에서 재연결 리스크를 감당할 만한 이득이 월 1회 적립에는 없어 기각했다.

Rate limit은 공식 저장소 `examples_user/kis_auth.py` 실측이 실전 50ms, 모의 500ms 슬립이다. `kis-api-guide.md`의 200ms 규칙이 실전값보다 4배 보수적이라 그대로 유지해도 안전하며 실전 전환 후에도 바꿀 필요가 없다. 연속조회 페이지 사이 딜레이만 빼먹지 않으면 된다.

### 선행 필수로 확인된 결함: Guid 폴백

체결 대사를 붙이기 전에 반드시 고쳐야 하는 지점이 있다.

```csharp
string orderNo = "";
if (json.TryGetProperty("output", out var output))
{
    orderNo = output.GetProperty("ODNO").GetString() ?? Guid.NewGuid().ToString("N").Substring(0, 12);
}
```

ODNO 추출 실패 시 **증권사에 존재하지 않는 가짜 주문번호**가 `TB_TRADE_HISTORY.ORDER_NO`에 들어간다. 그 행은 `inquire-ccnl` 응답과 영원히 매칭되지 않으므로 대사 로직이 "미체결"로 확정 오판한다. 지금은 `FILLED` 하드코딩이라 드러나지 않지만 대사를 붙이는 순간 조용한 거짓이 된다.

### 검토한 체결 기록 설계

`ORDER_NO` 기준으로 얼마 체결됐는지 기록하는 방향을 검토했고 타당하다고 판단했다. 스키마가 이미 그 방향으로 설계돼 있었다.

```sql
STATUS        VARCHAR(20) NOT NULL DEFAULT 'PENDING',
```

DB 기본값이 `PENDING`이고 프론트 라벨맵도 이미 지원한다.

```javascript
const STATUS_LABEL = { FILLED: '체결', PENDING: '대기', FAILED: '실패' };
```

즉 `PENDING` 전환은 새 설계가 아니라 원설계 복원이다. 코드가 `FILLED`를 하드코딩하며 설계를 배신한 상태다.

추가할 컬럼은 둘이다. 별도 `TB_ORDER_FILL` 테이블은 만들지 않는다 — 체결 단위 이력을 볼 소비자가 없고 DCA 대조에는 누적 합계로 충분하다.

```sql
ALTER TABLE TB_TRADE_HISTORY ADD COLUMN IF NOT EXISTS FILLED_QTY   INTEGER;
ALTER TABLE TB_TRADE_HISTORY ADD COLUMN IF NOT EXISTS FILLED_PRICE NUMERIC;
```

`NULL`은 "아직 조회 안 함", `0`은 "조회했고 미체결 확정"이다. 이 구분 때문에 nullable이어야 한다. `NOT NULL DEFAULT 0`으로 만들면 모든 과거 행이 미체결로 보인다.

갱신 키는 `TRADE_ID`(PK)를 쓴다. `ORDER_NO`에 유니크 제약이 없고 KIS ODNO가 영업일 단위로 재사용되는지 확인되지 않았으므로 `WHERE ORDER_NO = @x`는 위험하다. 그래서 `Insert`에 `RETURNING TRADE_ID`가 필요하다 — 기존 호출자 2곳은 반환값을 무시하면 그대로 컴파일된다.

후속 조회 실행 경로는 새 크론이 아니라 `DailyExecutionService` 앞단에 붙이는 게 훨씬 싸다. 적립은 월 1회지만 크론은 매일 돌므로, "이번 달 이미 적립" 스킵 전에 미해소 `PENDING` 해소 패스를 먼저 돌리면 새 실행 경로·새 실패 모드가 0이 된다.

DB 스키마 변경은 자동 적용 경로가 없다. `DBManager.RunMigration`이 2026-07-30에 제거되어 기동 시 `create_tables.sql`만 실행하며, 그 파일은 `CREATE TABLE IF NOT EXISTS`이므로 컬럼을 추가해도 기존 DB에 반영되지 않는다. `create_tables.sql`(신규 DB용)과 `Data/sql/` ALTER 스크립트(기존 DB용 수동 실행)를 같은 커밋에서 함께 넣어야 한다.

`FILLED_PRICE`를 `TaxEstimator`에 배선하지 않는다. 취득단가 단일 진실 원천은 KIS 평단이며, DB 기록가를 세금에 끌어들이면 진실 원천이 둘이 된다.

### 검토 후 기각한 것: 보유잔고 델타로 자동 FILLED 판정

잔고 수량이 늘면 체결로 간주해 상태를 바꾸는 안을 검토했으나 기각했다. 잔고는 누적 상태고 체결은 이벤트여서 상태로 이벤트를 역추적하는 구조가 된다.

부분 체결이면 수량 차이가 주문 수량과 달라 판정이 틀리고, 같은 날 같은 종목에 적립과 수동 주문이 겹치면 귀속이 불가능하며, 주문 직전 수량을 저장하는 컬럼이 없어 애초에 차이를 계산할 수 없다.

결정적으로 코드에 이미 두 개의 함정이 기록돼 있다. KIS가 "체결기준현재잔고"를 별도 API(CTRP6504R)로 분리해 뒀다는 것은 지금 쓰는 `ovrs_cblc_qty`가 체결 즉시 반영이 아닐 수 있다는 신호이며, 모의(VTTS3012R)는 `OVRS_EXCG_CD=NASD`가 나스닥만이라 NYSE·AMEX 보유분이 누락되어 **모의로 검증조차 불가능**하다.

상태를 바꾸지 않고 "잔고 증분 대 기록 누적의 불일치"만 메일에 한 줄 경고하는 축소판은 위험 없이 계측 목적을 달성하므로, `inquire-ccnl` 배선이 어려워질 경우의 대안으로 남긴다.

### 설정·환경변수 전 표면 조사

설정 관문은 `AppConfigManager.Get` 하나이며 우선순위는 **환경변수 → DB `TB_APP_CONFIG` → appsettings.json → 호출부 기본값**이다. 문서와 `Program.cs` 주석 일부가 이 순서를 반대로 서술하고 있다.

이 관문을 거치지 않는 우회 경로가 셋이다.

| 우회 | 위치 | 읽는 층 |
|---|---|---|
| DB 접속 | `Data/DBManager.cs` | 환경변수 → 하드코딩 로컬 폴백 |
| 메일 | `Utils/NotificationService.cs` | 환경변수 → appsettings (DB 불가) |
| 암호화 키 | `Utils/CryptoUtil.cs` | IConfiguration → 환경변수 (DB 불가) |

`appsettings.json`의 시크릿 성격 키는 전부 빈 문자열이며 `Kis` 섹션에 `AppKey`·`AppSecret`·`AccountNo` 항목 자체가 없다. `appsettings.local.json`은 `.gitignore`와 `.dockerignore` 양쪽에서 제외되고 `git ls-files`에 없다. **커밋 유출 없음.**

`render.yaml`이 저장소에 없어 프로덕션 환경변수 목록을 코드로 검증할 수 없다. 이것이 아래 위험들의 위험도를 올린다.

#### 발견한 위험 3건

첫째, **`DCA_LAST_RUN_MONTH`가 환경변수로 섀도잉 가능하다.** `AppConfigManager.Get`은 키 이름을 그대로 `Environment.GetEnvironmentVariable`에 넘기므로, 동명 환경변수가 존재하면 `Set`은 DB에 쓰지만 `Get`은 영원히 환경변수 값을 반환한다. 과거 월 값이면 월 1회 멱등 가드가 영구 무력화되어 크론이 매일 매수하고, 현재 월 값이면 적립이 영구 스킵된다. 로그와 UI는 저장 성공을 보고하므로 증상만 보면 가드가 동작하는 것처럼 보인다. Render 환경변수 목록 확인 결과 **이 키는 없었다.**

둘째, **`POST /api/config`가 임의 키를 DB에 무제한 기록한다.** GET은 5개 키만 노출하는데 POST는 화이트리스트가 없다. `DCA_LAST_RUN_MONTH`·`ADMIN_PASSWORD_HASH` 조작과 `DcaSettings.SaveConfig`의 티커·수량·Id 검증을 우회한 원시 JSON 주입이 가능하다. 읽기(`RevealSecret`)는 화이트리스트로 막혀 있는데 쓰기는 열려 있어 방향이 비대칭이다.

셋째, **환경변수 우선순위 때문에 조용한 저장 실패가 발생한다.** 동명 환경변수가 있으면 UI 저장이 DB에 기록되고 성공 응답까지 오지만 동작은 바뀌지 않는다.

#### 죽은 설정 2건

`KIS_SERVER`는 `Controllers/ConfigController.cs`에서 화면 표시용으로만 읽히고 분기에 쓰이지 않는다. 도메인은 `IS_PAPER_TRADING` 단독으로 결정된다. 그런데 `recommended_rules.md`의 실거래 전환 절차가 "KIS `Server`를 실전으로"를 요구하고 있어 **무효한 지시**다.

`RESEND_API_KEY`는 UI가 DB에 암호화 저장하지만 `NotificationService`가 DB를 읽지 않아 **설정 화면 저장이 메일 발송에 전혀 반영되지 않는다.** `API_ACCESS_KEY`는 `AppConfigManager.Get` 경유라 DB 반영이 되므로 동작이 갈린다.

#### 환경변수 정리 결정

Render 환경변수 12개를 확인했고, 이 중 `AI_PROVIDER`와 `GEMINI_API_KEY`는 Phase 6에서 코드째 제거된 판단 레이어의 잔재로 코드 참조가 0건이었다. 삭제 완료.

나머지 10개는 **환경변수에 그대로 둔다.** 시크릿을 DB로 이관하는 안을 검토했으나 철회했다. `security.md`가 환경변수를 1순위로 명시하고, DB 유출이 곧 시크릿 유출이 되며, 현재 시크릿이 환경변수에 있어 `MASTER_KEY` 분실 피해가 작은 견고함을 잃게 된다. `IS_PAPER_TRADING`은 DB로 옮기면 DB 조회 실패 시 appsettings 기본값(모의)으로 조용히 추락하고, `API_ACCESS_KEY`는 DB 장애가 곧 크론 401이 된다.

수정 빈도로 보면 자주 바꾸는 것(DCA 템플릿·월배정)은 이미 전용 UI에 있고, 환경변수 10개는 거의 손대지 않는 값들이다. 따라서 문제는 "많다"가 아니라 "어디 있는지 안 보인다"였고, 해법은 값을 옮기는 게 아니라 레퍼런스 문서와 진단 엔드포인트다.

INI 파일로 묶는 안도 검토 후 기각했다. `appsettings.local.json`이 이미 그 역할이고 `Program.cs`에서 optional 로드되며 gitignore 대상이다. INI를 넣으면 층이 하나 더 늘어 문제를 악화시키고, 배포 환경은 휘발성 파일시스템이라 파일 자체가 성립하지 않는다.

`SensitiveKeys`에 `ADMIN_USERNAME`·`ADMIN_PASSWORD_HASH`를 추가하는 안도 철회했다. `MASTER_KEY` 분실 시 `ADMIN_PASSWORD_HASH` 암호화는 복호화 실패 → 빈 값 → `needsSetup=true`가 되어 누구나 관리자를 재등록할 수 있고, `ADMIN_USERNAME`만 암호화하면 로그인 불가와 setup 차단이 겹쳐 완전 잠김이 된다. 유출 위험의 실체는 로그였고 그건 이미 막았다.

| QQQ | 20.10% | 20.54% | +0.43%p |
| SPY | 14.77% | 15.14% | +0.37%p |

미래를 아는 매수 시점 선택조차 연 0.4%p다. 따라서 어떤 타이밍 전략도 이 천장을 못 넘고, AI 모델 품질 논쟁이 원천적으로 무의미해진다. 실제 구현 가능한 규칙(SMA200 추세추종)은 −2.0~−2.4%로 졌다.

이 결론의 한계도 문서가 정직하게 고지한다. 기간 편향(최근 15년 강세장), 롱온리 월간 매수에 한정된 상한, 밸류애버리징 결과는 투입 원금이 달라 같은 돈 비교가 아니라는 점, 그리고 **LLM 뉴스판단은 lookahead 오염으로 정직한 백테스트가 불가능해 의도적으로 제외**했다는 점이다. 즉 "AI 뉴스 판단이 열등함을 입증했다"고 말할 수 없고, 기각 근거는 상한 논리다.

현재 AI를 쓸 자리는 없다. 판단 영역은 규칙이 금지하고 상한 논리로 무의미하며, 정보 전용 후보(실패 메일 원인 해설, 로그 이상 요약, 세무 자료 정리)는 전부 규모가 작아 YAGNI다. 선례로 `Macro`(FRED)는 정보 전용이었으나 프론트 소비자가 0이어서 2026-07-30에 제거됐다.

다음 단계.

1. **입금 전 필요액 확인.** 적립설정 화면에서 7월 템플릿의 총 매수금액을 읽고 환율로 나눠 10% 여유를 더한다. 부분 충족은 마커가 찍혀 그 달 남은 종목이 재시도되지 않으므로 어중간한 금액을 넣지 않는다. 환전 마감은 평일 `23:30`이고 사이클은 `23:40`이다.
2. **오늘 밤 사이클 결과로 체결 계측.** KIS 앱에서 실제 체결 여부와 체결가를 확인하고 `TB_TRADE_HISTORY` 기록가와 대조한다. 미체결이 관측되면 지정가 버퍼를, 관측되지 않으면 아무것도 하지 않는다.
3. **`Guid` 폴백 제거.** 체결 대사의 선행 조건이다.
4. **`PENDING` + `inquire-ccnl` 배선.** 컬럼 2개, `TRADE_ID` 갱신, `DailyExecutionService` 앞단 해소 패스, 프론트 컬럼·`PARTIAL` 라벨, `kis-api-guide.md`에 함정 2개 기록. 스키마 변경이 걸려 있어 `feature/` 브랜치와 사용자 테스트 승인이 필요하다.
5. **설정 진단.** `GET /api/config`에 출처 층 필드를 더해 "이 키가 환경변수에서 오는가 DB에서 오는가"를 보이게 한다.
6. **`POST /api/config` 화이트리스트.** 임의 키 기록을 막는다.
7. **과거 로그 마스킹.** `TB_SYSTEM_LOG`에 남은 계정명을 `UPDATE`로 가린다. 사전 `COUNT` 확인과 트랜잭션 건수 검증이 필요하고 되돌릴 수 없다.
8. **`MASTER_KEY`·`AUTH_TOKEN_SECRET` 오프라인 백업.** 재암호화 경로가 없어 분실이 곧 복구 불가다. 다만 DB에 `enc:v1:` 행이 0건이면 `MASTER_KEY` 피해 범위는 작다.

정정이 필요한 문서.

`recommended_rules.md`의 실거래 전환 절차에서 "KIS `Server`를 실전으로"는 무효다. 실제 스위치는 `IS_PAPER_TRADING="0"` 하나이며 `"false"`는 모의로 떨어진다.
