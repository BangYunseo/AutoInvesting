# 체결 대사 주문체결내역조회 전환

## 개요
> 체결 대사가 보유 수량 차이로 체결을 추론하던 방식을 KIS 주문체결내역조회(`inquire-ccnl`)로 전환하는 작업이다. 오늘은 조회 메서드를 붙이는 데까지 진행했고 대사 로직은 아직 바꾸지 않았다. 같은 날 `dev`/`main` 2브랜치 체제로 전환했다.

## 배경 / 목적

`[2026-09-10] 01_돈경로_코드지도_및_수정목록.md`에서 기록한 결함 2(ODNO 기반 상태 갱신)의 후속으로 시작했다. 처음에는 스냅샷 구조를 축소하고 `TB_TRADE_HISTORY`를 읽게 하는 방향으로 설계했으나, 논의 중에 전제가 틀렸다는 결론이 나왔다.

문제는 데이터 구조나 갱신 키가 아니라 **대사가 잘못된 API에서 값을 받고 있는 것**이다.

현재 대사는 `GetHoldingsAsync`(잔고 조회)로 보유 수량만 두 번 받아 차이로 체결을 추론한다. 잔고에는 주문번호가 달려 있지 않으므로, 같은 종목에 주문이 여러 건이면 어느 주문의 체결인지 귀속할 방법이 없다. 정보가 애초에 응답에 들어오지 않는다.

KIS에는 주문 단위 체결 수량을 직접 주는 API가 있다. 그쪽으로 바꾸면 추론이 필요 없어지고, 지금까지 쌓인 결함 여러 개가 고치는 게 아니라 원인째 사라진다.

## 본문

### 현재 대사 방식과 한계

`ReconcileAsync`는 스냅샷에 저장해둔 주문 직전 보유 수량과 현재 보유 수량의 차이로 체결을 판정한다.

```csharp
var nowQty = (await client.GetHoldingsAsync())
    .GroupBy(h => h.Ticker, StringComparer.OrdinalIgnoreCase)
    .ToDictionary(g => g.Key.ToUpper(), g => g.Sum(h => h.Qty), StringComparer.OrdinalIgnoreCase);

int totalOrdered = 0, totalFilled = 0;
bool anySold = false;
var lines = new List<string>();

foreach (var o in snap.Ordered)
{
    snap.Before.TryGetValue(o.Ticker, out int before);
    nowQty.TryGetValue(o.Ticker, out int now);

    int delta = now - before;
    if (delta < 0) anySold = true;

    int filled = Math.Max(0, Math.Min(delta, o.Qty));
    totalOrdered += o.Qty;
    totalFilled += filled;

    string status = filled >= o.Qty ? "FILLED" : filled > 0 ? "PARTIAL" : "FAILED";
    TradeHistoryDAO.UpdateStatusByOrderNo(o.OrderNo, status);

    lines.Add($"{o.Ticker}: 주문 {o.Qty}주 · 체결 {filled}주 (보유 {before}→{now})");
    Logger.Info($"[Reconcile] {o.Ticker} 주문 {o.Qty}주 → 체결 {filled}주 (보유 {before}→{now}), 상태 {status}");
}
```

이 방식이 성립하려면 세 가지가 전부 참이어야 한다. 주문 직전 보유 수량을 정확히 찍어두었을 것, 대사 시점까지 그 종목의 수량이 우리 주문 외의 이유로 변하지 않았을 것, 같은 종목에 주문이 하나뿐일 것.

셋 다 깨질 수 있다.

#### 빈 Before가 전량 체결로 읽힌다

주문 직전 잔고 조회가 실패하면 빈 딕셔너리로 계속 진행한다.

```csharp
catch (Exception ex)
{
    beforeQty = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase);
    Logger.Warn($"[DCA] 주문 전 보유 수량 조회 실패 : 체결 대사 불가: {ex.Message}");
}
```

로그는 "체결 대사 불가"라고 말하지만 그 스냅샷이 그대로 저장된다. `SavePendingSnapshot`의 유일한 가드는 접수 건수가 0인지뿐이다.

```csharp
if (result.Accepted.Count == 0) return;
```

대사 시점에 `before`가 0이 되고, `delta`는 기존 보유 전량이 된다. `Math.Min` 클램프를 거치면 `filled = o.Qty`가 되어 전 종목이 FILLED로 판정된다. `delta`가 음수가 아니므로 `anySold` 안전망도 발동하지 않는다.

실제로는 한 주도 체결되지 않았을 수 있는데 DB에는 FILLED로 확정 기록되고, 스냅샷은 같은 패스에서 삭제되어 사후 재판정 근거가 사라진다.

#### 사려던 것이 아니라 접수된 것만 관측한다

스냅샷의 주문 목록은 `result.Accepted`로 구성된다. 현재가 조회에 실패해 계획에서 빠진 종목은 애초에 들어오지 않는다.

```csharp
decimal px = await _broker.GetCurrentPriceAsync(ticker);
if (px <= 0)
{
    Logger.Warn($"[DCA] {ticker} 조회 실패 : {ticker}는 매수를 건너뜁니다.");
    continue;
}
```

그 종목은 `result.Failures`에도 담기지 않는다. 대사는 그 존재를 모르고, 나머지가 체결되면 "전량 체결"로 마감한다. 매달 같은 종목이 빠져도 메일은 매번 정상이라고 보고한다.

#### 주문별 귀속이 불가능하다

크론 주문과 수동 주문이 같은 종목에 걸리면 하나의 `delta`를 두 주문이 나눠 가져야 한다. 잔고 응답에는 주문번호가 없으므로 배분 근거가 없다.

현재는 스냅샷이 티커로 묶이면서 같은 종목을 한 건으로 합치기 때문에 이 문제가 드러나지 않는다. 대신 DB 반영이 깨져 나머지 행이 영구히 PENDING으로 남는다.

```csharp
Ordered = result.Accepted
    .GroupBy(f => f.Ticker.ToUpper())
    .Select(g => new PendingOrder
    {
        Ticker = g.Key,
        Qty = g.Sum(x => x.Qty),
        OrderNo = g.Select(x => x.OrderNo).FirstOrDefault(o => !string.IsNullOrEmpty(o)) ?? string.Empty
    })
    .ToList()
```

### 전환하면 사라지는 것

`inquire-ccnl`은 주문 단위로 체결 수량을 직접 준다. 응답에 주문번호가 함께 오므로 귀속이 가능하다.

| 응답 필드 | 뜻 |
|---|---|
| `odno` | 주문번호 |
| `ft_ord_qty` | 주문 수량 |
| `ft_ccld_qty` | 체결 수량 |
| `nccs_qty` | 미체결 수량 |
| `prcs_stat_name` | 완료 / 거부 / 전송 |
| `rjct_rson_name` | 거부 사유 |

추론이 사라지므로 추론을 지탱하던 장치가 전부 불필요해진다.

| 지금 있는 것 | 전환 후 |
|---|---|
| `DCA_PENDING_SNAPSHOT`의 `Before` | 불필요. 어제 수량을 기억할 이유가 없다 |
| `delta = now - before` | 불필요. 체결 수량을 직접 받는다 |
| `anySold`(수량 감소 시 판정 불신) | 불필요. 사람이 매도해도 판정에 영향 없다 |
| 수동 주문과 크론 주문의 구분 문제 | 불필요. 주문마다 답이 따로 온다 |
| 빈 `Before`로 인한 거짓 FILLED | 원인 소멸 |

`ODNO`의 위상은 반대로 올라간다. 지금은 판정에 쓰이지 않는 참고값이지만, 전환 후에는 응답과 우리 기록을 맞추는 키가 된다. 주문번호를 받지 못한 건은 종목과 수량, 시각으로 찾는 대비가 필요하다.

```csharp
public async Task<List<OrderFillDto>> GetOrderFillsAsync(string startDate, string endDate)
{
    await _tokenManager.EnsureValidTokenAsync();
    // Rate limit 방지 (초당 3건 제한)
    await Task.Delay(400);

    string trId = _isPaperTrading ? "VTTS3035R" : "TTTS3035R";

    // 모의 : 실전 분기
    string all = _isPaperTrading ? "" : "%";

    // 주문번호(ODNO)로는 검색 불가(기간 필터 조회)
    string path = "/uapi/overseas-stock/v1/trading/inquire-ccnl"
        + $"?CANO={_accountNoPrefix}&ACNT_PRDT_CD={_accountNoSuffix}"
        + $"&PDNO={all}"
        + $"&ORD_STRT_DT={startDate}&ORD_END_DT={endDate}"
        + "&SLL_BUY_DVSN=00"      // 전체(매도+매수)
        + "&CCLD_NCCS_DVSN=00"    // 전체(체결+미체결)
        + $"&OVRS_EXCG_CD={all}"
        + "&SORT_SQN=DS"         
        + "&ORD_DT=&ORD_GNO_BRNO=&ODNO="
        + "&CTX_AREA_NK200=&CTX_AREA_FK200=";

    var response = await SendWithRetryAsync(() => CreateRequest(HttpMethod.Get, path, trId));
    response.EnsureSuccessStatusCode();

    var responseString = await response.Content.ReadAsStringAsync();
    var json = JsonSerializer.Deserialize<JsonElement>(responseString);

    // rt_cd 검사
    string rtCd = json.TryGetProperty("rt_cd", out var rc) ? (rc.GetString() ?? "") : "";
    if (rtCd != "0")
    {
        string msg1 = json.TryGetProperty("msg1", out var m1) ? (m1.GetString() ?? "").Trim() : "";
        throw new Exception($"주문 체결 내역 조회 에러 (rt_cd={rtCd}, msg1={msg1})");
    }

    var list = new List<OrderFillDto>();
    if (json.TryGetProperty("output", out var output) && output.ValueKind == JsonValueKind.Array)
    {
        foreach (var item in output.EnumerateArray())
        {
            list.Add(new OrderFillDto
            {
                OrderNo = ReadString(item, "odno"),
                Ticker = ReadString(item, "pdno"),
                OrderQty = ReadInt(item, "ft_ord_qty"),
                FilledQty = ReadInt(item, "ft_ccld_qty"),
                UnfilledQty = ReadInt(item, "nccs_qty"),
                StatusName = ReadString(item, "prcs_stat_name"),
                RejectReason = ReadString(item, "rjct_rson_name"),
            });
        }
    }

    // 1페이지 조회(실전 20건/모의 15건). tr_cont가 M/F면 다음 페이지가 남았다는 뜻이다.
    string cont = response.Headers.TryGetValues("tr_cont", out var contValues)
        ? string.Join("", contValues).Trim()
        : "";

    if (cont == "M" || cont == "F")
    {
        Logger.Warn($"[KisBroker] 주문 체결 내역 조회: {startDate}~{endDate} {list.Count}건 - 일부 페이지가 조회되지 않았습니다.");
    }
    else
    {
        Logger.Info($"[KisBroker] 주문 체결 내역 조회: {startDate}~{endDate} {list.Count}건");
    }

    return list;
}
```

파싱 헬퍼 두 개를 같이 넣었다.

```csharp
private static string ReadString(JsonElement item, string name)
    => item.TryGetProperty(name, out var p) ? (p.GetString() ?? "").Trim() : "";

/// <summary>
/// 수량 필드 조회
/// </summary>
private static int ReadInt(JsonElement item, string name)
{
    string raw = ReadString(item, name);
    if (decimal.TryParse(raw, NumberStyles.Any, CultureInfo.InvariantCulture, out decimal d))
        return (int)Math.Floor(d);
    return 0;
}
```

### 구현에서 정한 것

모의계좌는 `PDNO`·`SLL_BUY_DVSN`·`CCLD_NCCS_DVSN`·`OVRS_EXCG_CD`가 전체조회만 지원하고, 전체를 뜻하는 표기가 실전(`%`)과 모의(`""`)로 다르다. 그 두 자리만 분기하고 나머지는 실전에서도 전체조회 값으로 통일해 경로를 하나로 유지했다.

`CCLD_NCCS_DVSN`은 `00`(전체)으로 둔다. 체결만 받으면 잔여 수량을 알 수 없다.

`rt_cd` 검사는 `GetHoldingsAsync`와 같은 이유로 예외를 던진다. 빈 배열이 "체결 0건"으로 조용히 통과하면 대사가 전량 미체결로 오판한다.

수량은 `decimal`로 파싱한 뒤 내림한다. KIS가 `"2"`로 줄지 `"2.0000"`으로 줄지 문서로는 확실하지 않고, 후자에서 `int.TryParse`는 0이 된다.

연속조회는 붙이지 않았다. 호출부가 하루 단위로 부르면(`startDate == endDate`) 상한(실전 20건, 모의 15건)에 닿을 일이 없다. 범위를 넓게 부르는 호출부가 생기면 `tr_cont`가 `M`/`F`로 와서 경고 로그가 먼저 뜬다.

주문번호로는 검색할 수 없다. 문서가 `ODNO` 요청 파라미터에 공란을 강제한다. 기간으로 받아 응답의 `odno`로 우리가 맞춘다.

### 확인하지 않은 것

실제로 호출해보지 않았다. 이것이 확인되기 전에는 대사를 바꿀 수 없다.

모의계좌에 이번 달 주문 기록이 있는지 모른다. 없으면 빈 배열이 돌아와 연동은 됐지만 검증이 안 된 상태가 된다. 그 경우 실전 계좌로 조회해야 한다. GET 요청이므로 자금은 나가지 않는다.

모의에서 `ft_ccld_qty`가 실전과 같은 형태로 오는지 모른다. 잔고 조회에서 `OVRS_EXCG_CD=NASD`의 의미가 실전(미국 전체)과 모의(나스닥만)로 달라 종목이 누락된 전례가 있다. 같은 종류의 함정이 여기에도 있을 수 있다.

대사 시각(KST 06:30)에 당일 체결 내역이 조회되는지 확인하지 않았다. 정산 시점에 따라 아직 반영되지 않았을 수 있다.

### 브랜치 전환

같은 날 `dev`/`main` 2브랜치 체제로 바꿨다. `main` 직접 커밋은 검증 전 코드가 곧바로 실거래 서버로 나간다.

GitHub Actions의 `schedule` 트리거는 기본 브랜치에서만 발화한다. `dev`에 무엇을 커밋하든 `daily-run.yml`과 `reconcile.yml`이 돌지 않으므로 실자금 집행 경로와 분리된다.

`main` 머지는 `git merge --ff-only dev`만 쓴다. 갈라진 상태면 머지가 거부되므로 모르고 머지 커밋을 만드는 사고를 막는다.

규칙은 `.agents/rules/git-conventions.md`에 반영했다.

### 남은 결함과 착수 순서

어제 기록한 4건 중 전환으로 해결되는 것과 따로 고쳐야 하는 것이 갈린다.

| # | 결함 | 전환으로 해결되나 |
|---|---|---|
| 1 | 주문 POST 재시도 10회, 멱등키 없음 | 아니오. 주문 측 별건 |
| 2 | ODNO 기반 상태 갱신, 스냅샷 GroupBy | 예. 주문별 응답으로 대체 |
| 3 | 일부 종목 현재가 실패 시 조용한 누락 | 아니오. 엔진 측에서 고쳐야 한다 |
| 4 | 거래소 폴백 `NASD`가 실패 사유를 가림 | 아니오 |

착수 순서는 다음과 같다.

첫째, 결함 3을 엔진에서 고친다. `DcaAccumulationEngine`에서 현재가 조회에 실패한 종목을 `result.Failures`에 담으면 된다. 세 줄이고 대사 코드를 건드리지 않는다. 가장 상류이며 이것만으로 보고서 집계와 종목 카드가 함께 복구된다.

둘째, `inquire-ccnl`을 실제로 호출해 값을 확인한다.

셋째, 확인이 끝나면 대사를 전환한다. 스냅샷 관련 코드를 걷어낸다.

넷째, 결함 1을 따로 다룬다. 대사로는 원리상 막을 수 없다. 주문 POST만 재시도 정책에서 분리하거나, 재시도 전에 미체결 주문을 조회해 확인하는 방식이 후보다.

결함 4는 우선순위가 가장 낮다. 거래소를 확인하지 못하면 주문을 시도하지 않고 명확한 사유로 실패시키면 된다.

### 후속 기능 후보

부분 체결 시 미체결분만 다시 사는 기능이다. 현재는 부분 체결에서 마커를 되돌리지 않으므로 그 달 적립이 누락된다.

`AccumulateAsync`는 임의의 수량 딕셔너리를 받으므로 엔진 자체는 바꿀 필요가 없다. 지금은 호출부가 항상 템플릿 전량을 넘길 뿐이다.

```csharp
public async Task<DcaCycleResult> AccumulateAsync(
    Dictionary<string, int> quantities,
    decimal budgetKrw)
```

어려운 지점은 잔여 매수가 월 1회 게이트를 통과해야 한다는 것이다. 현재 게이트를 뚫는 것은 `force`와 `reserved` 둘뿐이고 모두 사람의 명시적 의사다. 여기에 코드가 판단한 잔여를 추가하면 중복 매수의 새 입구가 생긴다.

이 기능은 대사 전환이 끝난 뒤에 올린다.

## 정리 / 결론

문제는 로직이 아니라 값의 출처였다. 잔고 API로는 주문별 체결을 알 수 없고, 이는 코드를 아무리 고쳐도 해결되지 않는다.

`inquire-ccnl`로 바꾸면 스냅샷, `delta` 계산, `anySold` 판정, 수동 주문 구분이 전부 불필요해진다. 어제 기록한 결함 중 하나는 고치는 것이 아니라 원인이 사라진다.

오늘은 조회 메서드를 붙이는 데까지 했다. 빌드 오류 0, 테스트 57건 전부 통과다. 대사 로직은 손대지 않았으므로 기존 동작은 그대로다.

다음 단계는 실제 호출 검증이다. 모의계좌에서 값이 문서대로 오는지 확인하기 전에는 대사를 바꿀 수 없다. 확인 없이 전환하면 대사가 조용히 오작동하고, 그 결과는 중복 매수 또는 적립 누락이다.
