# 조회 컨트롤러 리팩토링 진행

## 개요
> 마스터 인계 노트 `[2026-07-04] 01_코드베이스 분석 리팩토링 인계.md`의 6순위(조회 컨트롤러)를 이어받아, 조회 컨트롤러 6개를 동작 보존 원칙으로 이해·문서화하고 정리 후보를 적용하는 작업의 260717 세션 진행 상태를 담는다. 재개 시 이 파일과 260704 인계 노트를 함께 볼 것.

## 배경 / 목적
동작 보존(behavior-preserving) 원칙으로 조회 컨트롤러 6개(Price/History/Portfolio/Config/Dca/Auth)를 이해·문서화하고, 발견된 정리 후보를 사용자 확인 후 적용한다. 문서는 사용자 스타일(간결 + Part 2는 줄번호 대신 "코드 스니펫 + 기능 설명")로 작성한다.

## 본문
### 계획
1. 6개 컨트롤러 병렬 정독·의존성 추적·확인포인트(응답규격/입력검증/위임/예외) 검증 → 리팩토링 후보 도출.
2. 후보를 순수 동작보존(①~⑥) / 동작 변경(⑦~⑨)으로 분류, 하나씩 설명·확인 후 적용.
3. 이해 문서 6개(docs/modules/*.md) 작성.
4. 성격별 커밋(미push) → 인계 노트 갱신.

### 확정한 것
- 문서 스타일: Part 2 라인바이라인은 줄번호(`46~75행`) 금지, 실제 코드 스니펫 + 그 블록 기능 설명. Part 1도 간결. (샘플로 `docs/modules/[2026-07-04] 02_AppConfigManager.md` Part 2를 이 스타일로 변환 완료.)
- 로그 접두사: 영문 모듈 태그로 통일(architecture.md 규칙 + 추적성 근거). 코드베이스가 이미 혼재(대부분 영문, 일부 한글)였음.

### 적용 완료
빌드 경고 0 / 오류 0.

- ① Logger.Error 누락 보강: 500 반환하면서 로그가 없던 3곳 — `ConfigController`(GetAllConfigs/UpdateConfig), `TestController`(Buy)에 `Logger.Error` 추가. 500 응답 본문은 미변경(순수 로그 추가). 전수 스캔 결과 나머지 13개 500-지점은 이미 로그 있음.
- 로그 접두사 영문 통일: `[설정]`→`[AppConfig]`, `[환율]`→`[ExchangeRate]`, `[서버]`→`[Program]`, Portfolio 무접두사/`[API]`→`[Portfolio]`, `[TestController]`→`[Test]`. (SSOT 규칙 문서 `code-style-guide.md`의 `[API]` 예시는 미변경 — harness-sync 별건.)
- ⑧ 성공 응답 배열→객체 엔벨로프: 백엔드 `holdings`/`trades`를 `{ holdings }`/`{ trades }`로. 프론트 소비처 2곳(`Order.jsx`, `History.jsx`)도 `data.holdings`/`data.trades`로 동시 수정. (`portfolio/summary`는 원래 객체라 무관.)

### 워크플로우 분석 결론
- 6개 컨트롤러 구조는 건강: 위임 깔끔, 빈 catch 없음, 레이어 역방향 의존/IBrokerClient 우회 없음.
- 반복 문제는 전부 "응답·관측 이음매"에 집중(로직 아님): 500 규격 3파 분열·예외원문 유출, 성공 응답 엔벨로프 불일치, 로그인 실패 처리 불일치(Order는 503, Price/Portfolio는 무시), 저장 동사 POST(Config) vs PUT(Dca), 6개 중 4개 동기 블로킹 DB I/O.
- 부수 발견: `OrderNo`는 DAO 저장/조회 양쪽에서 누락돼 항상 빈 값(근본 원인=DAO, Data 레이어 단계에서 판단).

### 결정 대기
여기부터 이어간다.

- AppConfigManager `Get()` 매 조회 로그: 미커밋 상태의 사용자 변경에 `Get()` 히트마다 `Logger.Info`가 있음. `Get()`이 매우 자주 불려 로그 폭주 + TB_SYSTEM_LOG DB INSERT 폭증 우려. → 제거(권장) 또는 Debug 강등 결정 필요. 이걸 정해야 `Data/AppConfigManager.cs`를 깔끔히 커밋 가능.
- ⑦ 500 규격 통일 + 예외원문 유출 차단 적용 여부: 500 본문을 `{ error = 일반메시지 }`로 통일하고 `ex.Message`는 서버 로그에만. (History/Dca/Order/Config/Portfolio/Test가 예외원문 유출 중. 동작 변경 — 프론트 파싱 확인 필요.)
- ⑨ Dca PUT 응답을 정규화 저장값으로: 현재 PUT 응답이 정규화 전 원본 요청을 에코 → 응답≠DB≠다음GET. 저장 후 재조회 값 반환으로 교정. (동작 변경, 위험 낮음.)

### 남은 순수 후보
동작보존, 미적용.

- ③ `HistoryController` 죽은 using 제거(System.Collections.Generic/IO/Linq).
- ④ 낡은 주석 정정: `TradeHistoryDto`의 'LS증권'→KIS, `PriceController` 클래스 주석에 "Sim은 미지 티커 $100 폴백이라 404 미도달" 보강.
- ⑤ `ConfigController`의 로컬 secretKeys ↔ `AppConfigManager.SensitiveKeys` 중복 제거(동일 집합 2곳 정의). 단 SensitiveKeys가 private이라 접근성 확대(internal 등) 선행 필요.
- ⑥ `AuthController` 비밀번호 최소길이 리터럴(8)을 상수로 승격.

### 미착수 목표
원래 6순위 본 목표.

- 컨트롤러 이해 문서 6개(docs/modules/PriceController.md 등) 작성 — 워크플로우 분석 결과 있음, 스타일 확정됨. 아직 안 씀.

### 커밋 상태
- 이번 세션 변경 전부 미커밋. 성격별로 분리 커밋 예정(예: 로그태그 통일 / Logger.Error 보강 / 응답 엔벨로프+프론트). AppConfigManager는 위 로그 결정 후. push는 사용자 명시 확인 후(재배포 트리거).

### 관련 파일 / 검증
- 변경: `Data/AppConfigManager.cs`, `docs/modules/[2026-07-04] 02_AppConfigManager.md`, `Utils/ExchangeRateService.cs`, `Program.cs`, `Controllers/ConfigController.cs`, `Controllers/TestController.cs`, `Controllers/PortfolioController.cs`, `Controllers/HistoryController.cs`, `Frontend/src/pages/Order.jsx`, `Frontend/src/pages/History.jsx`
- 검증: `dotnet build AutoInvest.csproj`(경고0·오류0 확인). 프론트 JSX는 소비처 2곳 직접 대조로 확인(런타임 검증은 미실시 — Sim 모드 권장).

## 정리 / 결론
- 6개 조회 컨트롤러 구조 자체는 건강하며, 문제는 로직이 아니라 "응답·관측 이음매"(500 규격 분열, 예외원문 유출, 성공 응답 엔벨로프 불일치, 로그인 실패 처리·저장 동사 불일치, 동기 블로킹 DB I/O)에 집중됨.
- 이번 세션에서 순수 동작보존 항목(① Logger.Error 보강, 로그 접두사 영문 통일, ⑧ 응답 객체 엔벨로프)을 적용했고 빌드는 경고·오류 0.
- 재개 지점: AppConfigManager `Get()` 매 조회 로그 처리(제거/Debug 강등)를 먼저 결정해야 AppConfigManager를 깔끔히 커밋할 수 있고, 이어서 동작 변경 후보(⑦/⑨)와 남은 순수 후보(③~⑥), 컨트롤러 이해 문서 6개 작성을 진행한다.
- 모든 변경은 미커밋 상태이며 성격별 분리 커밋 후 사용자 확인을 거쳐 push한다.
