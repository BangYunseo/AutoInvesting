## 목적 / 요청

바이브 코딩으로 만들어져 오너(사용자)가 전체 구조를 충분히 이해 못 하는 코드를, **동작을 바꾸지 않으면서
(behavior-preserving)** 이해·정리·문서화한다. 목표는 상품화가 아니라 "오너가 자기 도구로 신뢰·이해하기".
지시서의 Phase 0→4를 순서대로, 각 모듈 종료 시 **요약 보고 + 사용자 확인** 후 다음으로.

## 절대 원칙 (반드시 준수)

1. **동작 보존** — 매매/실행 로직의 의미가 바뀔 수 있는 변경은 **먼저 설명·확인 후에만**. 기본은 구조/문서 정리.
2. **자금/주문·시크릿 코드는 최우선 보수적** — 우선순위 뒤로, 건드릴 땐 별도 확인.
3. **한 번에 하나씩, 작은 커밋** — 모듈 하나 끝날 때마다 성격별로 커밋 + 요약 보고.
4. **문서화 동시 진행**.
5. **모르면 추측 금지, 질문**. (특히 투자 의도·임계값은 코드만으로 알 수 없음)

## 확정 결정 (그대로 따를 것)

- **레거시/죽은 코드 = 삭제** (불필요 코드가 실제 작업을 오염). 단:
  - 죽은 **"코드"** 는 삭제(git 복구 가능). **운영 DB "테이블 물리 DROP"** 은 영구 손실 → **별도 확인**.
  - `TB_MARKET_SNAPSHOT` 은 규칙상 **보존**(수정·삭제 금지).
- **문서 홈 통합 = 방식 (A)**: 워크플로우 동안 `docs/` 에 쌓고, **Phase 4에서 `docs/` 를 정식 홈으로 확정**,
  낡은 `Documents/`(CODE_MAP·API_REFERENCE·ONBOARDING 등)은 대체/폐기해 단일 홈 통합.
- **모듈 이해 문서 형식** — 2파트 골격이되 **간결하게**(아래 "문서 스타일" 참조):
  - Part 1(오너 관점 요약): 한 문장 역할 / 입력→처리→출력·부작용 / 내리는 결정(평문) / 함정 / 만질 곳 / 불명확 항목.
  - Part 2(라인 바이 라인): **정말 복잡한 메서드에만.** 자명하면 생략(엔진처럼 단순하면 최소화). 끝에 "리팩토링 노트".
- **문서 스타일 = 간결 (사용자 피드백 260704)**: 지금까지 문서가 과밀·장황("더럽다")함. 굵게·이모지·중첩 표
  남발 자제, 불필요한 반복 제거. **기존 문서 정리·정확성 더블체크는 Phase 4에서 사용자가 직접** 통독하며 수행
  → 대신 다 고쳐주지 말고 "읽기 쉬운 초안" 제공에 집중.
- **커밋은 진행하되 push는 안 함** (push = Render 재배포 트리거 → 항상 명시적 확인 후).
- **문서에 커밋 해시 기록 안 함** (파일명만). 되짚어 revert할 일 거의 없어 유지비용만 듦. 이력은 `git log`로.
- **테스트 메서드명은 한국어** (`메서드_시나리오_기대결과`). 기존 테스트 관례·러너 리포트 가독성 때문. (프로덕션 코드는 영문 PascalCase 유지 — 테스트에만 국한)
- 설정 파일: `appsettings.local.json` 은 로컬 전용(미필수, Render는 환경변수). `appsettings.json` 은 유지(기본값 시드/문서용, 시크릿 칸 공란).

## 모듈 루프 (각 모듈마다 반복)

이해문서 작성 → (안전망 없으면)스모크테스트 → **리팩토링 제안·사용자 확인** → 적용 → **빌드+테스트 재검증**
→ 문서에 리팩토링 노트 → **성격별 커밋(미push)** → 인계 노트 갱신 → 요약 보고 후 다음 모듈.

> 코드 변경이 없는 모듈(문서만)도 있음(예: DcaSettings, DcaAccumulationEngine). 그때는 "코드 변경 없음"으로 명시.

- 문서: `docs/modules/AppConfigManager.md`, `docs/modules/DcaSettings.md`(DcaSettings는 코드 변경 없음).

### 3순위 — SimBrokerClient (완료, 코드 변경 O)
- 정독 중 **주석-코드 드리프트 발견**: 클래스 주석 "기준가 ±3% 범위에서 생성"은 죽은 코드 제거로 `_rng`가
  사라지며 없어진 동작 → 실제는 기준가 그대로 반환.
- 리팩토링(사용자 승인): ① ±3% 주석 정정 ② 시뮬 기준가·환율을 2026-07 근사 스냅샷으로 갱신
  (SCHD 32.39 / QQQM 293.42 / GLD 378.13 / JEPI 56.71 / SPLG 80.00, 환율 1530). **수량 로직은 가격 무관 → 동작 보존.**
  "실시간 아님·수동 갱신" 주석 명시, 라이브 조회로 바꾸지 않음(결정성 유지).
- 테스트: `Tests/SimBrokerClientTests.cs` 신규 10건. 시장값(가격·환율)은 관계·양수만, 시뮬 내부 계약(폴백 $100·
  예수금·가중평균 산식)은 정확히 검증 → 값 갱신에 안 깨짐.
- 문서: `docs/modules/SimBrokerClient.md`.

### 4순위 — DcaAccumulationEngine (완료, 코드 변경 없음)
- **코드 변경 없음** — 실주문 최고위험 + 이미 Phase 6 원칙(판단 없음·순수/부수효과 분리·예산 상한 경고)에 부합 → 동작 보존.
- 구조: `PlanPurchases`(순수함수, 테스트 7건 이미 존재) / `AccumulateAsync`(환율·현재가 조회→계획→주문→DB기록→메일) 분리.
- **불명확 항목 2건(동작 변경이라 보류)**:
  ① `OrderNo`가 `TradeHistoryDAO.Insert`의 INSERT 컬럼에 없어 **DB 미저장**(반환 목록/메일에만 존재)
     → Data/DBManager 단계에서 `TB_TRADE_HISTORY` 스키마와 함께 판단.
  ② `TradeDate = DateTime.Now`(서버 로컬) vs DcaSettings의 KST 기준 불일치.
- `AccumulateAsync`는 정적 DAO·브로커 I/O 의존이라 단위테스트하려면 DI 리팩토링(=동작 변경) 필요 → 안 함. Sim 모드로 검증.
- 문서: `docs/modules/DcaAccumulationEngine.md`.

## 커밋 시 주의 (실수 방지)

- **`git add -A` 금지** — 다른 세션/사용자가 편집 중인 파일(예: `Data/AppConfigManager.*`)이나 의도치 않은 파일이
  딸려 들어감. **변경한 경로만 명시적으로** add. (과거 untracked 지시서가 딸려와 amend로 제거한 이력 있음.)
- 커밋 메시지: **한국어**, `<type>: <제목>`(scope 금지, 50자 이내), 성격별 분리(docs/test/refactor/remove 등).
- **커밋 본문에 해시 언급 금지**(위 확정 결정). **push는 사용자 명시 확인 후에만.**
- 커밋 전 `security.md` 시크릿/개인정보 체크(값 노출·DB접속정보 금지).
