# 돈 경로 코드 지도 및 수정 목록

## 개요
> 실제 자금이 집행되는 경로(크론 트리거 → 수량 확정 → 주문 송신 → 기록)를 파일·라인 단위로 훑고, 읽는 과정에서 확인된 결함 4건과 각각의 수정 방향을 정리한다. 코드 수정은 주석 갱신까지만 진행했고, 로직 변경은 착수하지 않았다.

## 배경 / 목적
이 저장소는 실전 계좌로 매월 자동 매수를 집행한다. 그런데 돈이 어디서 결정되고 어디서 되돌릴 수 없게 되는지를 코드 수준에서 완전히 파악하지 못한 상태였다. 장애가 나면 로그와 메일만으로 판단해야 하는데, 그 판단 근거가 코드 어디에 있는지 모르면 대응이 늦는다.

그래서 크론 발화부터 주문 송신까지를 순서대로 읽었다. 읽기가 목적이었으므로 로직 변경은 하지 않았고, 이해에 직접 도움이 되는 표현 정리(삼항 연산자를 if/else로 푸는 등)와 사실과 어긋난 주석 교정만 했다.

이 문서는 다음 세션이 같은 자리에서 이어받기 위한 인계 노트다.

## 본문

### 돈이 흐르는 4단계

집행 경로는 아래 네 단계다. 각 단계에서 확정되는 값이 다르다.

| 단계 | 위치 | 확정되는 것 |
|---|---|---|
| 트리거 | `.github/workflows/daily-run.yml` → `OrderController.RunDcaCycle` | 오늘 집행할 것인가 |
| 수량 확정 | `DcaSettings.Load` → `DcaAccumulationEngine.PlanPurchases` | 몇 주를 살 것인가 |
| 송신 | `KisBrokerClient.PlaceOrderAsync` | **되돌릴 수 없음** |
| 기록·대사 | `TradeHistoryDAO` → `DailyExecutionService.ReconcileAsync` | 실제로 샀는가 |

### 1단계 트리거와 게이트

크론은 매일 KST 00:10에 발화한다. 미국 정규장(KST 23:30~06:00) 안이라 장중에 주문이 나간다.

`OrderController.cs`의 진입점은 껍데기다. 백그라운드로 던지고 즉시 202를 반환한다.

```csharp
[HttpPost("dca-run")]
public IActionResult RunDcaCycle([FromQuery] bool force = false)
{
    _ = Task.Run(async () =>
    {
        try
        {
            using var scope = _scopeFactory.CreateScope();
            var dailyService = scope.ServiceProvider.GetRequiredService<DailyExecutionService>();
            await dailyService.RunDcaCycleAsync(force);
        }
        catch (Exception ex)
        {
            Logger.Error($"[Order] 백그라운드 적립식 사이클 실행 실패: {ex.Message}");
        }
    });

    Logger.Info($"[Order] 적립식 매수 사이클을 백그라운드로 시작했습니다 (즉시 202 반환, force={force}).");
    return Accepted(new
    {
        message = force
            ? "적립식 매수 사이클을 강제로 시작했습니다 (당월 중복 여부와 무관). 처리 결과는 서버 로그와 이메일로 확인하세요."
            : "적립식 매수 사이클을 시작했습니다. 처리 결과는 서버 로그와 이메일로 확인하세요."
    });
}
```

HTTP 202는 집행 결과를 보증하지 않는다. 크론의 초록 체크는 "요청이 접수됐다"까지만 뜻한다.

실제 게이트는 `DailyExecutionService.RunDcaCycleAsync`에 있다. 통과해야 할 조건이 순서대로 있다.

`TryReadDb`가 `false`를 돌려주는 경우는 DB 조회 자체가 예외로 터졌을 때뿐이다. 행이 없으면 `true` + `null`이다.

```csharp
public static bool TryReadDb(string key, out string? value)
{
    value = null;
    try
    {
        using (var conn = DBManager.Instance.GetConnection())
        using (var cmd = new NpgsqlCommand(
            "SELECT CONFIG_VALUE FROM TB_APP_CONFIG WHERE CONFIG_KEY=@k", conn))
        {
            cmd.Parameters.AddWithValue("@k", key);
            string? raw = cmd.ExecuteScalar()?.ToString();

            value = CryptoUtil.IsEncrypted(raw ?? string.Empty)
                ? CryptoUtil.DecryptSecret(raw!)
                : raw;

            return true;
        }
    }
    catch (Exception ex)
    {
        Logger.Warn($"[AppConfig] DB 조회 실패 -> 기본 설정 폴백 [{key}]: {ex.Message}");
        return false;
    }
}
```

이 구분이 필요한 이유는 `Get`이 "값 없음"과 "못 읽음"을 같은 기본값으로 뭉개기 때문이다. 마커 판정에 `Get`을 쓰면 DB 장애 하루가 중복 매수가 된다.

`Get`의 폴백 순서는 아래와 같다. 환경변수가 DB보다 우선이므로, 실효값 확인은 Render 환경변수를 봐야 한다.

```csharp
public static string Get(string key, string defaultValue = "")
{
    try
    {
        // 환경변수 (최우선 — 배포 환경 실제 값)
        string? envValue = Environment.GetEnvironmentVariable(key);
        if (!string.IsNullOrEmpty(envValue)) return envValue;

        // DB 테이블(TB_APP_CONFIG) — DB 장애 시 null 반환 -> appsettings.json 기본값 폴백
        string? dbValue = TryGetFromDb(key);
        if (!string.IsNullOrEmpty(dbValue)) return dbValue;

        // appsettings.json (키 매핑: IS_PAPER_TRADING → Trading:IsPaperTrading 등)
        if (_configuration != null)
        {
            string? configValue = ResolveFromConfiguration(key);
            if (!string.IsNullOrEmpty(configValue)) return configValue;
        }

        // 기본값
        return defaultValue;
    }
    catch (Exception ex)
    {
        Logger.Error($"[AppConfig] 조회 실패 [{key}]: {ex.Message}");
        return defaultValue;
    }
}
```

`Get`을 쓰는 자리가 안전한지는 키마다 다르다. 판정 기준은 "기본값이 매수 안 하는 쪽인가"다.

| 위치 | 기본값일 때 | 방향 |
|---|---|---|
| `SessionManager` `IS_PAPER_TRADING` | `"1"` → 모의 | 안전 |
| `SessionManager` `KIS_APP_KEY` | `""` → SimBroker | 안전 |
| `DcaSettings` `DCA_TEMPLATES` | `""` → 템플릿 0개 → 매수 스킵 | 안전 |
| `DailyExecutionService` `DCA_PENDING_SNAPSHOT` | `""` → 대사 불가, 마커 유지 | 안전 |
| `ApiKeyAuthAttribute` `API_ACCESS_KEY` | `""` → 빈 키 가드로 인증 거부 | 안전 |
| `DcaSettings` `DCA_RUN_DAY` | `""` → `0` → 지정일 게이트 무효 | 위험 방향 |
| `DcaSettings` `DCA_MONTH_MAP` | `""` → 월배정 무시, 첫 템플릿 사용 | 위험 방향 |
| `OrderController` 화면 표시 | `""` → "안 샀음"으로 보임 | 사람 오판 유도 |

위험 방향 3건은 현재 도달 불가능하다. fail-closed 가드가 앞에서 먼저 막기 때문이다. 다만 이 안전은 코드가 아니라 호출 순서에 의존한다. 순서가 바뀌면 뚫린다.

### 2단계 수량 확정

`DcaSettings.Load`가 이번 달 템플릿을 골라 종목별 수량과 예산을 돌려준다.

```csharp
public static (Dictionary<string, int> Quantities, decimal BudgetKrw) Load()
{
    var templates = LoadTemplates();
    var monthMap = LoadMonthMap();
    int month = KstNow().Month;

    DcaTemplate? chosen = SelectTemplate(templates, monthMap, month);

    if (chosen == null)
    {
        Logger.Warn($"[DcaSettings] {month}월에 배정된 템플릿이 없어 이번 사이클 매수를 스킵합니다.");
        return (new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase), 0m);
    }

    var qtys = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase);
    foreach (var kv in chosen.Quantities)
        if (kv.Value > 0) qtys[kv.Key] = kv.Value;

    decimal budget = chosen.BudgetKrw > 0 ? chosen.BudgetKrw : DefaultBudgetKrw;
    Logger.Info($"[DcaSettings] {month}월 적용 템플릿='{chosen.Name}' (종목 {qtys.Count}개, 예산 {budget:N0}원)");
    return (qtys, budget);
}
```

`SelectTemplate`은 순수 함수다. 외부 I/O도 현재 시각 의존도 없다. 출구가 4개다.

```csharp
public static DcaTemplate? SelectTemplate(
    IReadOnlyList<DcaTemplate> templates,
    IReadOnlyDictionary<int, string> monthMap,
    int month)
{
    if (templates == null || templates.Count == 0) return null;

    if (monthMap != null && monthMap.TryGetValue(month, out var tid) && !string.IsNullOrWhiteSpace(tid))
    {
        return templates.FirstOrDefault(t => t.Id == tid);
    }

    if (monthMap == null || monthMap.Count == 0)
    {
        return templates.FirstOrDefault();
    }

    return null;
}
```

출구 3과 4의 차이가 크다. 월 배정이 통째로 비면 첫 템플릿으로 매달 사고, 한 달이라도 배정이 있으면 배정 없는 달은 전부 스킵한다. 3월 하나만 배정해두면 나머지 11개월이 "안 삼"으로 바뀐다.

배정된 Id의 템플릿이 삭제된 경우도 `FirstOrDefault`가 `null`을 돌려주어 그 달을 스킵한다.

수량이 확정되는 곳은 `PlanPurchases`다.

```csharp
public static Dictionary<string, int> PlanPurchases(
    IReadOnlyDictionary<string, int> quantities,
    decimal exchangeRate,
    IReadOnlyDictionary<string, decimal> priceUsd,
    out decimal totalCostKrw)
{
    var plan = new Dictionary<string, int>();
    totalCostKrw = 0m;

    foreach (var kv in quantities)
    {
        int qty = kv.Value;
        if (qty <= 0) continue;
        if (!priceUsd.TryGetValue(kv.Key, out decimal px) || px <= 0) continue;

        plan[kv.Key] = qty;
        totalCostKrw += qty * px * exchangeRate;
    }

    return plan;
}
```

수량을 줄이는 코드는 없다. 사람이 저장한 정수가 그대로 주문 수량이 된다. 예산은 경고만 낸다.

`totalCostKrw`는 `decimal`이라 누적 오차가 없지만, 값 자체는 추정치다. 지정가라 미체결이면 실제 지출은 0원이고, 환율은 주문 시각과 실제 환전 시점이 다르며, 수수료와 제세금이 빠져 있다. 소비자는 예산 경고 판정과 메일 표시 두 곳뿐이고 수량 결정에는 관여하지 않는다.

`AccumulateAsync`가 부수효과를 담당한다.

```csharp
public async Task<DcaCycleResult> AccumulateAsync(
    Dictionary<string, int> quantities,
    decimal budgetKrw)
{
    var result = new DcaCycleResult();

    if (quantities == null || quantities.Count == 0)
    {
        Logger.Warn("[DCA] 매수 수량이 없어 매수를 건너뜁니다.");
        return result;
    }

    decimal exchangeRate = await _broker.GetExchangeRateAsync();
    if (exchangeRate <= 0)
    {
        Logger.Error("[DCA] 환율 조회에 실패해 매수를 건너뜁니다.");
        return result;
    }

    // 현재가
    var priceUsd = new Dictionary<string, decimal>();
    foreach (var ticker in quantities.Keys)
    {
        decimal px = await _broker.GetCurrentPriceAsync(ticker);
        if (px <= 0)
        {
            Logger.Warn($"[DCA] {ticker} 조회 실패 : {ticker}는 매수를 건너뜁니다.");
            continue;
        }
        priceUsd[ticker] = px;
    }

    if (priceUsd.Count == 0)
    {
        Logger.Error("[DCA] 유효한 현재가가 있는 종목이 없어 매수를 건너뜁니다.");
        return result;
    }

    var plan = PlanPurchases(quantities, exchangeRate, priceUsd, out decimal totalCostKrw);

    result.TotalCostKrw = totalCostKrw;
    result.ExchangeRate = exchangeRate;

    Logger.Info($"[DCA] ===== 매수 진행 (예산 {budgetKrw:N0}원, 환율 {exchangeRate:N0}, 종목 {plan.Count}개) =====");

    if (budgetKrw > 0 && totalCostKrw > budgetKrw)
    {
        string msg = $"총 매수금액 {totalCostKrw:N0}원이 예산 {budgetKrw:N0}원을 초과합니다.\n" +
            $"(초과 {totalCostKrw - budgetKrw:N0}원)\n" +
            "매수가 실패할 수 있습니다. 진행하시겠습니까?";
        Logger.Warn($"[DCA] ⚠ {msg}");
        result.BudgetWarning = msg;
    }

    foreach (var (ticker, qty) in plan)
    {
        decimal price = priceUsd[ticker];
        try
        {
            var orderNo = await _broker.PlaceBuyOrderAsync(ticker, qty, price);

            var trade = new TradeHistoryDto
            {
                TradeDate = DateTime.Now,
                Ticker = ticker,
                OrderType = "BUY",
                Qty = qty,
                Price = price,
                Status = "PENDING",
                OrderNo = orderNo
            };
            TradeHistoryDAO.Insert(trade);

            result.Accepted.Add(trade);

            if (string.IsNullOrEmpty(orderNo))
                Logger.Warn($"[DCA] 주문 접수: {ticker} {qty}주 @ ${price} — 주문번호 미수신, 체결 대사 불가");
            else
                Logger.Info($"[DCA] 주문 접수: {ticker} {qty}주 @ ${price} (주문번호: {orderNo})");
        }
        catch (Exception ex)
        {
            Logger.Error($"[DCA] {ticker} 매수 실패: {ex.Message}");
            result.Failures.Add(new DcaBuyFailure { Ticker = ticker, Qty = qty, Error = ex.Message });
        }
    }

    var perTicker = plan.Select(kv => $"{kv.Key} {kv.Value}주");
    Logger.Info($"[DCA] === 매수 완료: 총 {plan.Values.Sum()}주 ({string.Join(", ", perTicker)}), " +
        $"총 매수금액 {totalCostKrw:N0}원 ===");

    return result;
}
```

`BudgetWarning`의 소비자는 `DailyExecutionService`의 메일 본문 한 곳뿐이다. 프론트엔드에서 읽는 코드는 없다. 크론 경로에는 사람이 없으므로 이 자리에서는 판단하지 않고 기록만 하는 것이 맞다. 확인이 필요한 경우는 화면 경로(`Order.jsx`의 확인 모달, `DcaConfig.jsx`의 금액 표시)에서 처리한다.

### 3단계 송신

실집행 여부는 `SessionManager.GetClient`에서 갈린다. 이번 세션에서 삼항 연산자를 if/else로 풀고 모드 로그를 추가했다.

```csharp
public IBrokerClient GetClient()
{
    if (_client != null) return _client;

    // 0 실전투자, 1 모의투자
    bool isPaperTrading;
    if (AppConfigManager.Get("IS_PAPER_TRADING", "1") == "0")
    {
        isPaperTrading = false;
        Logger.Info("[Session] 거래 모드: 실전투자");
    }
    else
    {
        isPaperTrading = true;
        Logger.Info("[Session] 거래 모드: 모의투자");
    }

    // KIS API 키 미확인 시 시뮬레이션 동작(실거래 불가)
    var kisAppKey = AppConfigManager.Get("KIS_APP_KEY", "");
    if (string.IsNullOrEmpty(kisAppKey))
    {
        Logger.Info("[Session] KIS API 키가 없습니다. 시뮬레이션 모드로 동작합니다.");
        _client = new SimBrokerClient();
        return _client;
    }

    var appSecret = AppConfigManager.Get("KIS_APP_SECRET", "");         // 자격증명
    var accountNo = AppConfigManager.Get("KIS_ACCOUNT_NO", "");         // 계좌
    var accountProd = AppConfigManager.Get("KIS_ACCOUNT_PROD", "01");   // 계좌상품코드

    string baseUrl;
    if (isPaperTrading) baseUrl = "https://openapivts.koreainvestment.com:29443";
    else baseUrl = "https://openapi.koreainvestment.com:9443";

    Logger.Info($"[Session] KIS API 클라이언트 생성 ({(isPaperTrading ? "모의" : "실전")} 모드)");
    _client = new KisBrokerClient(baseUrl, kisAppKey, appSecret, accountNo, accountProd, isPaperTrading);
    return _client;
}
```

모드가 3개다. 시뮬레이션은 네트워크가 나가지 않고, 모의투자는 KIS 서버에 실제로 접속하되 계좌가 가짜다. 실전만 진짜 돈이다.

실집행 조건은 `KIS_APP_KEY`가 있고 동시에 `IS_PAPER_TRADING`이 정확히 문자열 `"0"`일 때다. 앱키 검사가 먼저이므로, 실전으로 켜두었어도 키가 비면 시뮬레이션으로 떨어진다.

`_client`가 캐시되므로 환경변수를 바꿔도 재배포 전까지 반영되지 않는다.

주문 송신은 `KisBrokerClient.PlaceOrderAsync`다.

```csharp
private async Task<string> PlaceOrderAsync(string ticker, int qty, decimal price, bool isBuy)
{
    await _tokenManager.EnsureValidTokenAsync();

    // 거래소 코드로 주문
    string ovrsExcgCd = await ResolveOrderExchangeAsync(ticker);

    await Task.Delay(400);

    // 미국 매수 모의 : 실전 / 미국 매도 모의 : 실전 구분
    string trId = isBuy
        ? (_isPaperTrading ? "VTTT1002U" : "TTTT1002U")
        : (_isPaperTrading ? "VTTT1006U" : "TTTT1006U");

    string path = "/uapi/overseas-stock/v1/trading/order";

    var body = new
    {
        CANO = _accountNoPrefix,
        ACNT_PRDT_CD = _accountNoSuffix,
        OVRS_EXCG_CD = ovrsExcgCd,
        PDNO = ticker,
        ORD_QTY = qty.ToString(),
        OVRS_ORD_UNPR = price.ToString("0.00", CultureInfo.InvariantCulture),
        ORD_SVR_DVSN_CD = "0",
        ORD_DVSN = "00"
    };

    var response = await SendWithRetryAsync(() =>
    {
        var request = CreateRequest(HttpMethod.Post, path, trId);
        request.Content = new StringContent(JsonSerializer.Serialize(body), Encoding.UTF8, "application/json");
        return request;
    });

    response.EnsureSuccessStatusCode();

    var responseString = await response.Content.ReadAsStringAsync();
    var json = JsonSerializer.Deserialize<JsonElement>(responseString);

    string rtCd = json.GetProperty("rt_cd").GetString() ?? "";
    string msg = json.GetProperty("msg1").GetString() ?? "";

    if (rtCd != "0")
    {
        throw new Exception($"주문 에러: {msg}");
    }
```

URL은 매수·매도·실전·모의가 모두 같다. 구분은 헤더의 `tr_id`가 한다. `_isPaperTrading` 하나가 `baseUrl`과 `tr_id`를 동시에 결정하므로 접속망과 거래ID가 어긋나는 조합은 만들어지지 않는다.

`ORD_DVSN = "00"`은 지정가다. `OVRS_ORD_UNPR`에 조회한 현재가를 그대로 넣으므로 버퍼가 없다. 주문 사이에 주가가 오르면 미체결로 끝난다.

검사가 두 단계인 이유는 KIS가 업무 오류를 HTTP 200 + `rt_cd`≠`"0"`으로 돌려주기 때문이다. `EnsureSuccessStatusCode`만으로는 잔고 부족을 성공으로 읽는다.

거래소 코드는 종목마다 다르고, 런타임에 찾아낸다.

```csharp
private async Task<string> ResolveOrderExchangeAsync(string ticker)
{
    if (!_tickerPriceExchange.TryGetValue(ticker, out var excd))
    {
        // 거래소가 확인되지 않은 경우 현재가 조회
        await GetCurrentPriceAsync(ticker);
        _tickerPriceExchange.TryGetValue(ticker, out excd);
    }

    if (!string.IsNullOrEmpty(excd) && PriceToOrderExchange.TryGetValue(excd, out var orderExcg))
    {
        return orderExcg;
    }

    Logger.Warn($"[KisBroker] {ticker} 거래소 미확인 : 기본값 NASD 적용");
    return "NASD";
}
```

시세 API는 3글자(`NAS`/`NYS`/`AMS`), 주문 API는 4글자(`NASD`/`NYSE`/`AMEX`)를 쓴다. `GetCurrentPriceAsync`가 세 거래소를 순회해 가격이 잡히는 곳을 찾아 `_tickerPriceExchange`에 캐시하고, 주문 시 그것을 변환한다. 캐시가 비면 현재가를 다시 조회하고, 그래도 실패하면 `NASD`로 폴백한다.

재시도 정책은 클래스 상단에 정의돼 있고 모든 호출이 공유한다.

```csharp
private static readonly HttpClient _httpClient = new HttpClient();
private static readonly AsyncRetryPolicy<HttpResponseMessage> _retryPolicy = Policy<HttpResponseMessage>
    .Handle<HttpRequestException>()
    .Or<TaskCanceledException>()
    .OrResult(r => !r.IsSuccessStatusCode && ((int)r.StatusCode >= 500 || (int)r.StatusCode == 429 || (int)r.StatusCode == 408))
    .WaitAndRetryAsync(10, retryAttempt => TimeSpan.FromSeconds(Math.Min(Math.Pow(2, retryAttempt), 30)),
        (outcome, timeSpan, retryCount, context) =>
        {
            string reason = outcome.Exception != null ? outcome.Exception.Message : $"상태코드: {outcome.Result?.StatusCode}";
            Logger.Warn($"[KisBroker] API 호출 실패 ({reason}). {retryCount}/10회 재시도 대기: {timeSpan.TotalSeconds}초");
        });
```

```csharp
private async Task<HttpResponseMessage> SendWithRetryAsync(Func<HttpRequestMessage> requestFactory)
{
    return await _retryPolicy.ExecuteAsync(async () =>
    {
        var request = requestFactory();
        return await _httpClient.SendAsync(request);
    });
}
```

대기 시간은 2·4·8·16초 후 30초로 고정된다. 최악의 경우 210초 동안 같은 요청을 11회 보낸다.

```csharp
private static void SavePendingSnapshot(string month, Dictionary<string, int> beforeQty, DcaCycleResult result)
{
    if (result.Accepted.Count == 0) return;

    var snapshot = new PendingSnapshot
    {
        Month = month,
        Before = beforeQty,
        Ordered = result.Accepted
            .GroupBy(f => f.Ticker.ToUpper())
            .Select(g => new PendingOrder
            {
                Ticker = g.Key,
                Qty = g.Sum(x => x.Qty),
                OrderNo = g.Select(x => x.OrderNo).FirstOrDefault(o => !string.IsNullOrEmpty(o)) ?? string.Empty
            })
            .ToList()
    };

    if (!AppConfigManager.Set(PendingSnapshotKey, JsonSerializer.Serialize(snapshot)))
        Logger.Error($"[DcaCycle] {PendingSnapshotKey} 저장 실패 — 이번 건은 체결 대사 불가");
}
```

체결 판정은 보유 수량 차이로 한다. `ODNO`는 판정에 쓰이지 않고, 결과를 DB에 기록할 때의 조건절에서만 쓰인다.

```csharp
var nowQty = (await client.GetHoldingsAsync())
    .GroupBy(h => h.Ticker, StringComparer.OrdinalIgnoreCase)
    .ToDictionary(g => g.Key.ToUpper(), g => g.Sum(h => h.Qty), StringComparer.OrdinalIgnoreCase);

int totalOrdered = 0, totalFilled = 0;
bool anySold = false;
var lines = new List<string>();

foreach (var o in snap.Ordered)
{
    snap.Before.TryGetValue(o.Ticker, out int before);
    nowQty.TryGetValue(o.Ticker, out int now);

    int delta = now - before;
    if (delta < 0) anySold = true;

    int filled = Math.Max(0, Math.Min(delta, o.Qty));
    totalOrdered += o.Qty;
    totalFilled += filled;

    string status = filled >= o.Qty ? "FILLED" : filled > 0 ? "PARTIAL" : "FAILED";
    TradeHistoryDAO.UpdateStatusByOrderNo(o.OrderNo, status);

    lines.Add($"{o.Ticker}: 주문 {o.Qty}주 · 체결 {filled}주 (보유 {before}→{now})");
    Logger.Info($"[Reconcile] {o.Ticker} 주문 {o.Qty}주 → 체결 {filled}주 (보유 {before}→{now}), 상태 {status}");
}
```

```csharp
public static int UpdateStatusByOrderNo(string orderNo, string status)
{
    if (string.IsNullOrWhiteSpace(orderNo)) return 0;

    using (var conn = DBManager.Instance.GetConnection())
    using (var cmd = new NpgsqlCommand(
        "UPDATE TB_TRADE_HISTORY SET STATUS=@s WHERE ORDER_NO=@o", conn))

    }
}
```

### 확인된 결함 4건

#### 결함 1 주문 재시도에 멱등키가 없다

Polly 정책이 조회와 주문에 동일하게 적용된다. 주문 body에는 클라이언트가 만든 고유 식별자가 없어서, KIS가 접수한 뒤 응답만 유실되면 같은 매수가 재전송된다. `HttpClient`에 `Timeout` 설정이 없어 기본 100초가 적용되므로, KIS가 느릴 때 타임아웃으로 재시도가 걸릴 수 있다. 최대 11회다.

수정 방향은 주문 경로를 재시도 정책에서 분리하는 것이다. 조회는 재시도가 맞으므로 정책 자체를 바꾸면 안 된다. 멱등키를 붙이려면 KIS가 개인 계정에서 받아주는 필드가 있는지 먼저 확인해야 한다(`gt_uid`는 법인 전용으로 문서에 표기돼 있다).

#### 결함 2 체결 상태 갱신 키가 ODNO다

`ODNO`를 못 받으면 해당 행이 영구히 `PENDING`으로 남는다. 더 큰 문제는 스냅샷이 티커로 `GroupBy`되면서 같은 종목의 여러 주문이 1건으로 뭉개지는 것이다. 한 사이클에 같은 종목을 두 번 주문하면(자동 + 수동, `force` 재실행) DB 행은 2개인데 스냅샷은 1개라 나머지 행이 갱신되지 않는다.

수정 방향은 갱신 키를 진짜 PK인 `TB_TRADE_HISTORY.TRADE_ID`로 바꾸는 것이다.

1. `TradeHistoryDAO.Insert`를 `void`에서 `int`로 바꾸고 `RETURNING TRADE_ID` + `ExecuteScalar` 사용
2. `DcaAccumulationEngine`에서 반환된 id를 `trade.TradeId`에 담기(DTO에 필드는 이미 있다)
3. `PendingOrder`의 `OrderNo` 단일 값을 `TradeIds` 목록으로 교체하고 `GroupBy`로 뭉개지 않기
4. `ReconcileAsync`의 `UpdateStatusByOrderNo`를 `TradeId` 기반 갱신으로 교체

`DCA_PENDING_SNAPSHOT`의 JSON 구조가 바뀌므로, 이번 달 스냅샷이 남아 있는 상태로 배포하면 구형식을 읽지 못한다. 구형식 폴백을 넣거나 배포 시점을 조정해야 한다.

#### 결함 3 일부 종목 현재가 실패가 조용히 누락된다

전 종목이 실패하면 매수를 건너뛰고 마커를 남기지 않아 다음 날 자동 재시도된다. 그러나 일부만 실패하면 나머지가 접수되고 마커가 찍혀 그 달 재시도가 막힌다. 빠진 종목은 `plan`에 없으므로 `Failures`에도 들어가지 않아 메일에 나타나지 않는다. 남는 흔적은 서버 로그의 `Warn` 한 줄뿐이다.

수정 방향은 두 가지 중 하나다. 조회 실패 종목을 `result.Failures`에 담아 메일에 노출시키거나, 조회 실패가 하나라도 있으면 그 사이클 전체를 스킵하는 것이다. 후자는 안전하지만 한 종목 때문에 전체가 밀리므로 판단이 필요하다.

#### 결함 4 거래소 폴백이 실패 사유를 가린다

거래소를 확인하지 못하면 `NASD`로 주문을 시도한다. AMEX 종목이면 KIS가 "해당종목정보가 없습니다"로 거부하므로 돈은 나가지 않는다. 다만 메일에 표시되는 사유가 실제 원인(거래소 조회 실패)과 다르다. 또한 나스닥 종목이면 폴백이 우연히 맞아, 종목에 따라 재현이 달라진다.

수정 방향은 거래소를 확인하지 못하면 주문을 시도하지 않고 명확한 사유로 실패시키는 것이다.

### 이번 세션에서 실제로 변경한 것

로직 변경은 `SessionManager` 한 곳뿐이고 동작은 동일하다. 나머지는 주석과 문구다.

`Core/SessionManager.cs`에서 삼항 연산자와 이중부정을 if/else로 풀고 거래 모드 로그를 추가했다. 지역변수 초기값을 제거해 미대입 경로를 컴파일러가 잡도록 했다.

`Core/DcaSettings.cs`에서 템플릿 필터링을 LINQ에서 `foreach`로 바꿨다. 동작 동일하다.

`Core/DcaAccumulationEngine.cs`에 `totalCostKrw`가 추정치라는 점과 실제 비용이 필요할 때의 방향을 `ponytail:` 주석으로 남겼다.

`Core/KisBrokerClient.cs`의 ODNO 관련 주석을 교정했다. "체결 대사의 유일한 매칭 키"라는 서술이 실제 코드와 어긋나 있었다. 실제 영향과 결함 2의 수정 방향을 함께 적었다.

`Core/DailyExecutionService.cs`와 여러 파일에서 주석과 로그 문구를 정리했다.

## 정리 / 결론

되돌릴 수 없는 지점은 `KisBrokerClient.PlaceOrderAsync`의 `SendWithRetryAsync` 호출이다. 그 앞은 전부 되돌릴 수 있고, 뒤는 사람이 시장에서 되파는 것 외에 방법이 없다. `rt_cd` 판정은 그 뒤에 있으므로, 예외가 났다고 주문이 나가지 않았다는 보장은 없다.

수량은 사람이 저장한 정수가 그대로 간다. 예산은 수량을 줄이지 않고, 예수금 검증은 매수 경로 어디에도 없다. 실질적인 상한은 KIS의 거부뿐이다.

우선순위는 결함 1이 가장 높다. 중복 매수는 실제 자금 손실로 직결되고, 나머지 셋은 기록 부정확이나 적립 누락이다.

착수 순서는 결함 2를 먼저 하는 것이 낫다. 결함 1을 고치려면 주문 경로를 분리해야 하는데, 그때 `TRADE_ID` 기반 기록이 이미 있으면 재시도 여부를 행 단위로 판단할 수 있다.

다음 세션은 `ReconcileAsync` 전체를 읽는 것부터 시작한다. 이번에 판정부만 확인했고 스냅샷 로드와 예외 처리는 보지 않았다.
