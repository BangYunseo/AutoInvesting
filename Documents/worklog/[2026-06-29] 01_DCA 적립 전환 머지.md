# DCA 적립 전환 브랜치 main 머지 및 워크플로우·규칙 정비

## 개요
> 주말 별도 브랜치에서 개발한 DCA 적립 전환(판단 레이어 제거)을 main에 rebase 반영·배포하고, 브랜치 라이프사이클 규칙과 작업 보고서(worklog) 규칙을 명문화한 작업이다.

## 배경 / 목적
주말에 별도 브랜치(`feature/phase5-feedback-loop`)에서 개발한 **DCA 적립 전환**(판단 레이어 제거)을 main에 반영하고 Render에 배포한다. 더불어 브랜치 라이프사이클 규칙과 작업 보고서(worklog) 규칙을 명문화한다.

## 본문
### 계획
1. 주말 브랜치 내용 확인 → main과의 분기 상태 점검
2. 안전한 방식으로 재조정(rebase) → 빌드 검증
3. (사용자 결정) main ff 머지 → push(재배포) → 브랜치 삭제
4. 규칙 문서화: 브랜치 라이프사이클 / worklog

### 진행 및 결정
- 브랜치가 **현재 main보다 50커밋 뒤(분기점 `2f3034e`)** 에서 출발 → fast-forward 불가, 충돌·유실 위험 확인.
- 결정: **DCA 4커밋을 main 위로 rebase**. 충돌 해소 정책 = "판단 레이어 삭제는 DCA 우선 / 살아남는 인프라(KIS·보안·Resend)는 main 보존". `appsettings.json`·`TestController`는 양쪽 병합.
- rebase 후 빌드에서 main이 분기 뒤 추가한 `SimController`·`SimTrainingDataGenerator`가 삭제된 AI 레이어를 참조 → DCA 취지대로 함께 삭제 후 빌드 통과(오류 0).
- 사용자가 "모의투자 계좌라 매일 적립 무방" 확인 → 일일 크론 유지. 단 실거래 전환 시 과매수 위험을 문서/주석/룰에 남김.
- 일일 크론이 옛 엔드포인트 `/api/order/daily-run` 호출(현재는 `dca-run`) → 워크플로우 수정.

### 남은 정리 항목
- `/api/test/health` 진단 엔드포인트 유실(삭제된 AI 분석기 참조) → DCA용으로 재작성 필요.
- stale 문서: `Documents/API_REFERENCE.md`, `API_REFERENCE_TABLE.md`, `CODE_MAP.md`가 삭제된 컨트롤러(Strategy·Backtest·Monitoring·SellPlan·Sim) 기술. 일부 문서가 이메일 스택을 "MailKit"로 표기(실제는 Resend).
- orphan DTO `Data/DTO/AdaptiveThresholdStatusDto.cs` 등 판단 잔재(빌드 무해) 정리.
- **실거래 전환 시(MUST)**: 크론을 매월 1일(`40 14 1 * *`)로 변경 + 엔진에 당월 멱등 가드 추가 (상세: `DEVELOPMENT.md`).

## 정리 / 결론
- DCA 적립 전환 4커밋을 main 위로 rebase해 판단 레이어 삭제를 우선 반영하고, 인프라(KIS·보안·Resend)는 main 기준을 보존했다.
- rebase 후 AI 레이어를 참조하던 `SimController`·`SimTrainingDataGenerator`를 제거해 빌드 오류 0으로 main ff 머지·배포를 완료했다.
- 일일 크론은 모의투자 계좌 기준으로 유지하되, 워크플로우의 호출 엔드포인트를 `dca-run`으로 교정하고 실거래 전환 시 과매수 방지 가드를 문서·주석·룰에 남겼다.
- 브랜치 라이프사이클 규칙과 worklog 규칙을 명문화하고 `Documents/worklog/` 체계를 신설했다.
- 후속 정리 항목(`/api/test/health` 재작성, stale 문서 정정, orphan DTO 정리, 실거래 전환 가드)이 남아 있다.
