# 코드베이스 분석 & 점진적 리팩토링 인계 노트

## 개요
> 바이브 코딩으로 만들어져 오너가 전체 구조를 충분히 이해하지 못하는 AutoInvesting 코드베이스를, 동작을 바꾸지 않으면서(behavior-preserving) 이해·정리·문서화하는 점진적 리팩토링 작업의 인계 노트다. `/clear` 등으로 세션이 초기화돼도 이 노트만 읽으면 동일한 방식으로 버그 없이 이어서 작업할 수 있게 하는 것이 목적이다.

## 배경 / 목적
바이브 코딩으로 만들어져 오너(사용자)가 전체 구조를 충분히 이해 못 하는 코드를, 동작을 바꾸지 않으면서(behavior-preserving) 이해·정리·문서화한다. 목표는 상품화가 아니라 "오너가 자기 도구로 신뢰·이해하기"다. 지시서의 Phase 0→4를 순서대로, 각 모듈 종료 시 요약 보고 + 사용자 확인 후 다음으로 진행한다.

이 노트는 진행 중 상태를 담는 살아있는 인계 노트이며, 새 세션이 열리면 아래 "재개 방법"부터 읽어 워크플로우를 파악한 뒤 이어서 작업한다.

## 본문
### 재개 방법
새 세션이 가장 먼저 할 일을 순서대로 정리한다.

1. 이 인계 노트 전체를 읽는다 = 워크플로우 SSOT. (원래의 작업지시서 `AUTOINVESTING_ANALYSIS_REFACTOR_PLAN.md`는 내용이 `Documents/[2026-07-04] 01_프로젝트 개요.md`~`Documents/[2026-07-04] 03_모듈 우선순위.md`와 이 노트로 모두 흡수되어 260704 삭제함 — 더 이상 없음.)
2. `Documents/[2026-07-04] 01_프로젝트 개요.md` → `Documents/[2026-07-04] 02_아키텍처.md` → `Documents/[2026-07-04] 03_모듈 우선순위.md` 순서로 전체 그림·진행 순서 파악.
3. `Documents/modules/`의 완료된 모듈 노트 읽기 (아래 "진행 순서"의 완료 목록).
4. 이 노트의 "절대 원칙" → "확정 결정" → "모듈 루프" → "다음 단계"를 지키며 이어서 진행.
5. `CLAUDE.md`(및 `.agents/rules/*`)의 프로젝트 규칙도 적용됨 — 특히 `worklog.md`, `git-conventions.md`, `security.md`.

### 절대 원칙
반드시 준수할 원칙이다.

1. 동작 보존 — 매매/실행 로직의 의미가 바뀔 수 있는 변경은 먼저 설명·확인 후에만. 기본은 구조/문서 정리.
2. 자금/주문·시크릿 코드는 최우선 보수적 — 우선순위 뒤로, 건드릴 땐 별도 확인.
3. 한 번에 하나씩, 작은 커밋 — 모듈 하나 끝날 때마다 성격별로 커밋 + 요약 보고.
4. 문서화 동시 진행.
5. 모르면 추측 금지, 질문. (특히 투자 의도·임계값은 코드만으로 알 수 없음)

### 확정 결정
그대로 따를 결정 사항이다.

- 레거시/죽은 코드 = 삭제 (불필요 코드가 실제 작업을 오염). 단:
  - 죽은 "코드"는 삭제(git 복구 가능). 운영 DB "테이블 물리 DROP"은 영구 손실 → 별도 확인.
  - `TB_MARKET_SNAPSHOT`은 규칙상 보존(수정·삭제 금지).
- 문서 홈 통합 = ~~방식 (A): docs/를 정식 홈으로 확정~~ → **2026-07-23 방향 반전: 정식 문서 홈을 `Documents/`로 확정**(라이브 규칙이 이미 `Documents/`를 가리켜 파급 최소). `docs/` 산출물을 `Documents/`로 이관하고 낡은 문서(CODE_MAP·API_REFERENCE 등)는 대체·폐기.
- 모듈 이해 문서 형식 — 2파트 골격이되 간결하게(아래 "문서 스타일" 참조):
  - Part 1(오너 관점 요약): 한 문장 역할 / 입력→처리→출력·부작용 / 내리는 결정(평문) / 함정 / 만질 곳 / 불명확 항목.
  - Part 2(라인 바이 라인): 정말 복잡한 메서드에만. 자명하면 생략(엔진처럼 단순하면 최소화). 끝에 "리팩토링 노트".
- 문서 스타일 = 간결 (사용자 피드백 260704): 지금까지 문서가 과밀·장황("더럽다")함. 굵게·이모지·중첩 표 남발 자제, 불필요한 반복 제거. 기존 문서 정리·정확성 더블체크는 Phase 4에서 사용자가 직접 통독하며 수행 → 대신 다 고쳐주지 말고 "읽기 쉬운 초안" 제공에 집중.
- 커밋은 진행하되 push는 안 함 (push = Render 재배포 트리거 → 항상 명시적 확인 후).
- 문서에 커밋 해시 기록 안 함 (파일명만). 되짚어 revert할 일 거의 없어 유지비용만 듦. 이력은 `git log`로.
- 테스트 메서드명은 한국어 (`메서드_시나리오_기대결과`). 기존 테스트 관례·러너 리포트 가독성 때문. (프로덕션 코드는 영문 PascalCase 유지 — 테스트에만 국한)
- 설정 파일: `appsettings.local.json`은 로컬 전용(미필수, Render는 환경변수). `appsettings.json`은 유지(기본값 시드/문서용, 시크릿 칸 공란).

### 모듈 루프
각 모듈마다 다음을 반복한다.

이해문서 작성 → (안전망 없으면) 스모크테스트 → 리팩토링 제안·사용자 확인 → 적용 → 빌드+테스트 재검증 → 문서에 리팩토링 노트 → 성격별 커밋(미push) → 인계 노트 갱신 → 요약 보고 후 다음 모듈.

코드 변경이 없는 모듈(문서만)도 있음(예: DcaSettings, DcaAccumulationEngine). 그때는 "코드 변경 없음"으로 명시한다.

### 커밋 시 주의
실수 방지 사항이다.

- `git add -A` 금지 — 다른 세션/사용자가 편집 중인 파일(예: `Data/AppConfigManager.*`)이나 의도치 않은 파일이 딸려 들어감. 변경한 경로만 명시적으로 add. (과거 untracked 지시서가 딸려와 amend로 제거한 이력 있음.)
- 커밋 메시지: 한국어, `<type>: <제목>`(scope 금지, 50자 이내), 성격별 분리(docs/test/refactor/remove 등).
- 커밋 본문에 해시 언급 금지(위 확정 결정). push는 사용자 명시 확인 후에만.
- 커밋 전 `security.md` 시크릿/개인정보 체크(값 노출·DB접속정보 금지).

## 정리 / 결론
- 진행 순서 1~5순위(죽은 코드 제거 / AppConfigManager+DcaSettings / SimBrokerClient / DcaAccumulationEngine / DailyExecutionService)는 완료했다.
- 다음은 6순위 조회 컨트롤러(`Price → History → Portfolio → Config → Dca → Auth`)이며, 저위험 읽기 계열이라 코드 변경은 대체로 없을 전망이다.
- 죽은 테이블 스키마 정리와 `OrderNo`/`TradeDate` 불명확 항목은 Data(DBManager) 단계에서, 낡은 `Documents/` 통합·정확성 더블체크는 Phase 4에서 사용자가 직접 처리한다.
- 모든 커밋은 미push 상태이며, push는 Render 재배포 트리거이므로 사용자 명시 확인 후에만 진행한다.
