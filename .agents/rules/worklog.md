# 작업 보고서(Worklog) 규칙

기능 단위 작업을 할 때는 **인계(handoff)용 보고서**를 남긴다.
목적은 **세션이 종료·만료돼도, 그 보고서만 보면 "무슨 작업을 왜 했고, 어디까지 됐고, 다음에 뭘 할지"를 다시 파악**하는 것이다.
(전체 개발 이력 = `Documents/reference/DEVELOPMENT.md`. worklog는 **진행 중 상태를 담는 살아있는 인계 노트**다.)

## 형식 · 파일명 (MUST)

- 폴더: **`Documents/worklog/`**
- **형식·파일명은 `/create-md` 스킬의 표준을 그대로 따른다.**
  - 파일명: **`[YYYY-MM-DD] NN_제목.md`** (날짜 = 작성일, `NN` = 두 자리 순번 `01`부터, 같은 날짜 내 순서대로)
  - 문서 양식: YAML 프론트매터(`title` / `date` / `company` / `tags` / `status`) → 단일 H1(제목) → `## 개요` → `## 배경 / 목적` → `## 본문` → `## 정리 / 결론` → `## 참고`
  - `## 개요`는 이름 고정. 헤딩은 H2→H3→H4 순서(H4가 최하위). 코드블록은 언어 명시 + **전체 그대로(핵심만 발췌·`// ...` 축약 금지)**.
  - `company`는 `[개인]`, `tags`는 내용 요약 태그만(회사명 금지), `status`는 생성 시 `draft`(이후 `in-progress`/`done`으로 갱신). **검토 끝에 채택하지 않은 문서는 `rejected`로 바꾼다** — `draft`로 남기면 다음 세션이 미완 계획으로 읽고 다시 착수한다.
- 템플릿: `Documents/worklog/_TEMPLATE.md`
- worklog 성격상 본문은 **"무엇을 왜 했고 / 무엇이 남았는지(다음 단계)"** 가 드러나게 쓴다(핸드오프 목적).

## 적용 범위 (MUST)

- **기능 단위 작업에만** 작성한다 — "동작하는 기능" 개발, 여러 파일에 걸친 변경, 아키텍처/머지/마이그레이션 등.
- 오타·한 줄 수정·포맷팅 등 사소한 변경은 **작성하지 않는다**.

## 작성 시점 (MUST)

1. **작업 시작 시**: 보고서를 먼저 만들고 개요·배경/목적·계획을 적는다 (착수 전 기록 → 중단돼도 의도가 남는다).
2. **진행 중**: 중요한 결정·발견·막힌 지점이 생기면 그때그때 갱신한다.
3. **완료 시**: 결과·남은 일(다음 단계)·관련 파일로 마감한다.

## 보안 (MUST)

- 보고서에 **시크릿·개인정보·DB 접속정보를 절대 적지 않는다** (`security.md`, 조직 보안정책). 파일·키·엔드포인트 "이름"까지만, 값은 금지.
- **커밋 해시는 기록하지 않는다** (파일명만). 이력은 `git log`로 찾는다.
