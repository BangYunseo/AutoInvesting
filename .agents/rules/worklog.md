# 작업 보고서(Worklog) 규칙

기능 단위 작업을 할 때는 **인계(handoff)용 짧은 보고서**를 남긴다.
목적은 **세션이 강제 종료되거나 만료돼도, 그 보고서만 보면 "무슨 작업을 왜 했고, 어디까지 됐고, 다음에 뭘 할지"를 다시 파악**할 수 있게 하는 것이다.
(전체 개발 이력 = `Documents/DEVELOPMENT.md`, 일회성 분석 = 본 worklog와 별개. worklog는 **진행 중 상태를 담는 살아있는 인계 노트**다.)

## 위치 · 파일명 (MUST)

- 폴더: **`Documents/worklog/`**
- 파일명: **`YYMMDD_짧은제목.md`** (예: `260629_DCA적립전환-머지.md`)
- 템플릿: `Documents/worklog/_TEMPLATE.md`

## 적용 범위 (MUST)

- **기능 단위 작업에만** 작성한다 — 사용자가 요청한 "동작하는 기능" 개발, 여러 파일에 걸친 변경, 아키텍처/머지/마이그레이션 등.
- 오타·한 줄 수정·포맷팅 등 사소한 변경은 **작성하지 않는다**.

## 작성 시점 (MUST)

1. **작업 시작 시**: 보고서를 먼저 만들고 **목적 / 요청 내용 / 계획**을 적는다 (착수 전 기록 → 중단돼도 의도가 남는다).
2. **진행 중**: 중요한 결정·발견·막힌 지점이 생기면 그때그때 갱신한다 (상태가 항상 최신이어야 인계가 된다).
3. **완료 시**: **완료 내역 / 남은 일·다음 단계 / 관련 파일**로 마감한다.

## 보안 (MUST)

- 보고서에 **시크릿·개인정보·DB 접속정보를 절대 적지 않는다** (`security.md`, 조직 보안정책). 파일·키·엔드포인트 "이름"까지만, 값은 금지.

## 보고서 형식 (`_TEMPLATE.md` 기준)

```markdown
# YYMMDD 작업 제목

- 상태: 진행중 | 완료 | 보류
- 작성/갱신: YYMMDD

## 목적 / 요청
무엇을 왜 하려는가 (사용자 요청 요약).

## 계획
어떤 순서로 할지 (착수 전 작성).

## 진행 / 결정
한 일, 중요한 판단·발견, 막힌 지점 (진행하며 갱신).

## 남은 일 / 다음 단계
중단 시 여기서부터 이어가면 되는 항목.

## 관련 파일
변경/산출 파일명 (값이 아닌 이름만). **커밋 해시는 기록하지 않는다** — 해시로 되짚어 revert하는 경우가 거의 없어 유지 비용만 든다. 필요하면 `git log`로 찾는다.
```
