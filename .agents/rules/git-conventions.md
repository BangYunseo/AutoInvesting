# Git 컨벤션

## 커밋 메시지 형식

```
<type>: <subject>
```

- 스코프(scope) 없이 type만 사용
- 커밋 메시지는 **한국어**로 작성
- 제목은 50자 이내
- 기능 단위별로 끊어서 커밋 (한 번에 모든 변경 커밋 금지)

## 커밋 타입

| 타입 | 설명 | 예시 |
|------|------|------|
| `feat` | 새 기능 | `feat: KIS API 토큰 매니저 구현` |
| `fix` | 버그 수정 | `fix: 스케줄러 중복 실행 방지 로직 수정` |
| `refactor` | 리팩토링 | `refactor: SPA 패널 전환 방식 적용` |
| `docs` | 문서 | `docs: README 증권사 정보 업데이트` |
| `style` | 코드 스타일 | `style: 코드 포맷팅 정리` |
| `design` | UI 디자인 변경 | `design: 대시보드 카드 레이아웃 수정` |
| `chore` | 빌드/설정 | `chore: gitignore 시크릿 파일 제외 추가` |
| `test` | 테스트 | `test: PlanPurchases 배분 시나리오 단위 테스트 추가` |
| `perf` | 성능 개선 | `perf: 환율 조회 캐싱 적용` |
| `ci` | CI 설정 | `ci: GitHub Actions 빌드 워크플로우 추가` |
| `rename` | 파일/폴더 이름 변경만 | `rename: DcaEngine → DcaAccumulationEngine 파일명 변경` |
| `remove` | 파일 삭제만 | `remove: 미사용 LegacyBroker.cs 삭제` |
| `build` | 빌드 파일 수정 | `build: .NET 8.0 타겟 프레임워크 명시` |

```
# ✅ 올바른 예
feat: KIS API 토큰 매니저 구현
fix: 보유 잔고 조회 시 빈 응답 예외 처리 추가

# ❌ 금지 — 스코프 사용
feat(core): KIS API 토큰 매니저 구현
```

## 브랜치 전략 (솔로 개발 기준)

이 프로젝트는 **1인 개발**이며 `main`이 곧 Render.com 배포 대상이다.
브랜치가 오래 갈라져 `main`에 미배포 커밋이 쌓이는 일을 막기 위해, **`main` 단일 + 단기 임시 브랜치** 방식을 따른다.

| 브랜치 | 용도 |
|--------|------|
| `main` | **기본 작업 + 배포 브랜치.** 항상 최신·배포 가능 상태를 유지한다. 일반 작업은 여기서 직접 커밋한다. |
| `feature/xxx`, `fix/xxx` | 큰 실험·위험한 변경에만 임시로 사용. **완료 즉시 `main`에 머지하고 삭제한다.** |

### 운영 원칙 (MUST)
- **임시 브랜치를 오래 들고 있지 않는다.** 한 작업 단위가 끝나면 바로 `main`에 머지(fast-forward 권장)하고 브랜치를 삭제한다.
- **`main`에 미배포 커밋을 누적하지 않는다.** 머지 후 곧바로 `git push origin main`으로 원격과 동기화한다 (원격 = 배포 트리거).
- 머지 전 `git rev-list --count HEAD..main`으로 분기 여부를 확인한다 (0이면 fast-forward 가능).
- push는 항상 명시적 확인 후 진행한다 (프로덕션 재배포를 유발하므로).

### 새 브랜치 라이프사이클 (MUST)

새 브랜치를 만들어 작업할 경우, 아래 단계를 **순서대로** 모두 거친 뒤에만 `main`에 반영한다.
어느 한 단계라도 건너뛰고 `main`에 머지하지 않는다.

1. **분기**: `main` 최신 상태에서 `feature/xxx`(또는 `fix/xxx`)를 만든다.
2. **브랜치 테스트**: 그 브랜치에서 빌드(`dotnet build`, 오류 0)와 동작 검증을 마친다. 필요 시 `IS_PAPER_TRADING`(SimBroker) 모드로 먼저 확인한다.
3. **사용자 테스트 완료 확인**: **사용자가 직접 테스트해 OK한 것을 확인한 뒤에만** 다음 단계로 진행한다. 에이전트 판단만으로 `main` 머지를 진행하지 않는다 (`main` = 프로덕션 배포 대상).
4. **main 머지**: 사용자 승인 후 `main`으로 머지한다(fast-forward 권장). 머지 직후 `git push origin main`으로 동기화한다(재배포 트리거 — push 전 명시적 확인).
5. **브랜치 삭제**: 머지가 끝나면 해당 브랜치를 **로컬·원격 모두 삭제**한다 (`git branch -d <name>` + `git push origin --delete <name>`).

> **드리프트 방지 (교훈)**: 브랜치가 `main`보다 오래 뒤처지면(예: 수십 커밋) 머지 시 충돌이 폭증하고 `main`의 최신 수정이 유실될 위험이 커진다. 브랜치는 짧게 유지하고, 길어지면 주기적으로 `main`을 머지/리베이스해 최신 상태로 따라간다.

> 협업 인원이 늘면 `dev` 통합 브랜치 + PR 리뷰 방식으로 다시 강화한다.
